12 — Business Rules Specification

Purpose of this Document

The Business Rules Specification defines the policies, validations, constraints, and decision logic governing the FD Booking module.

These rules ensure that the platform behaves consistently regardless of the client application (Web, Mobile, APIs, or future channels). By separating business rules from presentation logic, the platform becomes easier to maintain, audit, test, and extend.

This document serves as the authoritative reference for Product, Engineering, QA, Compliance, and Partner Integrations.

Objectives

The Business Rules document answers:

What actions are allowed?
Under what conditions?
What validations are mandatory?
Which rules are configurable?
Which rules are defined by partner banks?
Which rules are defined by regulations?
What should happen when a rule is violated?

1. Investment Rules
Rule BR-INV-001
Rule

Investment amount must satisfy the product's minimum investment amount.

Validation
Investment Amount >= Product Minimum Amount
Failure

Display:

The minimum investment for this product is ₹XX,XXX.

Owner

Product Configuration

Rule BR-INV-002
Rule

Investment amount cannot exceed the product's maximum limit.

Validation
Investment Amount <= Product Maximum Amount
Rule BR-INV-003
Rule

Investment amount must be entered in supported increments.

Example

Minimum

₹10,000

Increment

₹1,000

Valid

₹15,000

Invalid

₹15,550

Rule BR-INV-004
Rule

Estimated returns must always be recalculated whenever:

Amount changes
Tenure changes
Interest payout changes

Never cache outdated calculations.

2. Product Rules
Rule BR-PROD-001

Product must be active.

Rule BR-PROD-002

Booking window must be open.

Rule BR-PROD-003

Interest rate displayed during booking must match the current partner bank rate.

If the rate changes before confirmation:

Notify the user.
Recalculate returns.
Require confirmation before proceeding.
Rule BR-PROD-004

Products that become unavailable during booking cannot proceed to payment.

Offer:

Refresh
Similar Products
Return to Marketplace
3. Investor Rules
Rule BR-INVESTOR-001

Investor profile must be complete before booking.

Required information should be configurable to support different partner requirements.

Rule BR-INVESTOR-002

Previously verified information must never be requested again unless it has expired or requires re-verification.

Rule BR-INVESTOR-003

Only collect information that is required for the selected product and applicable regulations.

Avoid unnecessary data collection.

4. Nominee Rules
Rule BR-NOM-001

If nominee information is mandatory for a product or regulation, booking cannot continue without a nominee.

Rule BR-NOM-002

If nominees are optional, clearly explain the implications of proceeding without one.

Rule BR-NOM-003

Existing nominees should be reusable across future bookings unless the user chooses to update them.

5. Banking Rules
Rule BR-BANK-001

Only verified bank accounts may be used for investment funding.

Rule BR-BANK-002

Funding account and maturity account may be the same unless partner-specific rules require otherwise.

Rule BR-BANK-003

If multiple eligible accounts exist, users must explicitly select the account for the current booking.

6. Payment Rules
Rule BR-PAY-001

Payment must be initiated only after all validations have passed.

Rule BR-PAY-002

A failed payment must not erase booking progress.

Users should be able to retry without re-entering information.

Rule BR-PAY-003

Pending payments must expose their current status until a terminal outcome is reached.

Rule BR-PAY-004

Duplicate payment requests for the same booking must be prevented through idempotency mechanisms.

7. Booking Rules
Rule BR-BOOK-001

Every booking must have a unique Booking Reference generated by the platform.

Rule BR-BOOK-002

A booking should transition through only valid workflow states.

Example:

Initiated

↓

Review

↓

Payment

↓

Processing

↓

Confirmed

Skipping states is not permitted unless explicitly defined.

Rule BR-BOOK-003

Only confirmed bookings may create portfolio holdings.

Pending or failed bookings must never appear as active investments.

8. Compliance Rules
Rule BR-COMP-001

Required declarations must be accepted before payment.

Rule BR-COMP-002

Accepted consent records must be immutable and audit-friendly.

Rule BR-COMP-003

Every regulatory action must be timestamped and linked to the booking.

9. System Rules
Rule BR-SYS-001

User progress should be preserved automatically throughout the booking journey.

Rule BR-SYS-002

The investment summary must remain accessible at every booking stage.

Rule BR-SYS-003

Validation should occur as early as possible to prevent downstream errors.

Rule BR-SYS-004

The system should provide meaningful, user-friendly messages instead of technical errors.

10. Recovery Rules
Rule BR-REC-001

If the session expires, restore the booking after re-authentication whenever possible.

Rule BR-REC-002

If the network connection is interrupted, preserve local progress and synchronize when connectivity returns.

Rule BR-REC-003

If partner bank confirmation is delayed, place the booking in a "Pending Confirmation" state and keep the user informed.

Design Implications
Product Decisions
Centralize business rules so all channels enforce the same logic.
Differentiate configurable rules (partner-specific) from core platform rules.
Document every rule with a unique identifier to support traceability.
UX Decisions
Translate rule violations into clear, actionable guidance.
Validate early and contextually.
Explain why a rule exists when it affects the user's journey.
Engineering Decisions
Implement business rules within the domain layer, not the UI.
Externalize configurable rules to support multiple banking partners.
Ensure every rule is independently testable and version-controlled.
QA Decisions
Every rule becomes one or more automated test cases.
Validate happy paths, boundary values, and failure scenarios.
Maintain traceability from business rule to implementation and test coverage.
Document Outcome

The Business Rules Specification establishes the behavioral contract for the Booking module. By defining rules independently of the user interface, the platform ensures consistent behaviour across all clients, simplifies partner integrations, supports regulatory compliance, and provides a maintainable foundation for future investment products.

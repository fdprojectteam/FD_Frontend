17 — Canonical Data Model (CDM)
Purpose of this Document

The Canonical Data Model (CDM) defines the authoritative business entities used throughout the FD Investment Platform.

Rather than modeling data around databases, APIs, or user interfaces, the CDM models data around the business.

Each entity has:

A single owner
A clear business purpose
Defined relationships
Lifecycle
Ownership boundaries
Immutable and mutable attributes

The CDM serves as the common language across Product, Frontend, Backend, Data Engineering, QA, Analytics, and Partner Integrations.

Why Canonical?

Without a Canonical Model:

Frontend
Booking.amount

Backend
depositAmount

Payment
investmentValue

Portfolio
principal

Analytics
fdAmount

Five different names.

Same business concept.

Eventually, every team interprets it differently.

With a Canonical Model:

InvestmentAmount

Every service.

Every API.

Every event.

Every UI.

Uses the same business terminology.

Canonical Principles
1. Single Business Meaning

Every attribute must represent exactly one business concept.

Example

✅ InvestmentAmount

Not

❌ Amount

❌ Value

❌ Deposit

2. Single Owner

Every entity belongs to exactly one business domain.

Example

Investor

↓

Owned by Investor Service

Booking never owns investor information.

3. Shared Vocabulary

Every team uses identical terminology.

Examples

Booking Reference
Investment Amount
Interest Rate
Portfolio Holding
Maturity Date
4. Technology Independent

The CDM is independent of:

Database design
API contracts
UI implementation
Programming language

Design Implications
Product Decisions
Establish a shared business vocabulary across all teams.
Avoid duplicate representations of the same business concept.
Model entities based on business meaning rather than implementation convenience.
UX Decisions
Use consistent labels and terminology throughout the user journey.
Ensure displayed data aligns with the canonical definitions to build trust and reduce confusion.
Engineering Decisions
Generate API contracts and frontend models from the canonical entities.
Avoid duplicating ownership of business data across services.
Treat immutable fields as append-only to support auditing.
QA Decisions
Validate that every API, UI component, and event adheres to the canonical definitions.
Include consistency checks between services during integration testing.
Canonical Data Decision Records
Decision 01 — Single Business Vocabulary

Decision: Every business concept has one canonical name used across the platform.

Why: Prevents inconsistencies between frontend, backend, APIs, analytics, and documentation.

Decision 02 — Single Entity Ownership

Decision: Each entity has one authoritative owner.

Why: Eliminates conflicting updates and establishes a clear source of truth.

Decision 03 — Prefer Derived Values

Decision: Calculate values such as estimated returns rather than storing them unless required for historical accuracy.

Why: Reduces redundancy and ensures calculations remain consistent when inputs change.

Document Outcome

The Canonical Data Model establishes the common business language for the FD Investment Platform. It defines the core entities, their ownership, relationships, lifecycle characteristics, and naming standards, ensuring consistency across product design, engineering, integrations, analytics, and operations.

This document becomes the foundation from which API contracts, event schemas, frontend models, database schemas, and reporting structures can all be derived.

## 1. Architecture decisions

### D-M1 — The cap is enforced by disabling, and read from the store

`addId` does not consult the cap, by design (T2.7.2; a second enforcer is what
O1 closed). So the **picker must not offer an Add it cannot honour**: an Add on
a fifth product appends to the URL, the store caps display at four, and the
product the user just added is never shown — it lands in the hidden tail and
surfaces only after a later removal (R13a). The click appears to do nothing.

- `ComparePicker` receives **`isFull: boolean`** and **`isSelected`**, both
  derived by the screen (see D-AUTH below for *from what*).
- **No `MAX_COMPARE` import.** That would be a third enforcer and would fail the
  exact-list probe that closes O1.
- Add is disabled when `isFull || isSelected(id)` — **two reasons, distinguished
  for the user** (D-m5).

### D-AUTH — Both derivations read the route's authority, not its mirror

On `/compare` the URL is the selection (C4); the store follows it. Deriving the
picker's state from the store would read a value that lags the URL by a render,
which is what makes the race in D-PENDING possible in the first place.

```
isSelected(id)  ≡  ids.includes(id)              // count and membership: URL
isFull          ≡  ids.length >= selection.max   // limit: store
```

The split is deliberate and is the same one the URL→store sync already makes:
**the count comes from the URL, the limit comes from the store.** `selection.max`
is what the store publishes about itself, so the cap stays owned by one module
(C2) — and `MAX_COMPARE` is not imported, nor is `4` written anywhere.

Note that `ids` is uncapped by design (the parser does not cap — D8), so
`ids.length` is the honest count including any over-cap tail.

### D-PENDING — One Add at a time, guarded by the screen

D-O4 keeps the dialog open **specifically to invite multiple Adds**, and that is
what makes this necessary. `addId` computes the next list from `ids`, which
comes from `useSearchParams`; `ids` lags a `push` by at least a render, with the
comparison's refetch behind it. Two Adds inside that window either write a list
that never contained the first product, or both compute against
`isFull === false` and put a fifth id in the URL that is never displayed —
which is M1's failure arriving through a different door.

- `CompareScreen` records the **pending id** when `onAdd` fires.
- While a pending id is set, **every Add is disabled** — not only the pending
  one, because the hazard is the stale `ids`, not the repeated product.
- The guard clears when **either**:
  1. the pending id appears in `ids`, or
  2. `ids` changes for any other reason.

**Both branches are required.** `addId` returns early without navigating if the
id is already present, so a guard waiting only for condition 1 would never clear
and the dialog would sit with every Add disabled. Condition 2 also releases the
guard on Back/Forward, which is correct: a history navigation makes the URL
authoritative again.

#### D-PENDING is not verifiable in the current harness

*(Established by runtime evidence during T2.7.6 closure; see
`verification/README.md`.)*

The harness's `router.push` notifies **synchronously**, so `pendingAddId` is set
and cleared within one React flush and the disabled window has **zero width**.
The lag the guard exists to bridge — an asynchronous App Router navigation where
a render occurs with the pending id set and `ids` not yet updated — **does not
exist in jsdom**.

The consequence is precise, and worth stating rather than filing away:

| | Status |
|---|---|
| The guard **releases** (no deadlock) | **Verified** — L3b |
| The guard **engages** (blocks a second Add while one is in flight) | **Not verifiable here.** Manual browser check |

The first attempt at L3b forced the race by firing two clicks in one synchronous
turn. That models an interaction a user cannot perform — two real clicks are
separate tasks with a React flush between them — and a render-based guard cannot
defend against it by construction. It failed for that reason, not because the
guard is wrong.

**Why the guard is still required**, despite being unverifiable here: with the
real App Router `push` is asynchronous, so a render *does* occur with the pending
id set and `ids` stale, and without the guard the second click would compute from
that stale list and drop the first product. Recording this matters — a future
reader finding untested concurrency code has every reason to delete it.

This is a **behavioural** limitation, unlike the layout and browser-API gaps
(scroll-snap, sticky positioning, `next/image`, the focus trap). It is the first
in the compare feature and is listed separately for that reason.

**The second intent is dropped, not queued** (confirmed after the T2.7.6
implementation review). A user who clicks twice quickly gets one product and
clicks again; the guard does not remember the second click and replay it.
Queuing is deliberately **out of scope for T2.7.6** — it would need an intent
buffer and a decision about what happens if the queued Add would exceed the cap.

This is the smallest guard that preserves D-O4. Reversing D-O4 — closing the
dialog on Add — was the alternative and was rejected: it removes a sensible
interaction to avoid a race rather than addressing it.

### D-M2 — The screen owns the dialog's open state *and* the catalogue query

I3/I2a: only the screen owns hooks. But an unconditional catalogue fetch on
every `/compare` visit competes with the comparison batch for a page the user
may never open. The two are one decision, because the query must be gated on the
state:

```
CompareScreen
  ├─ const [pickerOpen, setPickerOpen] = useState(false)
  └─ useProducts(PICKER_PARAMS, { enabled: pickerOpen })
```

**This requires the one shared change in this task:** `useProducts(params?)`
gains an optional second argument carrying `enabled`. Additive, no existing call
site changes, and it keeps `ComparePicker` presentation-only. The alternative —
letting the picker fetch — makes it a second hook owner on the route.

### D-M3 — Nothing about the picker touches the URL except the Add

`/compare`'s parameter set is closed at **`ids` alone**. Dialog visibility, the
picker's page index and its scroll position are transient (I6).

- Paging state, if reached, is **local to the screen**.
- `useMarketplaceUrlState` is **not** imported by anything under `/compare` —
  its parameters belong to Home.
- The only URL write the picker causes is `addId`, through the existing writer:
  one `push` per Add (I8).

### D-M4 — The picker renders its own row, not `FDProductCard`

The card is prop-compatible to a suspicious degree — it already takes
`onCompare`, `isComparing`, `compareDisabled`. But T2.6.8 gave it a real
`<Link>` to the product route, and inside a dialog that **navigates away,
unmounting the comparison the user is assembling.** Its action also reads
"Compare", which on Home writes the store and here must write the URL: one
component, two authorities.

`ComparePicker` therefore renders a slim row — bank badge, bank name, rate,
tenure, Add — with no link and no second action. The row has one consumer and
stays internal to the picker; it earns its own component only if a second
consumer appears.

**Enforced on the import, not on the markup.** The obvious probe — "the picker
contains no `<Link>` and no `ROUTES.product`" — **does not catch this defect**:
a picker that imports `FDProductCard` contains neither string, because the link
is inside the card. The probe would pass while the exact failure ships, in the
same shape as the O1 probe that was named "enforced in the store, and only
there" and never looked at the file where the second enforcer lived.

So the primary invariant is: **`compare-picker.tsx` does not import
`FDProductCard`.** The `<Link>` / `ROUTES.product` check is kept as a secondary
net, catching a hand-rolled link rather than an inherited one.

### D-O3 — One page, sized by a constant, with the existing pager as the escape hatch

`PICKER_PAGE_SIZE` (24 today, matching the catalogue) is passed to
`useProducts`, so the dialog opens on a single scrollable list: one request, no
pager, no second interactive region inside a modal, no focus management beyond
Radix's own.

The existing `Pagination` component is rendered **only when the response reports
`totalPages > 1`**. That costs nothing today and keeps the picker correct if the
catalogue outgrows one page — rather than encoding "the catalogue fits on one
page" as an invisible assumption.

**The pager is an intentionally dormant path, and is recorded as one.** With
`PICKER_PAGE_SIZE = 24` against a 24-product catalogue, `totalPages` is 1, so
the condition is never true: **no user and no test reaches the pager today.**

- **Activation condition:** the catalogue exceeds `PICKER_PAGE_SIZE`, i.e. the
  batch response reports `totalPages > 1`.
- **Until then it is unexercised**, and no assertion should be written that
  implies otherwise.
- Precedent: `correct()` shipped one task ahead of its consumer in T2.7.2 under
  the same rule — a dormant path is acceptable when it is *named*, and a defect
  when it is assumed covered.

The key differs from Home's listing (`limit` differs), so nothing is shared with
the listing cache. Accepted: one request, gated on open.

### D-O4 — The dialog stays open after an Add

Adding is often plural — the user came to add *products*, not a product. Staying
open gives immediate feedback in place: the row they just added becomes
"Added" and disabled, and the count in the title rises behind the dialog. When
the fourth is reached, every Add disables and the limit message appears
(D-m5), which is a clearer end than the dialog vanishing.

Each Add is one `push` either way (I8), so two Adds produce two history entries
and Back undoes them one at a time.

## 2. Ownership and component boundaries

| Concern | Owner |
|---|---|
| Dialog open state | `CompareScreen` (local, transient — I6) |
| Catalogue query | `CompareScreen`, gated on open (D-M2) |
| Page index, if used | `CompareScreen` (local) |
| **Pending Add** | `CompareScreen` (local), cleared per D-PENDING |
| "Is this product selected?" | `CompareScreen`, from **`ids`** — `ids.includes(id)` (D-AUTH) |
| "Is the comparison full?" | `CompareScreen`, from **`ids.length >= selection.max`** — count from the URL, limit from the store (D-AUTH) |
| Adding | `useCompareUrlState.addId` — the route's existing single writer |
| Rendering the list | `ComparePicker` — presentation-only, props in, callback out |
| Accessible names | `utils/compare-labels.ts` (`addLabel`) |

`ComparePicker` props: `open`, `onOpenChange`, `items`, `isLoading`, `isFull`,
`isSelected`, `isAddPending`, `onAdd`, and pagination props if `totalPages > 1`.

It receives **answers, not inputs**: `isFull` and `isSelected` arrive already
derived, so the picker never chooses between the URL and the store and cannot
disagree with the screen about either.

**It never learns that a URL exists** (O1). That is what I3 requires and, not
coincidentally, what would let a future Booking flow reuse it.

## 3. Data flow

```
CompareScreen
  ├─ useCompareSelection() ────────────────► isFull
  ├─ useCompareUrlState(selection) ────────► ids, addId
  ├─ useCompareProducts(selection.ids) ────► the comparison
  └─ useProducts(PICKER_PARAMS, {enabled}) ► the catalogue
                                              │
                                              ▼
                                        ComparePicker
                                              │  onAdd(productId)
                                              ▼
                                   addId → push ?ids= → store follows (C4)
```

One direction. The picker reports an intent; the URL is written by the writer
that already owns it; the store follows the URL, as on every other interaction
on this route.

**Two "add" paths exist in the module and they are not interchangeable** (O2):
Home's product card writes the **store**; the picker writes the **URL**. Both
are correct — that is C4's per-route authority — and it is the thing most likely
to be got wrong by whoever builds R15a's floating bar.

## 4. Responsive strategy

The trigger lives in the title row, **outside both `data-compare-view`
containers**, and the dialog is portalled to `document.body`. So there is
**exactly one trigger and one dialog at every breakpoint** — no duplication to
disambiguate.

The label shortens inside that one button:

```
Add<span className="hidden md:inline"> another FD</span>
```

Same technique as the `h1` (T2.7.5). **Two buttons would be wrong**: it would
put two triggers in the DOM and two in the harness, for a control that is
singular (D-m2).

**The dialog itself has no mobile variant.** The approved design never shows it
open, `DialogContent` is already responsive, and inventing a second layout would
be UI the design does not have. Recorded as assumption **A10**.

## 5. Accessibility decisions

| # | Decision |
|---|---|
| A-1 | The dialog uses `DialogTitle` and `DialogDescription`; the description states the limit ("Compare up to four") so it is available before anything is disabled |
| A-2 | Each Add names its product — `addLabel(bankName)` → "Add HDFC Bank to comparison" — never four identical "Add"s (WCAG 2.4.6, the M2.5 pill precedent) |
| A-3 | An already-compared row shows a visible "Added" state and its control is `disabled` — it cannot act, so it is genuinely disabled rather than `aria-disabled` |
| A-4 | **When full, a `role="status"` line above the list says so** (D-m5). Disabled controls with no explanation are the accessibility failure mode of a limit, and at four selected *every* row is disabled |
| A-5 | Radix owns focus trap and restore. **Partially observable in jsdom** — a green L3 does not mean the dialog is accessible; that is a browser check |
| A-6 | The trigger is one button (§4), so a screen-reader user meets one "Add another FD", not two |

## 6. Verification impact

### 6.1 Scoping — the convention's gap (m1)

Radix portals `DialogContent` to `document.body`, **outside both
`data-compare-view` containers**. The scoping convention does not reach it.

**Dialog assertions are scoped to `[role="dialog"]`**, and the convention is
amended to say that portalled content is scoped by role rather than by
`data-compare-view`. Without this, dialog selectors would be document-wide —
the precise hazard the convention exists to remove.

### 6.2 Added — journeys

**`L3 · Add via the picker`**, scoped to `[role="dialog"]`: the trigger is
present exactly once · opening lists the catalogue · rows already in the
comparison are disabled and marked "Added" · adding performs **one push** and
the URL gains the id in last position · the dialog **stays open** and the added
row becomes disabled in place (D-O4) · adding to four disables every remaining
Add and shows the limit message (D-M1, A-4) · **the URL never gains a fifth id**
· closing the dialog performs no navigation.

**The Add must be proved end to end**, not merely to the URL. One assertion
follows the whole chain after the refetch settles: URL → store (via
`replaceAll`) → `useCompareProducts` → **a new column in the comparison**. That
chain is the point of C4 and it has a network round trip in it; asserting only
that the query string changed proves the writer works, not the feature.

**`L3b · Two Adds inside one navigation window`** — the race D-PENDING exists
to prevent:

- fire **two Add clicks with no `await`, no `settle()` and no `waitFor()`
  between them**;
- *then* wait once for the URL to settle;
- assert the **guarded** outcome: the second control was already disabled when
  the second click was issued, the first Add landed, the second product is
  absent, and exactly one product was added.

**Superseded at closure.** Runtime evidence showed this is unobservable in the
harness (see D-PENDING above), so `L3b` now verifies the half that *is*
observable — **the guard releases**: after an Add settles the next Add is enabled
again, both products land in click order, and there is one push per Add with no
correction. It does not claim to test engagement.

Two earlier versions of this journey were wrong in instructive ways: the first
asserted an id the journey had been *loaded* with, so no click could affect it;
the second forced a synthetic race the environment cannot express. Rows carry
`data-product-id` because bank names are not unique and the catalogue is returned
in rate order, so neither name nor position identifies a product.

**The absence of an await between the clicks is the assertion.** A `settle()`
slipped in serialises the interaction and the test then proves only what L3
already covers — vacuously green. This is the third time in this milestone an
assertion could have passed without exercising its subject, so it is stated as a
constraint rather than left to the writer's care.

### 6.3 Added — invariants

`ComparePicker` is presentation-only (no data hook, no router, no store) ·
it does not import `MAX_COMPARE` · **no file under the compare feature imports
`useMarketplaceUrlState`** (D-M3) · `addLabel` is centralised and no component
composes that name inline · the compare URL writer still emits `ids` and nothing
else · `useProducts`' new option is additive — its existing call sites are
unchanged.

**D-M4, enforced in two layers** (the first is the one that works):

| # | Probe | Catches |
|---|---|---|
| 1 | `compare-picker.tsx` does **not import `FDProductCard`** | The inherited link — the actual failure mode |
| 2 | The picker contains no `<Link>` and no `ROUTES.product` | A hand-rolled link |

**D-AUTH, enforced on the derivation:** the screen computes `isFull` from
`ids.length >= selection.max`; neither `MAX_COMPARE` nor a literal `4` appears
in the compare feature outside the store.

### 6.4 Added — units

`addLabel` renders the approved sentence; `compare-labels.ts` remains the only
place any of the three names is composed.

### 6.5 Unchanged

L0, L4, L4b, L6, L6b, L6c, L7, L9, L9b, every M2.5/M2.6 journey, the boundary
suite, and every existing probe. **No assertion text changes** — the picker adds
markup, it does not alter what exists.

## 10. Sequencing

1. **`addLabel` + `useProducts`' optional `enabled`.** Suite must stay green
   **with no assertion edits** — an additive change that alters no assertion is
   the only kind that can be shown not to have changed behaviour.
2. `ComparePicker`, presentation-only and props-driven — mountable and
   inspectable before anything is wired.
3. Screen wiring: trigger, open state, gated query, `isSelected`, `isFull`
   (both per D-AUTH), the pending guard, `onAdd → addId`.
4. L3 and **L3b**, scoped to `[role="dialog"]`. **L3b before the invariants** —
   it proves the guard *releases*, and a guard that never cleared would leave
   the dialog permanently inert. That failure is worth ruling out while the
   wiring is still fresh. (It does **not** prove the guard engages; that is the
   documented behavioural limitation.)
5. Invariant section; unit assertion; full suite; baseline.
6. Documentation (§8).

Step 1 first for the same reason it was first in T2.7.5, and step 2 before
step 3 so the picker is proven not to need anything it was not given.

## 11. Acceptance criteria

- The approved trigger renders **once**, with the label shortened inside it
- The dialog lists the catalogue, gated on open — no fetch when it never opens
- Rows already being compared are disabled and marked "Added"
- **Add is impossible at four**, the limit is stated, and the URL never gains a
  fifth id
- `isSelected` and `isFull` derive from **`ids`**, with the limit read as
  `selection.max` — no `MAX_COMPARE` and no literal `4` in the compare feature
- **The pending guard releases**: after an Add settles the next Add is enabled,
  both products land in click order, one push each (L3b). Engagement is
  **verified manually in a browser**, not by the suite
- The pending guard clears on either branch, so a no-op Add cannot deadlock it
- Adding performs exactly one `push`; the store follows the URL, and **a new
  column appears in the comparison** — the chain asserted end to end
- The dialog stays open after an Add
- The picker **does not import `FDProductCard`**, and imports no `MAX_COMPARE`,
  no `useMarketplaceUrlState`, no data hook and no router; it contains no
  `<Link>`
- The pager is recorded as dormant, with `totalPages > 1` as its activation
  condition, and nothing asserts it is exercised
- `addLabel` is the only place that name is composed
- Dialog assertions are scoped to `[role="dialog"]`; no document-wide compare
  selector is introduced
- No new primitive, no new dependency, no new query key
- Every existing assertion passes **with its text unchanged**
- Full suite green — **640 assertions measured** after the closure rewrite
  (150 unit · 257 invariants · 15 boundaries · 218 journeys)

# T3.2.10 — Tenure Selector: Readiness Package

**Date** 2026-08-06 · **Status** awaiting product data and two decisions
**Blocks** T3.2.10 · **No implementation. No code was written for this document.**

T3.2.9 is approved and the domain layer is complete. What remains before the

## 1. Required Product Data Specification

### 1.1 The shape

```ts
// src/types/finance.ts — already declared, awaiting data
interface TenureRate {
  tenureMonths: number;   // integer, > 0
  annualRate: number;     // percentage, e.g. 7.25 — never a fraction
}

// src/modules/booking/types/booking.ts — already declared
interface DepositTerms {
  tenureRates: TenureRate[];   // required, non-empty
  // …
}
```

Both types exist and are wired. **Nothing in this section requires a code
change — it is a request for values.**

### 1.2 Required fields

| Field | Type | Required | Rule |
|---|---|---|---|
| `tenureMonths` | integer | ✅ | `> 0`, whole months only |
| `annualRate` | number | ✅ | `> 0`, expressed as a percentage (`7.25`, not `0.0725`) |

Neither field is nullable. A row that cannot state both is not a row — it is a
tenure the bank has not priced, and the correct representation of that is
absence.

### 1.3 Validation rules

| # | Rule | Failure behaviour |
|---|---|---|
| V1 | `tenureMonths` is a positive integer | Row rejected; tenure not offered |
| V2 | `annualRate` is finite and `> 0` | Row rejected |
| V3 | `annualRate` is a percentage, not a fraction | A rate below `0.5` should be treated as suspect — no Indian FD pays 0.0725% |
| V4 | The array is non-empty | Product cannot be booked; screen shows the "no tenures available" state |
| V5 | `tenureMonths` values are unique | See §1.4 |
| V6 | Every rate is expressible to two decimals | `formatPercentage` trims to two; a third decimal would display rounded and reconcile wrongly |

**V3 is worth stating explicitly** because it is the single most likely data
error and the platform cannot detect it reliably: `7.25` and `0.0725` are both
valid numbers, and only one of them is a Fixed Deposit.

### 1.4 Uniqueness

**`tenureMonths` must be unique across the array.** Two rows for 24 months are
two different rates for one contract, and the platform has no rule for choosing
between them.

`resolveTenureRate` uses `Array.prototype.find`, so a duplicate would silently
resolve to whichever came first — a wrong rate with no error. **Recommendation:
the ingestion layer should reject duplicates rather than let the first win.**
Recorded as a verification item (§4.2, I-T4) rather than assumed away.

### 1.5 Ordering

**Ordering in the payload is not significant.** `selectableTenures` sorts
ascending by `tenureMonths` before anything renders, so a card supplied in any
order presents identically.

**Rates need not increase with tenure.** The resolver deliberately makes no
monotonicity assumption, and a unit assertion already covers an inverted curve
(36 months priced *below* 24). Banks publish inverted curves routinely, and a
control that assumed otherwise would misprice them.

### 1.6 Minimum required rows

| Rows | Consequence |
|---|---|
| **0** | Product unbookable. `validateTenure` returns *"This FD has no tenures available right now."* Chips and slider render nothing |
| **1** | Minimum viable. The control renders a single, pre-selected, read-only tenure and **no slider** — see §3 |
| **2+** | The control becomes a real choice |
| **≥ 4** | The approved artwork's chip row is populated as drawn |

**Minimum to unblock T3.2.10: 1 row.** The demo product already has it
(24 months @ 7.25%). **Minimum to match the approved artwork: 6 rows** — the six
non-Custom chips drawn, subject to §5.1.

### 1.7 Optional rows

Any tenure beyond the first is optional. There is no expectation that a card is
"complete": a bank offering only 12 and 24 months is a valid product, and the
control renders exactly two chips.

**Chips are derived from the card, never from a fixed list.** Adding a row adds
a chip with no code change — the property `selectableTenures` exists to
guarantee.

### 1.8 Unsupported tenures

A tenure absent from the card is **unsupported**, and the platform's behaviour is
already fixed and asserted:

- `resolveTenureRate(terms, n)` → `null`
- `isSupportedTenure(terms, n)` → `false`
- `calculateReturns(…)` → `null` — no figures at all
- Summary rail rate row → *"Not available for this tenure"*
- `validateTenure` → *"This FD is available for 12 months, 24 months or 36 months. Choose one of these to continue."*

**There is no fallback to the headline rate, and no interpolation between
published terms.** Decision C1 — *"Booking must not invent rates"* — and eleven
unit assertions enforce it. A 30-month deposit is not "the 24-month product for
longer"; it is a term nobody has quoted.

### 1.9 Future extensibility

The card will need to grow. These are the extensions already foreseeable, listed
so that today's shape does not preclude them:

| Extension | Driver | Shape impact |
|---|---|---|
| **Senior-citizen premium** | Spec 21b §G names senior benefits | `seniorRate?: number` per row, or a parallel card selected by investor profile |
| **Rate varies by payout mode** | Banks commonly price cumulative above monthly payout | Would make rate a function of *(tenure, payout)* — a **breaking** change to `resolveTenureRate`'s signature |
| **Amount slabs composed with tenure** | Marketplace already has `resolveApplicableRate` by amount | Composition order must be specified: tenure sets the base, amount may override |
| **Effective dating** | Doc 19 §Versioning — a booking must reference the rate effective when it was made | `effectiveFrom` / `effectiveTo` per row |
| **Day-granularity tenures** | The artwork's "7 Days" chip | **See §5.1 — this is a blocker, not an extension** |

Of these, **rate-by-payout is the one that would hurt.** It changes a signature
the returns engine, the summary rail and the validator all call. If partner banks
price payout modes differently, say so now and the parameter goes in before
three call sites depend on the current shape.

## 2. Integration Contract

### 2.1 What already exists

Every module below is **built, tested and approved**. T3.2.10 adds a control and
wires it; it adds no domain logic.

| Module | Signature | Status |
|---|---|---|
| `resolveTenureRate` | `(terms, tenureMonths) => number \| null` | ✅ T3.2.4b |
| `selectableTenures` | `(terms) => TenureRate[]` (ascending) | ✅ T3.2.4b |
| `isSupportedTenure` | `(terms, tenureMonths) => boolean` | ✅ T3.2.4b |
| `validateTenure` | `(tenureMonths \| null, terms) => string \| null` | ✅ T3.2.6 |
| `calculateReturns` | `({ principal, tenureMonths, payoutOption, terms, taxProfile? }) => ReturnsResult \| null` | ✅ T3.2.5 |
| `buildConfiguredSummaryRows` | `(deposit, configuration) => InvestmentSummaryRow[]` | ✅ T3.2.7 |
| `useBookingDraft().setInvestment` | `({ tenureMonths }) => void` | ✅ T3.2.2 |
| `Slider` | platform primitive | ✅ T3.2.3 |
| `Chip` | platform primitive | ✅ T1.5 |

### 2.2 Ownership

```
InvestmentDetailsScreen          orchestration only — owns no arithmetic
├── reads    useBookingDraft().draft.investment.tenureMonths
├── derives  selectableTenures(terms)          → what may be offered
├── derives  validateTenure(tenure, terms)     → the message
├── derives  calculateReturns({ … })           → every figure
├── derives  buildConfiguredSummaryRows(…)     → the rail
└── writes   setInvestment({ tenureMonths })   → the only writer

TenureSelector                   presentation only
├── receives options, value, error
└── emits    onChange(tenureMonths)
```

**`TenureSelector` must not import `resolveTenureRate`, `calculateReturns` or
`validateTenure`.** It receives what to render and reports what was pressed. This
is the same contract `PayoutOptionGroup` and `QuickAmountChips` already satisfy,
and it is asserted for both.

### 2.3 Execution flow — a tenure change

```
USER presses "24 Months" (or moves the slider, or types a custom month)
   │
   ▼
TenureSelector.onChange(24)
   │
   ▼
InvestmentDetailsScreen
   └── setInvestment({ tenureMonths: 24 })
          │
          ▼
   BookingDraftProvider                                  [T3.2.2]
   ├── React state updated (authoritative)
   └── effect → writeDraft() → sessionStorage            [FR-SYS-002]
          │
          ▼
   re-render — four derivations, each with one owner
          │
          ├── validateTenure(24, terms) ─────────────► message | null
          │
          ├── buildConfiguredSummaryRows(deposit, cfg) [T3.2.7]
          │     └── resolveTenureRate(terms, 24) ─────► rail rate row
          │                                             null → "Not available
          │                                                     for this tenure"
          │
          └── calculateReturns({ principal, 24, payout, terms })   [T3.2.5]
                ├── resolveTenureRate(terms, 24) ─────► null? ──► return null
                │                                        │
                │                                        └─► EstimatedReturns
                │                                            awaiting state
                └── rate found
                      ├── cumulative?  calculateMaturity()     [@/utils/maturity]
                      └── payout?      calculateSimpleInterest()
                            │
                            ▼
                      ReturnsResult ──► EstimatedReturns
                                        4 cells + Per Instalment
                                        aria-live="polite"      [C4]
```

**`resolveTenureRate` is called twice per change — once by the rail, once by the
returns engine — and that is correct.** Both read the same pure function over the
same card, so they cannot disagree; sharing a memoised value between them would
add a cache to save two array lookups.

### 2.4 The one contract change T3.2.10 requires

None to the domain. One to the screen: the `returns` memo currently guards on
`tenureMonths === null`, which today is always true. Once tenures are selectable
that guard starts passing, and the four-cell strip renders for the first time.
**No signature changes.**

## 3. UI Behaviour Matrix

Assumes the approved artwork: a chip row, a slider beneath it, and a `Custom`
affordance. **Rows 3 and 7 depend on §5.1 and §5.2 and cannot be built until
those are answered.**

| # | Situation | UI state | Interaction | Validation | Estimated Returns |
|---|---|---|---|---|---|
| **1** | **One tenure** (`tenureRates.length === 1`) | Single chip, pre-selected, visually static. **Slider suppressed** — a slider with one stop is a control that cannot be moved. `Custom` hidden | Chip is inert (already selected); no keyboard target beyond it | Always valid; no message | Renders in full as soon as amount and payout are set |
| **2** | **Multiple tenures** (`≥ 2`) | Chip per row, ascending. Slider spans the *set*, snapping to each published tenure — see §5.2 | Chips: single-select `radiogroup`, arrows move. Slider: arrows/Home/End move between published tenures | Valid on selection; message only if a stored draft holds an unsupported value | Recalculates on every change, announced politely |
| **3** | **Custom tenure** | ⚠ **Undefined — see §5.1.** As specified it opens a numeric month input; as specified it can almost never produce a priced tenure | — | — | — |
| **4** | **Unsupported tenure** (e.g. resumed draft, card changed) | No chip selected; slider at its lowest published stop; message shown | User must pick a published tenure to proceed | `validateTenure` → *"This FD is available for 12 months, 24 months or 36 months. Choose one of these to continue."* | `null` → awaiting state. **Rail rate row reads "Not available for this tenure"** |
| **5** | **Missing rate** (`tenureRates` empty) | No chips, no slider, no Custom. Region shows the empty message alone | Nothing selectable | `validateTenure` → *"This FD has no tenures available right now. Please choose another product."* | `null` → awaiting state |
| **6** | **Invalid month** (custom input: `0`, negative, fractional, `NaN`, empty) | Input marked `aria-invalid`; message beneath | Value not written to the draft; previous selection retained | `resolveTenureRate` rejects non-integers and `≤ 0`; message is `validateTenure`'s | Unchanged — the last valid configuration keeps its figures rather than blanking |
| **7** | **Out-of-range month** (integer, but not on the card — e.g. `30`) | Input accepted syntactically, then rejected semantically. Message names what *is* available | Not written to the draft | `validateTenure` → the "available for …" message | `null` → awaiting state |

**Rows 6 and 7 are deliberately different.** A malformed entry is a typing
mistake and must not destroy a working configuration; an out-of-range entry is a
real request the product cannot fulfil and must be answered with what it can.

**Row 4 is the one that will be seen in production.** A rate card changes, a
resumed draft holds a tenure that no longer exists, and the screen must recover
rather than quote a stale rate. The domain already returns `null` for it; the UI
work is showing the message and keeping the user moving.

## 5. Technical Review — assumptions still open

Two of these are likely blockers. They are raised now rather than discovered
mid-implementation.

### 5.1 ⚠ The artwork's "7 Days" chip cannot be represented — **likely blocker**

The approved artwork's first tenure chip reads **"7 Days"**. The domain has no
way to express it:

- `InvestmentConfiguration.tenureMonths: number | null`
- `TenureRate.tenureMonths: number`
- `resolveTenureRate` requires `Number.isInteger(tenureMonths)` and `> 0`

Seven days is 0.23 months. It is not an integer, and the platform's only unit of
tenure is the month. `DepositTerms.tenureRange` even advertises **"7 Days – 10
Years"**, so the product genuinely intends sub-month tenures.

This also makes **Custom tenure (behaviour row 3) largely unusable as
specified.** OQ-5 settled on a numeric *month* input, but `resolveTenureRate` is
an exact match against the card — so a custom entry only ever works if the month
the user types happens to be published, which makes the control a slower way to
press a chip.

**Options:**

- **A** — make **days** the canonical unit (`tenureDays`), with months as a
  display convenience. Most faithful to the product; touches `TenureRate`,
  `InvestmentConfiguration`, the persisted draft schema (**version bump**),
  `resolveTenureRate`, `validateTenure`, `formatTenure` and the returns engine's
  month arithmetic
- **B** — model tenure as `{ value, unit: 'days' | 'months' | 'years' }`. Most
  expressive, most invasive
- **C** — months only; **drop the "7 Days" chip** and narrow `tenureRange`.
  Cheapest, and contradicts both the artwork and the advertised range
- **D** — months only, and `Custom` is removed rather than shipped inert

**No recommendation without Product.** A and C are opposite answers to *"does
this platform sell short-term deposits"*, which is a product question. Note that
Founder §5 lists **"short-term parking"** among the goal-planner's use cases,
which points at A.

### 5.2 The slider's domain is undefined against a sparse card — **needs a decision**

The artwork shows a continuous slider beneath the chips. With a sparse card
(6 published tenures out of 120 possible months) a month-domain slider would let
a user land on 30 months and be told it does not exist — a control that mostly
produces errors.

**Recommendation: an index-domain slider.** `min=0`, `max=n-1`, one stop per
published tenure, `aria-valuetext` reading the tenure. It cannot select an
unpriced term, it needs no clamping, and `Slider` already supports it unchanged.

The cost is that spacing becomes non-linear — 3 and 6 months sit as far apart as
36 and 60. For a control whose stops are labelled by the chips above it, that is
the right trade. **Confirm before T3.2.10.**

### 5.3 Changing tenure may invalidate the selected payout — unhandled

Banks commonly restrict monthly payout on short tenures. `supportedPayouts`
(T3.2.9) is a property of the **product**, not of the *(product, tenure)* pair,
so the platform cannot currently express "monthly payout, but not under 6
months".

Today nothing breaks. If a partner bank has such a rule, `supportedPayouts`
becomes a function of tenure and the payout group needs to re-narrow — and a
user's already-chosen payout may become invalid mid-configuration. **Ask
Product whether any partner has tenure-dependent payout availability.**

### 5.4 Rate composition with amount slabs — unspecified

Marketplace has `resolveApplicableRate` (rate by **amount**); Booking now has
`resolveTenureRate` (rate by **tenure**). No product currently has both, so no
composition rule exists.

The moment one does, the order matters and both answers are defensible: tenure
sets the base and amount overrides, or the reverse. This is exactly the case
§5 of `shared-finance-layer.md` puts in `rates.ts` after refactor **R1**.
**Not a blocker for T3.2.10** — flagged so it is decided in R1 rather than
improvised.

### 5.5 Rate versioning and BR-PROD-003 — still unimplementable

BR-PROD-003 requires that a rate change mid-booking notifies the user,
recalculates, and demands confirmation. The card carries no `effectiveFrom`, and
there is no Booking endpoint to re-check against. Unchanged from the T3.2 plan's
decision D4; recorded so it is not mistaken for something T3.2.10 delivers.

### 5.6 Duplicate rows resolve silently — small, cheap to close

`resolveTenureRate` uses `find`, so duplicate `tenureMonths` resolves to the
first occurrence with no error. Harmless if ingestion rejects duplicates;
silently wrong if it does not. **Recommendation:** state uniqueness as a data
contract (§1.4) and add U-T9.

### 5.7 What is *not* an assumption

For completeness, these were checked and are settled — no action needed:

- Rate resolution, no-invention and no-interpolation — decided (C1), implemented, 11 assertions
- Payout semantics and the C4 rule — decided, implemented, asserted across every offered option
- Draft persistence and resume of a tenure — implemented and asserted
- Validation copy — implemented, plain-English, asserted against the spec's worked example
- `Slider` and `Chip` primitives — built, gallery-reviewed, no new dependency
- Post-tax — seam only, no assumptions (C6)

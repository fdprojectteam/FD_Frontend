## 1. Shared cell rendering — decision

### The unit

**`components/compare-value.tsx` — `<CompareValue row={row} column={index} />`.**

It renders the **content** of one comparison cell and nothing else:

| Responsibility | Why it belongs here |
|---|---|
| The value string `row.values[column]` | Indexing happens once, not per presentation |
| `NO_VALUE` → visible `—` + visually-hidden "None" (F3) | An em dash is a visual mark; assistive technology must hear an absence |
| The trailing ★, `aria-hidden` | Decorative — the qualifier carries the meaning |
| The visually-hidden `bestQualifier(row)` (F1, C9) | Colour and an icon cannot be the only signal (Document 14 §11) |

It takes `row` and `column` rather than pre-extracted strings, so the caller
cannot get the extraction subtly wrong — the one thing F2 is about.

### What it deliberately does **not** own

**The highlight surface.** Desktop tints the *cell*; mobile tints the *whole
row* (checklist D4). The lavender surface, brand text and rounding therefore
stay with each presentation's container, and `CompareValue` renders content
only.

That split is the crux: **content is shared because it is identical; chrome is
not shared because it is not.** A unit that also owned the surface would need a
`variant` prop that only ever means "which element gets the background", which
is a container's decision.

### The predicate the split creates — one source (review finding 1)

Because the surface belongs to the container, three components ask the same
question: `CompareValue` (does this cell get a star and a qualifier?),
`CompareTable` (does this `<td>` get tinted?) and `CompareCards` (does this row
get tinted?).

Three derivations of one rule is the duplication this milestone has removed
everywhere else — the cap (C2/O1), the qualifier text (F1), the row model (H4).
Its failure mode is partial application: a future change to what "best" means
leaves a cell tinted without a star, or starred without a tint, and **both
presentations still pass their own assertions.**

```ts
// utils/compare-rows.ts — beside bestQualifier
export function isBestCell(row: CompareRow, column: number): boolean;
```

**All three call sites use it. None re-derives `row.bestIndex === column`.**
Owned by the row model, because whether a cell wins is a fact about the row, not
about how either presentation draws it.

#### The allowed caller list — objective contract

Two probes, both exact lists, because they guarantee different things: the first
says *who may ask the question*, the second says *nobody may answer it
themselves*.

**P1 — callers of `isBestCell(`.** Matched call-shaped (identifier followed by
`(`), scanning `src/` and excluding the definition file. Exactly:

| File | Why it asks |
|---|---|
| `src/modules/marketplace/components/compare-value.tsx` | Star and hidden qualifier |
| `src/modules/marketplace/components/compare-table.tsx` | Cell tint (desktop) |
| `src/modules/marketplace/components/compare-cards.tsx` | Whole-row tint (mobile) |

Excluded by construction, not by listing:

- `src/modules/marketplace/utils/compare-rows.ts` — the definition. Excluded
  from the scan the way `maturity.ts` and `use-compare-selection.tsx` are in
  their probes. It must not call its own export either; nothing in the row
  builder needs it.
- `src/modules/marketplace/utils/index.ts` — a re-export is not a call, and a
  call-shaped match does not see `export { isBestCell }`. **The probe must match
  `isBestCell` followed by `(`**, not the bare identifier; a bare-identifier
  match would drag the barrel into the list and blunt it.
- `verification/**` — outside `src/`, not walked. The unit suite asserts
  `isBestCell` directly via `units-entry.ts`.

Any fourth entry fails the probe. `compare-screen.tsx` is **not** on the list:
it derives nothing and passes `rows` down.

**P2 — files that mention `bestIndex` at all.** Scanning
`src/modules/marketplace/`, exactly:

| File | Why |
|---|---|
| `src/modules/marketplace/types/compare.ts` | Declares the field |
| `src/modules/marketplace/utils/compare-rows.ts` | Assigns it |

**No component may contain the token.** P2 is the stronger of the two: P1 can be
satisfied while a component still writes `row.bestIndex === index` beside a call
it ignores, and P2 catches every form of re-derivation — comparison,
destructuring, or passing `bestIndex` down as a prop — because all of them
contain the token. P1 pins the askers; P2 removes the alternative.

### Why this satisfies F1 and C9

F1 centralised the qualifier *text*. T2.7.4 left the *rendering* of the
accessibility contract inline in `CompareTable`, so the mobile card would have
reproduced it — two implementations of C9, able to regress independently while
both suites stay green.

After this, C9 is a property of exactly one component. It is assertable once, in
one file, and both presentations inherit it by construction rather than by
review.

**Ownership:** business component, presentation-only (I3). It imports
`bestQualifier` and `NO_VALUE` from `utils/compare-rows.ts` and nothing else.

## 2. Responsive architecture — decision

### Correction to audit finding 5

The audit said dual DOM would leave duplicate interactive controls "in the
accessibility tree permanently". **That is wrong and is withdrawn.** Tailwind's
`hidden` is `display: none`, which removes a subtree from the accessibility
tree and from hit-testing. Only one presentation is ever exposed. The real costs
are different and smaller, and are set out below.

### Options

| | Approach | Assessment |
|---|---|---|
| **A** | **Dual DOM, CSS visibility** — `<div data-compare-view="desktop" class="hidden md:block">` / `<div data-compare-view="mobile" class="md:hidden">` | No hydration surface, no new hook, server and client render identically. Both trees exist in the DOM: ~2× nodes for ≤ 4 columns, and `BankBadge` renders twice (a `display:none` image may still be fetched). **Precedent:** M2.6 shortens labels this way |
| **B** | **Runtime conditional** via `matchMedia` | One tree in the DOM, cleaner in the harness — but the server cannot know the viewport, so the first client render either mismatches or flashes. `request-gate.md` records this project rejecting a render-gating fix for exactly that reason |
| **C** | Container queries | Same duplication as A with less support and no precedent here |

### Recommendation: **A**, with a scoping convention

Hydration correctness outweighs DOM economy at four columns, and B introduces a
class of bug (mismatch) that this codebase has already decided once not to
introduce.

**The genuine cost of A is verification, not accessibility.** jsdom applies no
media queries, so the harness sees *both* trees and a document-wide selector
would match either. That is exactly how `removeButton(name)` would silently bind
to the wrong tree.

**Mitigation, binding:** both containers carry `data-compare-view`, and **every
compare journey selector is scoped to one of them.** No document-wide compare
selector may exist after T2.7.5. This is a convention a probe can enforce.

### Trade-offs, stated

- **Accessibility:** equivalent. One presentation is exposed at a time under A;
  under B one exists at a time. Neither duplicates controls.
- **Hydration:** A has no surface; B has one. Decisive.
- **Verification:** B would be simpler; A is made safe by scoping. Cost is one
  convention, paid once.
- **Maintenance:** A keeps both presentations in the same file's control flow —
  visible to the next reader. B hides one behind a runtime condition that never
  fires in the harness's default (`matches: false`), so mobile would be *less*
  exercised, not more.

### This is a module decision, not a task detail (review finding 5)

Dual DOM plus the `data-compare-view` scoping convention governs **every**
responsive divergence in this module, not just the carousel — T2.7.7's action
bar diverges by breakpoint and will either inherit this or re-decide it.

It is therefore **promoted into the governing documentation** as part of this
task (§8, documentation): the approach, the reason B was rejected, and the
scoping convention are recorded in `marketplace-compare-state.md` so the next
task inherits a decision rather than re-litigating one. A task plan is where a
decision is *applied*, not where it lives.

## 2b. Carousel accessibility model — decision (review finding 3)

D1 = A is CSS scroll-snap, which means **every card is in the DOM and in the
accessibility tree at all times**; only one is visually in view. That fact
forces a choice the earlier draft left open, and the two readings build
different things.

**Decision: the carousel is a *scrollable list*, not a one-at-a-time widget.**

| | Binding rule |
|---|---|
| 1 | The scroller is a **labelled region**, so a screen-reader user knows what the cards belong to (M2.7 plan §2.3) |
| 2 | **All cards remain in the accessibility tree.** Off-screen cards are readable and their controls reachable |
| 3 | **No `aria-hidden`, no `inert`** on any card, at any scroll position |
| 4 | Arrows and dots are **scroll affordances**, not state controls: they move the viewport, they do not select a card |
| 5 | The position change is announced **politely**, and reports position ("Showing 2 of 3"), not a state change |

**Why this and not the widget model.** The widget reading requires hiding
off-screen cards *and* managing focus so it never lands in a hidden one — a
bespoke widget with its own a11y contract, which is exactly the debt risk R1
exists to avoid and which decision D1 chose composition to escape. The list
reading is what scroll-snap already is; nothing has to be built to make it true,
and nothing can drift out of true.

The visual convention "one card at a time" is preserved either way. Under this
decision it is a *presentation*, not a state.

## 3. Shared data contract — confirmation

**`CompareCards` takes exactly the contract `CompareTable` takes.** Formalised
rather than described:

```ts
// components/compare-view.ts (types only)
export interface CompareViewProps {
  products: ProductDetails[];
  rows: CompareRow[];
  onRemove: (productId: string) => void;
}
```

`CompareTableProps` and `CompareCardsProps` both **are** `CompareViewProps`.

How this preserves F2:

1. **One call site, one derivation.** `CompareScreen` calls `buildCompareRows`
   once and hands `products` and `rows` to both views as one prop group. No
   caller can assemble them from different places, because there is only one
   caller.
2. **`products` drives; `rows` is indexed.** Both views iterate `products.map`
   and index `rows[i].values[j]`, so the column count can never exceed the
   product count, and a missing value renders empty rather than shifting.
3. **`CompareValue` performs the indexing**, so neither view extracts a value by
   hand.
4. **The card slices by index, not by identity** — card `j` renders
   `products[j]` and every `rows[i].values[j]`. Because both come from the same
   prop group, a transposition would have to be introduced inside one component
   rather than between two.

A shared type also makes the contract assertable: a probe can require both view
components to declare `CompareViewProps`.

## 4. Shared header strategy — decision

**`CompareColumnHeader` gains `layout: 'stacked' | 'inline'`, defaulting to
`stacked`.**

- Desktop (`stacked`): badge and × on the top line, bank name beneath — as
  shipped in T2.7.4.
- Mobile (`inline`): badge, name, × on one line, as the approved card shows.

**Precedent:** `ProductHeader` takes exactly this pair for the same
desktop/mobile divergence (M2.6), `InterestRateDisplay` carries a `stacked`
layout, and there is a standing probe requiring component-library changes to be
**additive variants only**. This is the established answer to "same content,
two arrangements".

**Rejected: a second `CompareCardHeader`.** It would duplicate the badge/name
composition and, more seriously, the remove control's accessible name —
recreating audit finding 2 structurally rather than fixing it.

## 5. Row presentation taxonomy — decision

Benefits and Eligibility stack label-above-value on mobile (checklist D5); the
other five rows stay inline.

**Decision: a constant beside the row spec.**

```ts
// utils/compare-rows.ts
export const STACKED_COMPARE_ROWS: readonly CompareRowId[] = ['benefits', 'eligibility'];
```

- **Row vocabulary lives with the rows**, next to `ROWS` and `bestQualifier`.
  A row added later is defined and classified in one file.
- **Typed as `CompareRowId`**, which is why C3 narrowed it: a misspelling fails
  to compile, and the union makes "did we consider this row?" checkable.
- **`CompareCards` consumes it; it does not define it.** The card asks *is this
  row stacked?*, it does not know *which rows are*.

**Rejected: a `layout` field on `CompareRow`.** `CompareRow` is a model, and
`layout` is presentation. One presentation hint in a model invites the next one,
and it would change a type frozen at T2.7.1 for something no consumer of the
model needs.

**Rejected: a literal inside `CompareCards`.** Audit finding 4 — a second place
that knows the row taxonomy.

## 6. Accessibility helpers — decision

**New: `utils/compare-labels.ts`**, holding the accessible names derived from a
**product**:

```ts
export function removeLabel(bankName: string): string;  // "Remove HDFC Bank from comparison"
export function selectLabel(bankName: string): string;  // "Select HDFC Bank"
```

**Precedent:** `utils/filter-labels.ts` exists for exactly this — "one place that
turns values into human text" (M2.5). Compare gets its own for the same reason,
and consumers (`CompareColumnHeader`, `CompareTable`'s Select row,
`CompareCards`' card header and Select) read rather than compose.

**`bestQualifier` stays in `compare-rows.ts`.** The dividing line is the input,
not tidiness: `bestQualifier` is derived from a **row** and needs its label;
these two are derived from a **product**. Moving it now would churn a file
approved last task and re-point a passing probe for no behavioural gain.

## 7. Verification impact

### 7.1 Re-pointed — scope only, assertion text unchanged

| Helper / probe | Change |
|---|---|
| `compareColumns()`, `compareNames()`, `compareRowLabels()`, `compareRowCells()`, `bestCellIndex()`, `removeButton()` | Scoped to `[data-compare-view="desktop"]` |
| `loadCompare()`'s wait condition | Scoped likewise |
| `removal goes through the URL writer` | Unchanged — already follows the prop |

**No assertion text changes.** L4, L4b, L6, L6b, L6c and L7 must read exactly as
they do today and pass against the scoped helpers. A selector fix that also
relaxed a check would retire the behaviour L6b protects — the standing rule.

### 7.2 Added

**Journeys — `L9 · The mobile presentation`:** one card per product in selection
order · the card header carries badge, name and the remove control · the **whole
row** is highlighted, not the value · Benefits and Eligibility are stacked ·
Select is inside the card and inert · ‹ › and the dots are real `<button>`s,
keyboard-operable · the position change is announced politely · removing from
the card writes the URL exactly like the table does (one push).

**Journeys — `L9` accessibility model (finding 3):** the scroller is a labelled
region · **no card carries `aria-hidden` or `inert`** at any scroll position ·
every card's remove and Select controls are present in the accessibility tree,
including cards that are off-screen.

**Journeys — `L9b · The two presentations agree` (finding 2).** The contract's
whole purpose is that desktop and mobile cannot diverge, and nothing else
asserts it. Because approach A keeps both trees in the DOM and jsdom applies no
media queries, both are visible to the harness in a single run:

- for every attribute row, the highlighted column index is **identical** in
  `[data-compare-view="desktop"]` and `[data-compare-view="mobile"]`;
- for every attribute row, the rendered value strings are identical across the
  two trees, in column order;
- the column order itself is identical.

This is the assertion that would catch a second `bestIndex` derivation drifting
(finding 1) even if `isBestCell` were later bypassed in one presentation.

**Invariants:** `CompareCards` is presentation-only (I3) · both views declare
`CompareViewProps` · `bestQualifier` and `NO_VALUE` are referenced **only** by
`compare-value.tsx` (exact list) · **`isBestCell` has exactly three callers and
`bestIndex` appears in exactly two files — the lists are specified in §1, not
left to the probe author** · `STACKED_COMPARE_ROWS` has exactly one consumer · no
document-wide compare selector remains in the journey suite · no new file under
`components/ui/` (H1) · no new dependency (H2) · `CompareColumnHeader` exposes
`layout` as an additive variant.

**Units:** `STACKED_COMPARE_ROWS` contains exactly the two text rows, and every
id in it exists in the row model.

### 7.3 Unchanged

L0, L4, L4b, L6, L6b, L6c, L7, every M2.5/M2.6 journey, the whole boundary
suite, and the `buildCompareRows` one-call-site probe.

### 7.4 Outside the harness — stated before it goes green

jsdom has no layout engine, no scrolling and no media queries. **Scroll-snap,
swipe, arrow-driven scrolling, dot synchronisation and the breakpoint switch
itself are unverifiable here.** The suite can assert that the controls exist,
are real buttons, are labelled and are wired; it cannot assert that the carousel
moves. Those are manual, exactly as M2.6's breakpoint behaviour was.

### Assumptions in force

all counts, per the approved screen) · **A9** `—`, announced as "None".

**Scope note, flagged not assumed:** the `h1` shortening is screen-level, not
card-level. It is included here because it is part of the mobile presentation
this task owns, and because a heading inside the card would break the "exactly
one `h1`" assertion. "Add" (T2.7.6) and "Back" (T2.7.7) shorten in their own
tasks.

### Sequencing

1. `isBestCell` + `CompareValue` + `CompareViewProps`; `CompareTable` adopts all
   three — **suite must stay green with no assertion edits**, which proves the
   extraction was behaviour-preserving.
2. **`data-compare-view="desktop"` on the existing container; scope every
   compare journey helper and add the no-unscoped-selector probe.** Still one
   tree, so the suite stays green and any failure is unambiguous.
3. `compare-labels.ts`; `CompareColumnHeader` variant.
4. `STACKED_COMPARE_ROWS` + unit assertions.
5. `CompareCards`; `CompareScreen` renders both views inside their scoped
   containers.
6. L9 and L9b.
7. Invariant section; full suite; baseline.

**Step 1 first on purpose:** an extraction that changes no assertion is the only
kind that can be shown not to have changed behaviour.

**Step 2 before step 5 on purpose** (review finding 4). The earlier draft scoped
selectors *after* both trees existed, which meant a window where every compare
selector matched two trees and a failure could not be told apart from a selector
collision — with L6b, the assertion protecting Back/Forward, inside that window.
Scoping while one tree exists costs nothing and removes the window entirely.

### Acceptance criteria

- Both approved presentations render at their breakpoints; below `md` one card
  at a time with arrows and dots
- Cell content — value, `—`/"None", ★, hidden qualifier — is rendered by
  **exactly one** component
- **The winning state is derived by `isBestCell` and nowhere else**: exactly
  three callers (`compare-value`, `compare-table`, `compare-cards`), and
  `bestIndex` appears in exactly two files (`types/compare.ts`,
  `utils/compare-rows.ts`)
- Both views take the same `{ products, rows, onRemove }` contract
- Row taxonomy lives with the row model; the card consumes it
- Accessible names for remove and select come from one module
- **The carousel is a scrollable list: labelled region, every card in the
  accessibility tree, no `aria-hidden` or `inert`, polite position
  announcement**
- L4, L4b, L6, L6b, L6c, L7 pass **with their text unchanged**
- L9 green; **L9b proves the two presentations render the same winner and the
  same values**; no unscoped compare selector remains
- No new primitive, no new dependency, one `buildCompareRows` call site
- **The responsive architecture and carousel a11y model are recorded in
  `marketplace-compare-state.md`**, not only here
- Full suite green; baseline reported

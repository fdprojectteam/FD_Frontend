# M2.9 — Comparison Experience Refinement (Investment Preferences UX)

Project: FD Investment Platform
Requested: client change request, 2026-08-02
Status: **implemented** — static and unit gates green; runtime journeys and the
type/lint gates need a run on the developer machine (see *Gates*)
Scope: `/compare` only. No change to the approved visual design, the row model,
the selection contract, or the URL contract.

---

## The problem, stated as the client stated it

The comparison recalculated on every keystroke. Typing `500000` walked the whole
table through `5`, `50`, `500`, `5000`, `50000` — five full refreshes of figures
the user had not yet asked for.

Nothing about that was incorrect. It was *loud*. This screen is a workspace
where the numbers are the thing being read, and it moved while the user was
still deciding what to put into it.

## The decision

**Editing and applying are separated.** The field holds a draft; the comparison
is calculated from an applied value; the two meet only when the user says so.

```
input → draftDepositAmount → Update Comparison → appliedDepositAmount
                                                        ↓
                                                  ProductService
                                                        ↓
                                          CompareTable + CompareCards
```

### Why not a debounce

A debounce would have satisfied "the table stops flickering" and none of the
rest. The user would still not know whether the figures they were reading
answered the number in the field — the interface would be silently *between*
two answers for a few hundred milliseconds at a time. Separating draft from
applied makes the state nameable, so the screen can say which it is in.

## What changed

| File | Change |
|---|---|
| `hooks/use-comparison-preferences.ts` | Two values (`draftDepositAmount`, `appliedDepositAmount`); `applyPreferences`, `resetDraft`, `hasPendingChanges`, `canApply` |
| `components/preference-apply-bar.tsx` | **New.** Status + apply action for any preferences section |
| `components/investment-preferences.tsx` | New optional `action` slot beneath the fields |
| `components/compare-amount-field.tsx` | Reports `onSubmit` (Enter) and `onRevert` (Escape) |
| `components/compare-screen.tsx` | Wires draft/applied; one refresh transition wrapping both presentations |
| `hooks/use-compare-products.ts` | `placeholderData: keepPreviousData` |

### D1 — The applied value has exactly two writers

`applyPreferences`, and the one-shot products-derived default that runs before
the user has expressed any opinion. A third writer is a third way for the
comparison to change without being asked, which is the behaviour being removed.
Asserted statically by counting `setAppliedDepositAmount` call sites.

### D2 — The last-valid-parse latch is deleted

The hook used to keep the last figure that parsed so a half-deleted amount would
not blank the table. That was a workaround for recalculating mid-edit. With an
explicit apply, the applied value *is* by construction the last figure the user
confirmed, so an unparseable draft is a field error and nothing more.

### D3 — Pending is compared by value, not by text

`" 100000"` and `"0100000"` both read as the applied amount, so neither offers
an Update Comparison button — an action that would recalculate nothing is a
promise the refresh cannot keep. Applying normalises the draft to the figure now
being compared, so a valid edit cannot linger as a phantom pending change.

### D4 — The action is present when pending, disabled when unusable

The brief asks for the button to appear and disappear (steps 5 and 6); the
optional enhancements ask for it to be disabled when there is nothing to apply.
Both are honoured on their own terms: it is *present* whenever the draft differs
from the comparison, and *disabled* when the draft cannot be applied at all —
an unparseable amount is explained by the field's own error rather than by a
control quietly vanishing. The row reserves the button's height, so nothing
below the preferences moves when it arrives.

### D5 — Enter re-checks; the guard cannot live in the button

Enter reaches `applyPreferences` straight from the field, bypassing the disabled
control entirely. So the hook re-validates rather than trusting its caller.

### D6 — `keepPreviousData` on the comparison batch

The deposit amount is part of the query key, so a newly applied amount is a cold
key. Without this the table would have collapsed into skeletons on every apply —
the flicker moved, not fixed. The previous figures now hold, dimmed via
`isFetching`, until the new ones land.

Its cost, named rather than discovered later: an **errored** refetch now keeps
its previous data, so `products` alone no longer implies success. `CompareScreen`'s
content guard has carried `!isError` since T2.7.8a for exactly this anticipated
change, and a probe now pins it there.

### D7 — One refresh treatment, wrapping both presentations

Opacity only, `--ds-duration-base` (200ms — inside the brief's 150–250ms window)
on the platform easing token, and **no keyed remount**: the key would change with
the amount rather than with the data, fading the *old* figures in at the moment
of the click. One wrapper around both views is what makes "desktop and mobile
refresh together" structural rather than two timings to keep in step.

### D8 — One live region, two states, no timers

The status line reads either "Changes not applied" or "Comparing at ₹X". Applying
therefore announces itself: the region's content changes from the pending message
to the settled one, so a screen reader hears the confirmation without a transient
toast that has to be scheduled, cleared, and kept from stacking.

The pending text is full-strength content with a decorative amber dot, not amber
text: `--ds-color-warning` (amber-500) does not meet AA on the page surface, and
an unapplied edit is not a validation failure.

### D9 — Applying from the button returns focus to the field

The action is present only while there is something to apply, so the control the
user just activated unmounts — and focus falls to `<body>`, leaving a keyboard
user's next Tab to restart at the top of the page. `CompareScreen` hands focus
back to the field, which is where the edit began and where the next one starts.
Enter keeps its direct binding: it never lost focus, so it does not need the
redundant call.

### D10 — The new component is a *preferences* component

`PreferenceApplyBar` takes labels and a callback and knows nothing about
deposits, amounts, or comparisons — the same rule that made `PreferenceField` a
shell rather than one component per field. The second preferences section on the
platform uses it unchanged instead of copying it.

Likewise the field reports `onSubmit`/`onRevert` — the *gesture* — rather than
`onApply`. A field that knew it applied a comparison could not be reused by one.

---

## Unchanged on purpose

- The deposit amount is still **not** in the URL (D3 of the original change
  request): `/compare`'s approved parameter set stays closed at `?ids=`.
- Applying performs **no navigation**.
- Below-minimum columns still compute and flag; the flag now follows the applied
  amount rather than the keystroke.
- No change to `buildCompareRows`, `ProductService`, the selection contract, or
  either presentation component.

## Verification

**Invariants — 315 assertions, green.** A new section, *Draft vs applied*,
asserts the separation rather than the calmness — calmness is the consequence,
and a later refactor could keep the consequence while losing the rule:

- the hook holds two values, not one;
- the applied value has exactly two writers;
- a keystroke moves the draft and nothing else;
- applying re-checks rather than trusting its caller;
- the screen calculates from the applied preferences, and the draft reaches the
  field and nothing else;
- the apply bar owns no state and names no deposit;
- pending and settled share one polite status region;
- the field reports Enter/Escape without deciding what they do;
- applying from the button returns focus to the field it came from;
- the batch keeps previous figures, and the content guard still refuses to
  render a comparison beside an error;
- one refresh treatment wraps both views.

**Units — 164, green. Boundaries — 15, green.**

**Journeys — rewritten, not yet executed here.** L10 was inverted: typing must
now change nothing, and the recalculation is asserted against the explicit
apply. Added: Escape restores, Enter applies, apply normalises the draft, a
below-minimum draft flags nothing until applied, and an invalid draft leaves
both the button and Enter inert.

sign-off.**

## Manual checks only a browser can settle

1. Type into Deposit Amount and confirm **nothing** in either presentation moves
   — no figures, no winner pill, no below-minimum badge.
2. Click Update Comparison and confirm desktop and mobile change in the same
   frame, with a single soft 200ms settle and no skeleton flash.
3. Confirm the results below the preferences do not shift vertically when the
   button appears or leaves.
4. Enter applies from within the field; Escape restores the applied figure.
5. With reduced motion enabled, the refresh is immediate and still calm.
6. Screen reader: applying announces the new amount once, not on every keystroke.
7. Keyboard: after clicking Update Comparison, the next Tab continues from the
   Deposit Amount field rather than from the top of the page.

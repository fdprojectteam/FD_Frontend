## 1. Purpose and scope

The approved bottom action row: **"Back to Marketplace"** (secondary) and
**"Proceed to Booking"** (primary, with a trailing arrow). Right-aligned as a
pair on desktop; two buttons across the width on mobile, where the back label
shortens to **"Back"**. Sticky below `md`, static from `md`.

**In scope:** the bar, its placement in `CompareScreen`, its responsive
behaviour, and the journeys and probes that pin them.

**Out of scope:** booking itself (Phase 3, D3) · the per-column "Select", which
already ships inside `CompareTable` and `CompareCards` (T2.7.4/T2.7.5) · the
rapid-remove race (§9) · R15a's entry affordance on Home.

## 2. Architecture decisions

### D-A1 — The bar is screen-level, outside both view containers

Like the `h1` and the picker trigger, it renders **once** at every breakpoint,
outside `data-compare-view="desktop"` and `…="mobile"`.

That is not a style preference: the dual-DOM responsive model (recorded in
`marketplace-compare-state.md`) puts *both* presentations in the DOM, so
anything placed inside a view container exists twice. A duplicated action bar
would mean two "Proceed to Booking" controls in the tree and an ambiguous
selector for every journey that touches it — the hazard the scoping convention
exists to remove.

### D-A2 — It owns nothing (and today, takes nothing)

**It owns no state and derives nothing.** No `useState`, no memo, no store, no
router, no query — Back is a `<Link>` and Proceed is inert. It takes no props
*today* because there is nothing to give it.

**The rule is ownership, not the signature.** A prop is not forbidden: if
Booking later needs an `onProceed` or a `disabled`, receiving one and reporting
upward is exactly what a presentation component does (I3). What must not happen
is the bar acquiring the *authority* — deciding whether booking is available,
reading the selection, or holding state about it.

Stating it this way matters because it is the thing most likely to erode: the
first request to "carry the comparison into booking" will arrive looking like a
prop, and the question to ask is not "may it take a prop?" but "who decided the
value?".

Under C4 the selection lives in the URL of the route the user is already on, so
booking will read it from there or from the store — **not** from state smuggled
through this component now (D3: "booking navigation remains stateless").

### D-A3 — It renders only when there is a comparison to act on

Not in the empty state, not in the error state.

The empty state already offers "Browse Fixed Deposits" → `ROUTES.home`. Adding
the bar there would put **three** controls to the same destination on one
screen — the top back link, the empty state's action, and the bar — of which two
are within a few pixels of each other. Rendering it beside the comparison keeps
the count at two and matches every approved screen, all of which show products.

### D-A4 — Back is a `<Link href={ROUTES.home}>`, never `router.back()`

Established for the same route in M2.6 and restated in the M2.7 plan §3.6: a
user arriving from a shared `?ids=` link has no history to go back to, and
`router.back()` would take them off the site.

### D-A5 — Proceed to Booking is inert, and carries nothing

`aria-disabled="true"`, **no `href`**, no state — the established treatment for
an unbuilt destination ("How it works" on Home, "Continue to Booking" on
Details). Visually identical to a live primary button, so the approved layout is
intact.

**When Booking is implemented, `CompareScreen` — not `CompareActionBar` — will
own enablement and navigation**, passing the result down as props, so the
ownership model established here survives the feature that replaces the inert
button.

### D-A6 — The label shortens inside one element

```
Back<span className="hidden md:inline"> to Marketplace</span>
```

The suffix form, matching the `h1` and the picker trigger on this same screen,
rather than `DetailActionBar`'s two-span swap. Both are `display: none`, so only
one string is ever in the accessibility tree; the suffix form simply has fewer
nodes and is what the rest of this screen already does.

### D-A7 — Sticky below `md`, static from `md`

Mechanics copied from `DetailActionBar` — **the technique, not the component**
(the M2.7 plan's reuse audit is explicit that the two bars have different
buttons and are not one component):

```
outer:   sticky bottom-0 border-t   md:static md:border-t-0
inner:   container-page flex items-center justify-end gap-3 py-4 md:pt-8
buttons: flex-1 md:flex-none
```

`sticky` rather than `fixed` matters: a sticky element keeps its place in the
flow, so it cannot occlude the last card. Checklist **E5** ("bottom padding
reserved on mobile") is satisfied by the layout rather than by a magic number.

### D-A8 — Journeys scope the bar by `data-compare-actions`

The bar is outside both view containers, so neither `data-compare-view` scope
reaches it, and a document-wide selector would also match the *top* back link —
both are links to `ROUTES.home`.

A `data-compare-actions` attribute follows the convention already documented for
`data-compare-view`, `data-row-layout` and `data-best`. Rejected alternative: a
`<nav aria-label="Comparison actions">` landmark, which would give a scope *and*
an accessible name — but it invents a landmark the approved design does not
have, and landmark inflation has its own accessibility cost.

## 3. State authority — every interaction

| Interaction | Authority | Writes |
|---|---|---|
| **Back to Marketplace** | None — it is a route change, not state | Native `<Link>` navigation. **No `?ids=` write**: leaving the route does not edit the selection |
| **Proceed to Booking** | None — inert (D3) | Nothing |

**The bar performs no URL write and no store mutation.** On `/compare` the URL
is the selection (C4); the bar touches neither. That is the whole of its state
story, and any future change to this table is an architectural change.

---

## 4. Component responsibilities and boundaries

| Component | Responsibility |
|---|---|
| `CompareActionBar` | Render two controls and their responsive labels. Nothing else |
| `CompareScreen` | Decide **whether** it renders (D-A3) and **where** (D-A1) |

It is presentation-only under I3 in the strong sense: whatever it is given, it
**decides nothing**. Today it is given nothing, so the boundary is trivially
held; when Booking arrives and the screen passes enablement down, the boundary
is what keeps holding it (D-A2, D-A5).

---

## 5. Data flow

```
CompareScreen
  └─ (content branch only)  <CompareActionBar />
                                   │
                     ┌─────────────┴─────────────┐
             <Link href={ROUTES.home}>     inert button
             native navigation             no href, no state
```

No callbacks, no props, no query, no cache. The only flow is the user's own
navigation.

## 6. Accessibility decisions

| # | Decision |
|---|---|
| A-1 | Back is a real link, so it works with middle-click, "open in new tab", and screen-reader link lists |
| A-2 | Proceed uses `aria-disabled`, not `disabled`, so it stays focusable and discoverable — a control that exists but is not yet available, consistent with Home and Details |
| A-3 | Only one label string is in the accessibility tree at a time (`display: none`), so neither control is announced twice |
| A-4 | The arrow icon is `aria-hidden`; the label carries the meaning |
| A-5 | **Observation, not a change:** on mobile the bar says "Back" while the top link says "Back to Marketplace" — two controls, one destination, two names. WCAG 3.2.4 (consistent identification) prefers one name for one function. **This is what the approved design draws**, so it is recorded rather than overridden, and worth a sentence to design at sign-off |

**Not verifiable in jsdom:** stickiness, whether the bar occludes content, and
the reserved space at the bottom of the mobile carousel. Manual, alongside the
existing carousel checks.

---

## 7. Responsive strategy

One instance, two behaviours — **not** two instances. The bar is rendered once
outside the view containers and changes with CSS: sticky→static at `md`,
full-width pair→right-aligned pair, and the label suffix appearing at `md`.

This is deliberately *unlike* the table/cards split, where two presentations are
genuinely different components. Here the content is identical at both widths;
only its placement changes, which is a styling concern and must not become a
second component.

## 8. Verification impact

### Journeys — new `E` assertions, scoped to `[data-compare-actions]`

**Exactly one `[data-compare-actions]` exists in the document** — the assertion
that catches accidental duplication across the two responsive layouts, which is
the specific failure D-A1 exists to prevent and the one a reader would otherwise
have to infer from placement · it is outside both `data-compare-view`
containers · Back is an `<a>` with `href="/"` · Proceed has **no `href`**,
`aria-disabled="true"`, and produces **no navigation** when clicked · both label
strings are present for the CSS swap · the bar is **absent** in the empty state
and in the error state (D-A3) · clicking Back performs no `?ids=` write.

That last one matters: it is the assertion that would catch a future "clear the
selection on leave" behaviour appearing without approval.

### Invariants

`compare-action-bar.tsx` is presentation-only — no hook, no router, no store, no
service · **it owns no state and derives nothing** (D-A2): no `useState`, no
`useMemo`/`useReducer`, no conditional logic over a selection, and no import of
the compare store, the URL writer or a query · it contains no `href` for
booking ·
it uses `ROUTES.home` rather than a literal · `CompareScreen` renders it in the
content branch only · no new file under `components/ui/` (H1) · no new
dependency (H2).

### Units

**None.** The bar has no pure logic; a unit test here would assert JSX.

### Boundaries

**Unchanged.** No new import crosses a boundary.

### Unchanged elsewhere

L0, L3, L3b, L4, L4b, L6, L6b, L6c, L7, L9, L9b and every M2.5/M2.6 journey.
**No assertion text changes** — the bar adds markup below the content and alters
nothing that exists.

## 12. Sequencing

1. `CompareActionBar` — props-free, so it is mountable and inspectable before
   anything is wired.
2. `CompareScreen` renders it in the content branch, outside the view
   containers.
3. Journeys, scoped to `data-compare-actions`, including the two negative
   assertions (absent when empty; Back writes no `?ids=`).
4. Invariants.
5. Full suite; record the measured baseline.
6. Documentation.

Step 1 before step 2 for the same reason as T2.7.5 and T2.7.6: a component
proven to need nothing it was not given cannot quietly acquire a dependency
during wiring.

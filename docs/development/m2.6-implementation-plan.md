## 1. Decisions — all settled

| # | Decision | Outcome |
|---|---|---|
| **D1** | `ProductDetails` cache contract | **A′** — preview derived from the existing list caches; the priming write is deleted; `useProduct` exposes `{ preview, details }` |
| **D2** | Is the calculator's tenure editable? | **A** — fixed, rendered as a read-only field |
| **D3** | Does the calculator write `?amount=`? | **A** — local state only; revisit if user testing or Booking demonstrates a need |
| **D5** | React Hook Form? | **No** — Zod schema + local state. RHF arrives with the first real form (Booking) |
| **D6** | "Add to Compare" | **Module context**, ids only; provider mounted in `(public)/layout.tsx`; context is the source of truth, `/compare?ids=` will be a projection of it |
| **D7** | Action bar | **Sticky on mobile, static on desktop** — matching both approved screens |

**Consequence worth stating: M2.6 adds no runtime dependency.** D5 removes
`react-hook-form` and `@hookform/resolvers`; D6 removes `zustand`. `zod` is
already installed. This matches Document 13's bundle discipline.

### Why D1 = A′ (recorded, since it changes existing code)

`useProducts` currently primes the detail cache with a `ProductSummary` under a
`ProductDetails` key. On this screen that produces one paint where a value
**typed** `ProductDetails` has `undefined` for `eligibility`, `faqs`, `terms`,
`interestBreakdown`, and `trustIndicators`.

A′ deletes that write and derives the preview by **reading** the caches that
already hold the summary:

```ts
// hooks/use-product-preview.ts — reads, never writes
export function useProductPreview(id: string): ProductSummary | undefined {
  const queryClient = useQueryClient();
  return queryClient
    .getQueriesData<Paginated<ProductSummary>>({ queryKey: marketplaceKeys.products.lists() })
    .flatMap(([, page]) => page?.items ?? [])
    .find((product) => product.id === id);
}
```

No cache entry is ever written with a value that does not match its key's type;
no new query key is introduced (I5); and because `ProductDetails extends
ProductSummary`, components read `details ?? preview` and get a correctly typed
`ProductSummary` either way. A cold load has no list cache, so `preview` is
`undefined` and the screen shows a skeleton — the honest answer.

`phase-2-roadmap.md` §6 documents the priming *mechanism* and must be amended
(T2.6.0). The *outcome* it describes — instant render, background revalidation —
is preserved.

### Why D2 = A (recorded, because it constrains the UI)

`ProductSummary` carries one `interestRate` and one `tenureMonths`. An editable
tenure would apply the product's rate at a tenure it does not cover and display
a maturity value **the user cannot obtain**. Doing it honestly needs rate slabs,
which M2.1 excluded deliberately. The approved screen shows a *field*, so the
field stays — `readOnly` with `aria-readonly`, not replaced by text.

## 2. Architecture

### 2.1 Route and rendering

```
app/(public)/marketplace/[productId]/page.tsx      server component
  ├─ static metadata (see E5 — it cannot fetch)
  └─ <ProductDetailScreen productId={id} />        client, sole hook owner
app/(public)/marketplace/[productId]/not-found.tsx server component
```

`ProductDetailScreen` is to this route what `HomeScreen` is to `/`: the sole
hook owner and the only component that touches a query (I3, A1).

**No Suspense boundary is required.** Under D3=A no component here reads
`useSearchParams`, so there is no CSR bailout — unlike Home, where the boundary
is mandatory (M2.4 defect C2).

### 2.2 Navigation

I8 applies unchanged. Opening a product is intent → `<Link>` pushes → Back
returns to the listing **with its filters and page intact**, because M2.5 made
those real history entries. "Back to Marketplace" is a `<Link href={ROUTES.marketplace}>`,
**not** `router.back()`, which would strand a user who arrived from a shared
link. This route performs **zero** URL writes; a probe asserts it (§5).

### 2.3 Component contract

Corrected per Document 07 §15 — components receive prepared data and do not
compute. The split mirrors `SearchBar`, the module's existing form precedent.

| Component | Owns | Receives |
|---|---|---|
| `ProductDetailScreen` | every hook, the calculation, every callback | `productId` |
| `ProductHeader` | nothing | bank, name, rate |
| `TrustBadgeRow` | nothing | the **product's own** indicators (G5) |
| `KeyInfoGrid` | nothing | tenure, interest type, minimum, payout |
| `InvestmentCalculator` | draft amount (transient, I6) | rate, tenure, `result`, `error`, `onCalculate(amount)` |
| `BenefitChipList` | nothing | **exists (M2.2)** — reuse, do not rebuild |
| `EligibilityPanel` | nothing | eligibility |
| `ProductAccordions` | open/closed (transient, I6) | breakdown, faqs, terms |
| `DetailActionBar` | nothing | `isComparing`, `onCompare`, booking href |

All are built from frozen primitives (`Card`, `Chip`, `Accordion`, `Button`,
`Input`, `Badge`). **No new primitive.** If something appears to need one, that
is a design question, not an implementation shortcut.

**Placement rule (recorded so M2.7 does not re-open it).** Document 07 §7 lists
both "Deposit Calculator" and "FD Product Card" as Business Components. The
project already places `FDProductCard` inside the module, establishing the rule:
**domain-specific business components live in `modules/marketplace/components/`;
cross-module ones (`AmountDisplay`, `BankBadge`, `InterestRateDisplay`,
`TrustIndicator`) live in `components/business/`.** The ESLint boundaries
confirm it — `components → module` is forbidden, so a calculator in
`components/business/` could not import `calculateMaturity` without first
promoting the util and its types to `@/utils` and `@/types`.

### 2.4 Calculation

`calculateMaturity()` from M2.1 is the only formula; it already reproduces all
six published figures, including this screen's ₹1,00,000 → ₹1,07,978. The
**screen** calls it; the component never does.

**The default result requires no calculation at all.**
`ProductSummary.estimatedReturns` is already computed by `ProductService` at
`REFERENCE_AMOUNT` (₹1,00,000) and already equals the approved figures. The
screen renders that on load and computes only when the user submits a different
amount.

Input validation is a pure Zod schema in `utils/`, following the `url-values.ts`
precedent — no new folder, and directly unit-testable without React.

### 2.5 Compare selection (D6)

```
hooks/use-compare-selection.tsx     context + provider + hook, ids only
  add(id) · remove(id) · has(id) · count · MAX_COMPARE

app/(public)/layout.tsx             mounts CompareSelectionProvider
```

Feature state per Document 09 §3 — **not** the global store, which §5 reserves
for application-wide data. The cap lives in the store, not in the UI; enforcing
it in two places is how the two disagree. The store holds **ids only**;
`useCompareProducts(ids)` already resolves them through the existing key.

**Source of truth:** the context. `/compare?ids=` (M2.7) will be a shareable
projection hydrated into it on load — one writer, many readers, as on Home.

**This adds a provider seat** to `(public)/layout.tsx`. `app/providers.tsx`
documents its seats explicitly and none is feature-scoped; the seat list is
amended in T2.6.0 so the next reader is not surprised.

### 2.6 Action bar (D7)

Sticky to the viewport below `md`, static at the end of the content from `md`.
Mobile reserves bottom padding on the scroll container so the last accordion is
never obscured. The bar is a `<div role="group">` with an accessible name, not a
landmark — it must not compete with the page's existing `<nav>`, `<main>`, and
`<footer>`.

**Width and position (from the approved screens).** The bar spans the **full
page container** (`container-page`, 1200 px) — *not* the narrower content
column — with a divider directly above it. Desktop right-aligns the two
buttons; mobile lays them side by side across the full width. This is the only
element on the screen that is wider than the content column.

### 2.7 UI fidelity specification — binding

Everything below is **directly visible in the approved screens**. Where the
screens are silent, the item appears in the assumptions list instead, never as
an invented behaviour.

#### 2.7.1 Page measure

| | Value | Source |
|---|---|---|
| Page container | `container-page` — 1200 px max, 24 px gutter (16 px mobile) | existing token |
| **Product-detail content column** | **~920 px, centred** | `design-tokens.md` §12, sampled from the approved screen |
| Action bar | full `container-page` width | approved screen |

`design-tokens.md` §12 already records the 920 px column and states it is
"implemented as a narrower prose container in Phase 2" — so this is a token the
design system anticipated, not a new invention. T2.6.3 adds
`--ds-container-detail-max: 920px` and a `container-detail` utility mirroring
`container-page`. Every section from "Back to Marketplace" through the
accordions sits in that column; only the action bar escapes it.

#### 2.7.2 Responsive behaviour

| Section | Desktop (≥ `md`) | Mobile (< `md`) |
|---|---|---|
| Product header | Two columns — identity left, rate right; **"per annum" on its own line beneath the figure** | Stacked — identity row, then rate below; **"p.a." inline** beside the figure |
| Trust badges | **Three**: RBI Regulated · **₹5L** DICGC Insured · **AAA Rating** | **Two**: RBI Regulated · DICGC Insured (**no "₹5L", no AAA Rating**) |
| Key information | 4 cards across | 2 × 2 |
| Calculator inputs | Amount, Tenure and **Calculate on one row**; button height matches the inputs | Amount and Tenure on one row; **Calculate on its own row**, auto width, left-aligned |
| Calculator results | Principal → Interest Earned → Maturity Value on **one row** | Principal → Interest Earned on one row; **Maturity Value box on its own row** |
| Benefits | 4 chips, single row | Wraps to 2 rows |
| Eligibility | Muted panel, one line of text | Same panel, text wraps |
| Accordions | Identical at both breakpoints | Identical |
| Action bar | Buttons right-aligned; label **"Add to Compare"** | Buttons side by side, full width; label **"Compare"** |

The trust-badge row is the one place the screens differ in **content**, not
layout. It is rendered from the product's own indicators (G5); the third badge
and the "₹5L" qualifier are withheld below `md`. Withheld means **removed from
the accessibility tree**, not visually clipped — a screen-reader user must not
receive a badge the design deliberately hides.

#### 2.7.3 Section heading treatment

"Key information", "Benefits", and "Eligibility" render as **compact bold
labels**, visibly smaller than the section titles on Home ("Recommended for
you", "Fixed Deposits", "Featured banks"). `SectionHeading` is therefore **not**
reused on this screen; these are plain headings at the smaller scale. This is a
sizing observation from the screens, not a new pattern.

#### 2.7.4 Constructions that look like primitives and are not

- **Maturity Value box** — `surface-brand-subtle` + `content-brand` on a
  rounded `div`, the same token pair the hero already uses. Not a new
  "highlight" primitive.
- **Arrows between results** — decorative icons, `aria-hidden`. Not a stepper.
- **Eligibility panel** — a muted surface with no border or shadow. Not a
  `Card`.

#### 2.7.5 Assumptions — the design is silent, so these are recorded, not invented

| # | Assumption | Why it is an assumption |
|---|---|---|
| A1 | The `h1` is the bank name in the header card | No heading levels are visible; it is the most prominent text and K7 requires exactly one `h1` |
| A2 | The Tenure field keeps its input box and becomes `readOnly` / `aria-readonly` | D2 = A fixes the value; the screens draw it identically to the editable Amount field, so replacing it with text would deviate |
| A3 | Accordions default to collapsed, with no "expand all" | All three are drawn collapsed; no other state is shown |
| A4 | Result arrows are decorative | They carry no label; if they are meant to convey progression they need text alternatives |
| A5 | The footer **still renders**, inherited from `PublicLayout` | Neither screen shows a footer, but both are cropped at the action bar. Absence in a crop is not evidence of removal, and suppressing the shell footer would be a new UX decision |
| A6 | The desktop action bar is **static** at the end of content, per D7 | The desktop screen is genuinely ambiguous — there is dead space above the bar and no footer, which would also fit a pinned bar. D7 is an approved decision and is not reversed here |
| A7 | The 404 screen's copy (written in T2.6.2) is provisional | No 404 screen exists in the approved set |

A5 and A6 are the two worth confirming with design, because they are the only
assumptions that would change the shell T2.6.3 builds.

## 3. Contract gaps and edge cases

| # | Issue | Where it lands |
|---|---|---|
| **G3** | Partial detail payload | D1 = A′ |
| **G4 / E1** | **404 vs 500 must be distinguished.** `ApiError` carries `status` and `code` (`PRODUCT_NOT_FOUND`). 404 → `notFound()`; 500 → the retryable error card. Conflating them turns an outage into "this product does not exist". React Query's `retry` already skips 4xx via `isClientError`, so the not-found path must not retry | T2.6.3 |
| **G5** | `ProductDetailsDto.trustIndicators` is per-product; the Home trust strip uses a static platform list. Using the wrong one puts an AAA badge on an AA+ bank | T2.6.4 |
| **E2** | Amount below `minInvestment` — `Input` has an `invalid` variant, so no new primitive, but the error **copy** is new UI and needs confirmation | T2.6.5 |
| **E3** | Do not recompute on mount — `estimatedReturns` already carries the approved defaults | T2.6.5 |
| **E4** | `typedRoutes: true` vs `ROUTES.product(id)` — the builder's return type widens to `string`. The cast belongs in `constants/routes.ts`, once, not at every `<Link>` | T2.6.2 |
| **E5** | **`generateMetadata` cannot fetch.** MSW runs in the browser only and `src/app/api/` has no route handlers, so a server-side fetch reaches nothing. Metadata is static until a real API exists | T2.6.2 |
| **E6** | SEO — this route is client-rendered, so the product `h1` and rate are absent from prerendered HTML. Inherited from M2.4 R2 and more consequential here. Not solvable while data is browser-mocked; recorded, not discovered later | §6 R5 |
| **E7** | A valid id with an incomplete detail payload cannot occur today (the handler builds details from the summary) but will with a real API. Render the sections present rather than failing wholesale | T2.6.3 |

## 5. Verification plan

Extends the committed harness. M2.5's 221 assertions must stay green.

**Unit.** The Zod calculator schema (min, max, non-numeric, below
`minInvestment`); `calculateMaturity` re-asserted against all six published
figures; the A′ preview selector against a seeded list cache.

**Invariants.**

- `ProductDetailScreen` is the sole hook owner on its route
- no section component imports a service, repository, or the router
- **zero `router.push` / `router.replace` call sites in the detail route** — the
  cheapest guard against D3 being quietly reversed
- `ProductDetails` remains assignable to `ProductSummary` — so a future split of
  the two types fails loudly rather than silently breaking `details ?? preview`
- `calculateMaturity` has exactly one definition, and the calculator component
  does not import it
- the compare context has exactly one writer, and `MAX_COMPARE` is enforced there

**Journeys.**

| # | Asserts |
|---|---|
| K1 | Listing → detail → Back returns to the listing **with filters and page intact** — the end-to-end payoff of I8 |
| K2 | Cold load of a shared detail URL renders fully with no list cache to preview from |
| K3 | Calculator: default shows the approved ₹1,07,978 **without computing**; a new amount recalculates; invalid input shows an error and does not compute |
| K4 | Unknown id renders `not-found` |
| K5 | Accordions are keyboard operable; open state never reaches the URL (I6) |
| K6 | Compare: add from the detail screen, see it reflected on the card in the listing, cap enforced at 4 |
| K7 | A11y: one `h1`, no skipped heading level, labels bound, errors via `aria-describedby`, action bar reachable by keyboard |
| **K8** | **404 renders `not-found` and issues no retry; 500 renders the retryable card** (E1) |

**Gates.** `tsc`, `eslint --max-warnings 0`, `prettier --check`, `next build`,
`npm run verify`.

## 7. Definition of done

- Route renders the approved screen at both breakpoints, satisfying every row
  of the §2.7 fidelity specification
- Calculator reproduces the approved figures, validates accessibly, and computes nothing on mount
- Unknown id renders `not-found`; a server error renders the retryable card
- Back returns to the listing with filters, sort, and page intact
- Trust badges are the product's own (G5)
- No component computes a financial value
- No new runtime dependency
- Invariants I1–I8 re-verified, including the new route
- M2.5's 221 assertions still green
- All gates green

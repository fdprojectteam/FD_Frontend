## 1. What T2.7.8 is — and what it is not

The roadmap defines it as **"verification + milestone audit — suites, gates,
reports"**.

**It is not M2.9.** M2.9 is the *Final Marketplace Audit* across every screen —
screen-by-screen UI conformance, a11y counts, token compliance, bundle sanity,
Phase 3 handover. T2.7.8 is the **module audit for M2.7 alone**: does the
Comparison module meet its own definition of done, and what does it hand
forward? Duplicating M2.9's scope here would mean auditing Home and Details
twice and would leave M2.9 with nothing to find.

**It builds no UI.** The roadmap's own ordering rationale is "audit last,
mirroring the two audits you've already approved". A task that implements a
feature is not an audit of the milestone that preceded it.

That last point is what makes §3's first decision unavoidable.

### Criterion 5 — the module is unreachable

**Nothing in `src/` references `ROUTES.compare`.** Verified: the only occurrence
outside `constants/routes.ts` is none. A user cannot reach `/compare` except by
typing the URL, and under C4 a bare `/compare` shows the empty state, so even
that only works with hand-written `?ids=`.

So "selection survives Home ↔ Details ↔ Compare" cannot be exercised, and
**M2.7 as it stands ships a screen no user can open.** This is R15a, decided in
T2.7.3 (a floating Compare bar on Home) and never built, because every task
since has been correctly scoped to its own component.

### Criterion 10 — the sentence no longer means anything

M2.6's 401 assertions are not a set that still exists: probes were **re-pointed**
as components moved (the T2.7.4 helpers, the T2.7.5 prop-shape and qualifier
checks, the T2.7.7 gating probe), and journeys were rewritten twice. The honest
criterion is *"no assertion was weakened, and every re-point is recorded"* —
which is true and is documented per task in `verification/README.md`.

### Criterion 11 — two gates have never run

`npm run lint` and `npm run build` **have not run once during M2.7**, in any
task, because neither is executable in the agent environment (ESLint cannot
complete against the mounted drive; only `@next/swc-win32-x64-msvc` is
installed). P3 has carried since M2.6.

That is not a small residual: **type errors, lint errors and build failures are
invisible to everything M2.7 has verified.** The suite bundles with esbuild,
which does not type-check.

## 3. Scope decisions required before the contract can be written

Each of these is a judgement about what "closing M2.7" means. I am not making
them.

### S1 — Does T2.7.8 include building the entry affordance (R15a)? *(blocking)*

| | Option | Consequence |
|---|---|---|
| **A** | **T2.7.3b first** — build the floating Compare bar as its own task, then audit | Preserves "audit builds nothing"; M2.7 closes reachable and criterion 5 becomes verifiable |
| **B** | **Fold it into T2.7.8** | One task, but an audit that implements a feature cannot audit it |
| **C** | **Close M2.7 unreachable**, carry R15a to M2.8 or Phase 3 | Fastest; the milestone ships a screen no user can open, and criterion 5 is deferred with it |

**My reading, not a decision:** the roadmap's ordering rationale argues against
B, and criterion 5 argues against C. But C is defensible if the entry point is
genuinely a Home concern rather than a Comparison one — in which case criterion
5 should be *amended* rather than left failing.

### S2 — The rapid-remove race *(blocking)*

Carried from T2.7.6, recorded for this task. Two removes inside one navigation
window compute from the same stale `ids`, exactly as two Adds did.

Options: generalise the D-PENDING guard to removal · accept it, on the grounds
that nothing invites repeated clicking of a remove control the way an open
dialog does · defer to Phase 3.

**Note the asymmetry that makes this awkward:** the same harness limitation
applies. A guard's *release* would be verifiable; its *engagement* would not.
So choosing to fix it buys behaviour that cannot be proven here, and choosing
not to leaves a known race in shipped code. Both are defensible; neither is mine
to pick.

### S3 — Assumptions A1–A7 and A10 *(blocking)*

Eight assumptions are in force and **none has been confirmed by design**: dialog
contents, empty-state copy, no link to product details, no carousel loop, no
redirect on last removal, suppressed highlighting at N=1, "Products" at N=1, and
no mobile dialog variant.

Does M2.7 close with them *accepted* (converted to decisions), *carried* (still
open, listed for M2.9), or *blocked* pending design review? **A3 is the one I
would not close silently** — a user comparing three products cannot open any of
them, and that is a product decision rather than an implementation detail.

### S4 — The M2.6 cleanups *(minor, but needs an owner)*

C1 dead `useMarketplaceSearchParams` · C2 dead `calculateInterestEarned` ·
C3 unused barrel exports · C4 phantom `ROUTES.marketplace` · C5
`.verification-build/`. Carried since M2.6 sign-off. In or out of T2.7.8?

### S5 — What "all five gates green" requires *(blocking)*

Two gates cannot run here. Either the criterion is met **by you running them
locally** and reporting, or M2.7 closes with two of five gates unverified and
that is stated in the audit rather than implied away.

**This is the one I would not compromise on.** Everything M2.7 has verified was
verified without a type-check.

## 4. Ownership, invariants and boundaries — unchanged by an audit

T2.7.8 introduces no component, no hook, no state and no route, so the ownership
model is untouched:

- `CompareScreen` remains the owner of every business decision on the route.
- Presentation components remain authority-free; the T2.7.7 formulation
  (**ownership, not signature**) is the standard the audit should re-verify
  rather than restate.
- C4 remains the route's authority model; I1–I8 remain module-wide.

**What the audit must verify is that these are still true after seven tasks** —
not by re-reading them, but by confirming the exact-list probes that encode them
are all still exact: two URL writers, one `MAX_COMPARE` enforcer, one
`replaceAll` caller, three `isBestCell` callers, two `bestIndex` files, one
`buildCompareRows` call site, one highlight declaration.

## 5. Verification strategy for the audit itself

**Nothing new is asserted.** An audit that adds assertions is doing another
task's work. What it does is:

1. **Run the full suite** and record the measured baseline (658 at T2.7.7).
2. **Confirm every exact-list probe is still exact** — the lists are the
   milestone's architecture in executable form.
3. **Re-read every probe added in M2.7 against its name**, because three
   vacuous assertions shipped during this milestone and were caught only by
   review. The audit is the last chance to catch a fourth.
4. **Reconcile the documented limitations against reality** — four are recorded;
   confirm each is still true and none has quietly become testable.
5. **Report the gate status honestly**, including the two that did not run.

Point 3 is the one I would weight most heavily. The milestone's own record shows
the failure mode is not missing coverage but **coverage that appears to exist**.

scope was a component. T2.7.8's scope **is** the question: what does closing
M2.7 include? Writing a contract now would mean choosing S1 and S3 by
implication — deciding, in the act of drafting, whether an unreachable module
can be called complete.

**Answer S1–S5 and the contract follows directly**: deliverables, sequencing,
and acceptance criteria are all determined by those five answers, and I can
produce it in one pass.

**No production code, no verification changes, no documentation amendments have
been made.**

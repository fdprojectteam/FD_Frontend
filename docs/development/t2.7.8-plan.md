## 0. Decision log — the five scope decisions, resolved

Recorded with the reasoning and the impact of each, because a decision without
its consequences is re-litigated at the first inconvenience.

### S1 — Does T2.7.8 build R15a's entry affordance?

**Why it matters.** Nothing in `src/` references `ROUTES.compare`. The module is
unreachable, so DoD criterion 5 — *"selection survives Home ↔ Details ↔
Compare"* — cannot be assessed at all.

| Option | Consequence |
|---|---|
| **A — separate T2.7.3b, then audit** ✅ **taken** | Audit builds nothing; criterion 5 becomes assessable |
| B — fold into T2.7.8 | An audit that implements a feature cannot audit it |
| C — close unreachable | Fastest; ships a screen no user can open, and criterion 5 must then be *amended*, not left failing |

**Impact.** Production: none in T2.7.8 (all of it moves to T2.7.3b).
Verification: none here; T2.7.3b owns any new journey. Documentation: the audit
can assess criterion 5 on evidence. Milestone: **M2.7 gains a task** and closes
later, but closes reachable.

### S2 — The rapid-remove race

**Why it matters.** Two removes inside one navigation window compute from the
same stale `ids`, exactly as two Adds did. Left unrecorded it becomes folklore.

| Option | Consequence |
|---|---|
| **Carry as documented debt** ✅ **taken** | Known, recorded, owned; a real race remains in shipped code |
| Fix now (generalise D-PENDING) | Production change inside an audit — and *engagement* would still be unverifiable, so it buys behaviour that cannot be proven here |
| Fix later, unrecorded | The failure mode this project keeps closing |

**Impact.** Production: none. Verification: none. Documentation: one register
entry, recorded exactly as the Add race was — including that the harness could
verify a guard's *release* but never its *engagement*. Milestone: closes with a
named defect rather than a hidden one.

### S3 — Assumptions A1–A7 and A10

**Why it matters.** Eight assumptions are in force and none has been confirmed
by design. Marking a milestone complete over them converts them to product
decisions **by silence**.

| Option | Consequence |
|---|---|
| **Carry to M2.9 unconverted** ✅ **taken** | Design validates them once, with the screens in front of them |
| Accept now | Eight product decisions made by an audit |
| Block M2.7 | Stalls a milestone on questions that need design, not engineering |

**Impact.** Production, verification: none. Documentation: the register lists
them as **carried, not accepted** — the wording is the point. Milestone: M2.9
inherits a defined queue; **A3** (no link from a compared product to its details
page) is the one worth raising first.

### S4 — M2.6 cleanups C1–C5

**Why it matters.** Dead code accumulates quietly, but removing it inside an
audit means the audit changed the thing it measured.

| Option | Consequence |
|---|---|
| **Out of scope** ✅ **taken** | Baseline stays comparable; debt stays listed |
| In scope | The measured baseline would reflect an edit made during measurement |

**Impact.** Production, verification: none. Documentation: register entry.
Milestone: unchanged.

### S5 — What "all five gates green" requires

**Why it matters.** `npm run lint` and `npm run build` have **never run during
M2.7**. The suite bundles with esbuild, which does not type-check — so
everything this milestone verified was verified without one.

| Option | Consequence |
|---|---|
| **Required local gates, unverified until run and recorded** ✅ **taken** | Honest; criterion 11 stays open until you report results |
| Treat as deferred | Two of five gates silently reclassified as optional |
| Treat as expected-to-pass | The precise claim the evidence does not support |

**Impact.** Production, verification: none. Documentation: §5 states them as
unverified and forbids describing them otherwise. Milestone: **M2.7 cannot be
declared complete on the audit's evidence alone** — it needs your two runs.

## 2. What this task does **not** do

Stated first, because every previous task in this milestone was defined by what
it built, and this one is defined by what it refuses to.

- **No production code.** No component, hook, constant, route or type.
- **No architectural change**, no ownership change, no new decision.
- **No new behavioural assertions.** An audit that adds coverage is doing
  another task's work and then reporting on itself.
- **No probe weakened, re-pointed or removed.**
- **No fixes.** Including for anything the audit finds — see R-A2.
- **No M2.9 scope**: no screen-by-screen UI conformance for Home or Details, no
  bundle analysis, no platform-wide a11y count. Those belong to the Final
  Marketplace Audit, and duplicating them here leaves M2.9 nothing to examine.

## 3. Rules governing the audit

### R-A1 — Evidence, not restatement

A criterion is met when a **measured result** says so: a suite figure, a probe
name and its list, a recorded manual observation. "The document says X" is not
evidence that X holds.

### R-A2 — Findings are reported, never fixed *(derived from S2)*

If the audit finds a defect, a vacuous probe, or a stale document, it is
**recorded with a proposed owner and stops there**. S2 established the principle
for the rapid-remove race — carry as documented debt, change no production code —
and the same applies to anything found in the sweep.

**This includes a fourth vacuous assertion**, should §4.3 find one. Correcting it
would be a verification change inside an audit that is meant to have none, and
the correction should be its own reviewed task.

*Flagged for confirmation: this rule is derived from S2's principle rather than
stated in it. If you would rather the audit repair a vacuous probe in place, say
so before it runs.*

### R-A3 — The exact lists are the architecture

Seven probes encode M2.7's structure as executable lists. The audit confirms
each is **still exact**, not merely still passing:

| Exact list | Expected |
|---|---|
| Marketplace URL writers | 2 — `use-marketplace-url-state`, `use-compare-url-state` |
| `MAX_COMPARE` references | 4 files, none of them `use-compare-products` |
| `replaceAll` callers | 1 — `use-compare-url-state` |
| `isBestCell` callers | 3 — value, table, cards |
| `bestIndex` mentions | 2 — `types/compare`, `utils/compare-rows` |
| `buildCompareRows` call sites | 1 — `compare-screen` |
| Winning-cell treatment declarations | 1 — `compare-view.ts` |

A list that has grown is an architectural change that arrived without a decision.

### R-A4 — Limitations are re-tested, not re-copied

Four limitations are documented. For each, the audit asks *is this still true?*
— not *is this still written down?* A limitation that has quietly become
testable is coverage left on the table.

## 4. Audit procedure

### 4.1 Measure

Run `npm run verify`. Record the total and every layer. Compare against the
T2.7.7 baseline of **658** (150 · 266 · 15 · 227). Any movement is explained or
investigated; an unexplained increase is as much a finding as a decrease.

### 4.2 Confirm the exact lists (R-A3)

Read the seven lists from the suite output and confirm each matches §3's table.

### 4.3 The vacuity sweep

**The heaviest-weighted step.** Re-read every assertion added during M2.7 —
L0, L3, L3b, L4, L4b, L6, L6b, L6c, L7, L9, L9b, E, and every invariant section
from T2.7.1a onward — and ask of each: *does its name claim more than it
measures?*

This milestone shipped **three** assertions that could not fail, each caught only
by review:

| Where | What it claimed | What it measured |
|---|---|---|
| T2.7.6 `L3b` v1 | "the first Add is not lost" | an id the journey was *loaded* with |
| T2.7.6 `L3` close step | "closing performs no navigation" | a click on a **disabled** button |
| T2.7.7 `E` | "Back writes no `?ids=`" | counters that had just been reset |

Three in one milestone is a pattern, not bad luck. The sweep is the last
opportunity to find a fourth before M2.7 closes.

Output: a table of every assertion reviewed, with a verdict of *measures what it
claims* / *narrower than its name* / *cannot fail*.

### 4.4 Re-test the limitations (R-A4)

| # | Limitation | Question |
|---|---|---|
| 1 | Layout (scroll-snap, sticky, overflow) | Still true — jsdom has no layout engine |
| 2 | `next/image` outside a Next runtime | Still true |
| 3 | Cross-route navigation | **Changed?** The harness now selects a screen by route (T2.7.3). Whether Home → `/compare` is now expressible is a real question, and if it is, the limitation is narrower than written |
| 4 | The pending Add guard's *engagement* | Still true — the harness router is synchronous |

Item 3 is the one to look at properly: it was written when the harness mounted
`HomeScreen` only.

### 4.5 Assess the Definition of Done

Each of the eleven criteria in `m2.7-implementation-plan.md` §10, with evidence.
Two are known to need judgement:

- **Criterion 10** — *"M2.6's 401 assertions still green"* no longer names
  anything real: probes were re-pointed as components moved, and journeys were
  rewritten. **The audit records this as a finding and proposes** the honest
  form — *"no assertion was weakened, and every re-point is recorded"* — but
  **does not amend the plan**, because rewriting a Definition of Done during its
  own audit is not something an audit may do.
- **Criterion 11** — see §5.

Produce the audit document (§6).

## 1. Scope

### Business goals

Comparison is the decision-support step: it exists to convert a shortlist into
a booking. It is where the marketplace earns its "transparent rates, no hidden
terms" promise, because it puts the numbers side by side and names the winner
per row rather than leaving the user to compute.

### User goals

Answer "which of these is best for me?" without arithmetic — see rate, tenure,
minimum, returns, benefits, and eligibility together; drop a product that no
longer fits; add one that does; and proceed.

### Entry points

| From | Mechanism |
|---|---|
| Product card "Compare" (M2.4/M2.7) | Adds to selection; user navigates to `/compare` |
| Details "Add to Compare" (M2.6) | Same |
| **Shared/deep link `/compare?ids=a,b,c`** | The URL *is* the selection on this route; the store is synchronised from it (C4) |
| Browser back/forward | I8 history entries |

### Exit points

| To | Mechanism |
|---|---|
| Marketplace Home | "Back to Marketplace" link (top and action bar) |
| Product details | *Not in the approved screen* — see §9 R5 |
| Booking | "Select" per column and "Proceed to Booking" — **Phase 3**, inert |

### Dependencies

All satisfied by M2.1–M2.6: `CompareSelectionProvider` (T2.6.7),
`useCompareProducts` (M2.1, still unused — this is its first consumer),
`marketplaceKeys.products.compare(ids)`, `CompareRow`/`CompareSelection` types
(M2.1), `estimatedReturns` from `ProductService`, `BankBadge`, `Dialog`,
`ROUTES.compare`.

### Out of scope

Booking itself · rate slabs · per-product calculators on this screen · sorting
or reordering columns · saving comparisons · printing/exporting · comparing
more than four · any change to Home or Details.

### 2.3 Accessibility considerations

- The desktop table must be a real `<table>` with `<th scope="col">` for
  products and `<th scope="row">` for attributes. A grid of divs would leave
  screen-reader users unable to associate a value with its product.
- The ★ must not be the only signal of "best" (Document 14 §11 — colour and
  icon are not enough). Each winning cell needs a visually-hidden qualifier,
  e.g. "best interest rate".
- Remove buttons need per-product names ("Remove HDFC Bank from comparison"),
  like the M2.5 active-filter pills.
- Carousel (if D1 permits one) needs: labelled region, `aria-live` for the
  position change, keyboard-operable arrows, and dots that are real buttons.
- A removal changes the whole table; the count should be announced politely.

## 3. Architecture

### 3.1 Route

```
app/(public)/compare/page.tsx        server component, static metadata
  └─ <CompareScreen />               client, sole hook owner
```

**A Suspense boundary IS required here** — unlike the details route. This
screen reads `?ids=` via `useSearchParams`, which triggers the CSR bailout
during prerendering (M2.4 defect C2). This is the difference from M2.6 and must
not be copied over by habit.

### 3.2 Data flow

```
?ids=a,b,c ──► parseCompareIds() ──► CompareSelectionProvider (replaceAll)
                                            │
                                            ▼
                                   useCompareSelection().ids
                                            │
                                            ▼
                          useCompareProducts(ids) ──► ProductSummary[]
                                            │
                                            ▼
                              buildCompareRows(products) ──► CompareRow[]
                                            │
                                            ▼
                       CompareTable (≥md) / CompareCarousel (<md)
```

`buildCompareRows` is the M2.7 analogue of `toProductListParams`: **one pure
function**, the only place that decides row order, formatting, and which cell
wins. Directly unit-testable, and the single place a highlighting bug can live.

### 3.3 Compare context interaction

*(Amended T2.7.2a, after the architecture review found that hydrate-once left
Back and Forward inert on this route.)*

**On `/compare` the URL is authoritative; the context follows it.** Elsewhere —
Home, Details — no URL carries the selection, so the context is authoritative
there and `toggle` applies directly. This is not a special case for comparison:
it is the rule Home already follows for its filters, applied to another piece of
state.

1. **Intent writes the URL only.** Add and remove push a new `?ids=`; they do
   not touch the store. One write, so there is no window in which the two
   disagree.
2. **Synchronisation follows.** When the parsed, deduped, **capped** id list
   differs *by value* from the store, the hook calls `replaceAll`. This writes
   React state, never the router, so I7's zero-navigations-on-load still holds.
3. **Rendering reads the store**, so the cap governs what is displayed.

The context gains **one** method, `replaceAll(ids)`, which caps internally and
has exactly one caller. It is not the `addMany` rejected in T2.7.0: looping
`add` cannot express a removal, which is what a shorter `?ids=` and every Back
press require. Full contract: `marketplace-compare-state.md` C4.

### 3.4 URL projection (`?ids=`)

This route is the **second URL writer** in the module — explicitly permitted by
I2a ("a component that *is* the URL owner for its own route"). It follows the
same rules as Home:

- **One writer**, `useCompareUrlState`, owned by `CompareScreen`.
- **I7 write-only canonicalisation** — `?ids=` is rewritten on write, never on
  load. Invalid or unknown ids are normalised internally.
- **I8** — removing or adding a product is *intent* → `push`, and because the
  URL is authoritative (§3.3) those history entries are what Back and Forward
  actually replay. Dropping an unknown id after the batch responds is a
  *correction* → `replace`. Synchronising the store from the URL is neither: it
  performs no navigation at all.
- **Column order is insertion order** and is preserved in the URL, because the
  user can see it. `marketplaceKeys.products.compare(ids)` already **sorts**
  ids for the cache key, so `?ids=a,b` and `?ids=b,a` are two URLs but one
  cache entry — which is correct and worth asserting.

### 3.5 States

| State | Behaviour |
|---|---|
| **Loading** | Skeleton columns matching the final geometry (no layout shift, M2.6 C7) |
| **Empty** (no ids) | Not in the approved designs — see D6 |
| **Single product** | Renders, but "comparison" of one is odd — see D6 |
| **Error** | Retryable card, reusing the M2.6 pattern |
| **Partial** | Some ids resolve, some do not — see §9 R3 |
| **404 per id** | An unknown id is dropped from the selection, not a page error |

### 3.6 Navigation

"Back to Marketplace" is a `<Link href={ROUTES.home}>` — never `router.back()`,
for the same reason as M2.6 (a user arriving from a shared link has no history).
`ROUTES.compare` needs the `as Route` cast once the page exists (E4 precedent).

### 3.7 Cache behaviour

`useCompareProducts` uses `products.compare(sortedIds)` — a **distinct key per
selection**, so removing a product refetches the smaller set rather than
filtering client-side. That is one extra request per removal.

An alternative is to resolve each product from `products.detail(id)` or the
list caches and avoid the batch entirely. **Not proposed** — the batch endpoint
exists, the roadmap specifies it, and inventing a client-side join would
duplicate what the API already does. Recorded so the cost is a decision rather
than an accident.

### D1 — The mobile carousel *(decided: A)*

The approved mobile screen shows one card with ‹ › arrows and dots. Nothing in
the design system does this, and "no new primitives" is a standing rule.

| | Approach | Assessment |
|---|---|---|
| **A** | **CSS scroll-snap row**, arrows and dots as plain `Button`s driving `scrollTo` | No new primitive; native touch swipe; keyboard and screen-reader friendly; matches the approved appearance closely. Dots/arrows are composition, not a component. |
| **B** | A real carousel primitive | Matches the design exactly but adds a primitive and a dependency-free-but-nontrivial widget with its own a11y contract. |
| **C** | Stack all cards vertically below `md` | Simplest, no new anything — but visibly *not* the approved design. |

Recommendation: **A**. It reproduces the approved interaction using existing
primitives plus CSS, and scroll-snap degrades to a plain scroll if anything
fails.

### D2 — Hydration semantics *(decided: URL wins — amended T2.7.2a to "continuously", not "once")*

Does `?ids=` win over an existing in-memory selection, or merge with it? A user
with two products selected who opens a shared three-product link should get a
predictable result. Recommendation: **the URL wins** — a shared link means "show
me this comparison".

*Amended T2.7.2a.* This originally read "wins on cold load, **once**". Once-only
meant Back and Forward moved the address bar and left the table unchanged, which
also made I8's history entries unusable. The URL now wins **continuously** on
this route (§3.3, `marketplace-compare-state.md` C4).

### D3 — "Select" and "Proceed to Booking" *(decided: inert)*

Booking is Phase 3. Recommendation: both inert with `aria-disabled`, matching
the established treatment on Home ("How it works") and the M2.6 action bar. No
state is carried.

### D4 — What the "Add another FD" picker shows *(decided: full catalogue)*

The design never shows the dialog open. Options: the full catalogue with a
search field, the current listing's results, or the recommended set.
Recommendation: **the full catalogue paginated via the existing `useProducts`**,
with already-selected products disabled — no new endpoint, no new query key.

### D5 — Minimum sensible comparison *(decided: one product renders)*

Is `/compare?ids=a` (one product) valid? Recommendation: **yes, render it** —
it is a legitimate intermediate state while the user builds a shortlist, and
blocking it would mean inventing an error the design does not have.

### D6 — Empty state copy *(decided: reuse the M2.6 pattern)*

`/compare` with no ids has no approved screen. Reuse the M2.6 empty-state
pattern — a short line plus a "Browse Fixed Deposits" link to `ROUTES.home`.
**The copy is new and still needs design confirmation** (§5.7 A2).

### 5.7 Assumptions register *(T2.7.0)*

A decision settles what we build. An **assumption** is where the approved design
is silent and we must nevertheless ship something. These are recorded so that a
reviewer can see what was filled in, rather than discovering it in the diff.

Each has a **default in force** — implementation proceeds on it — and each is
reversible at the stated cost if design says otherwise.

| # | Where the design is silent | Default in force | Cost to reverse | Owner |
|---|---|---|---|---|
| **A1** | The "Add another FD" dialog is never shown open | Full catalogue via existing `useProducts`, already-selected items disabled, cap respected | Low — contents of one dialog (T2.7.6) | Design |
| **A2** | No empty-state screen for `/compare` with no ids | M2.6 pattern: one line + "Browse Fixed Deposits" → Home | Low — copy only | Design + copy |
| **A3** | No route from a compared product to its details page (**risk R5**) | **No link.** The approved screen has none, and adding one is a design change | Low to add later; high to remove once users have it | Design |
| **A4** | Carousel behaviour at the ends | **Does not loop.** Arrows disable at first/last | Low (T2.7.5) | Design |
| **A5** | Removing the last remaining product | Show the empty state; **do not redirect** to Home | Low — one branch (T2.7.3) | Design |
| **A6** | Highlighting when only one product is compared | **Suppress highlighting.** A sole column "winning" every row is noise, not information | Low — one condition in `buildCompareRows` (T2.7.1) | Design |
| **A7** | Whether the count reads "Comparing 1 of 4 Product" or "Products" at N=1 | Keep **"Products"** — the approved string is not pluralised dynamically anywhere else in the product | Trivial | Copy |

**A3 is the one worth a decision rather than a default.** A user comparing three
products cannot open any of them to read the FAQs or the interest breakdown
without going back to the listing and finding it again. That may well be
deliberate — the comparison screen is meant to end in a booking, not in more
browsing — but it is the assumption most likely to be wrong, and the cheapest to
correct before implementation rather than after.

## 7. Verification plan

**Unit** — `buildCompareRows`: row order; the four winner rules; Tenure and the
text rows having `bestIndex === null`; **ties resolving to the leftmost column**;
one product; empty input; values formatted through the shared utils.
`compare-url`: **syntax only** — parse, dedupe (first occurrence wins), drop
malformed ids and empty segments, bound the raw string, canonical serialisation,
order preservation. **It does not cap** *(corrected in T2.7.2b; this line read
"cap at 4" before D8 existed)*: the cap belongs to `useCompareSelection` alone
(C2, O1), and the assertion that proves it is **more than four ids parse
intact**.

**Invariants** — `CompareScreen` is the sole hook owner; **exactly two URL
writers now exist module-wide**, one per route; the compare route pushes and
never replaces except for correction; `buildCompareRows` has one call site; no
component recomputes maturity; the cap lives only in `useCompareSelection`
(exact file list, C2/O1); `replaceAll` has exactly one caller; no compare
component calls `add`/`remove`/`toggle`; the table is a real `<table>` with
scoped headers.

**Journeys (L-series)** — L1 select on Home → navigate → compare renders in
selection order · L2 remove a column → table, count, and URL all update in one
write · L3 add via the picker → cap enforced at 4 · L4 cold load of
`?ids=a,b,c` with **zero navigations** · L5 hostile ids (unknown, malformed,
> 4, duplicates) · L6 back/forward across removals · **L6b Back after a removal
restores the column and the count** · **L6c an over-cap URL settles (R13)** ·
L7 empty state → link home ·
L8 a11y: one `h1`, `<th scope>` correctness, per-product remove names, hidden
"best" qualifiers.

**Manual browser** — the mobile carousel (scroll-snap, swipe, arrows, dots) ·
sticky action bar at both breakpoints · table overflow at 3 vs 4 columns ·
Dialog focus trap and restore.

**Known jsdom limitations — stated up front.** The harness has no layout engine
and no scroll: **scroll-snap, arrow-driven scrolling, dot sync, and sticky
behaviour cannot be tested there**, nor can column overflow. Radix Dialog's
focus trap is only partially observable. These need a real browser, exactly as
M2.6's breakpoint behaviour did.

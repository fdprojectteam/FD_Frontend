# T0.7 — shadcn/ui Foundation: Implementation Blueprint

Project: FD Investment Platform
Status: Awaiting approval — no code until approved
Last Updated: 2026-07-30

---

## 1. Objective

shadcn/ui is introduced as a **component scaffolding source**, nothing more. It gives us accessible, battle-tested behavioral primitives (built on Radix UI) that we own as source code in our repository — no runtime component library dependency, no version-lock on someone else's visual decisions.

The position in our architecture is fixed and non-negotiable:

- shadcn/ui is **only a component foundation** — a starting point for behavior (focus trapping, keyboard navigation, ARIA wiring).
- It is **not our design system**. Our Design System (Documents 06–07 + the approved Design Token Inventory) is the single source of truth for every visual decision.
- **Every generated component is re-skinned with our design tokens before first use.** Default shadcn appearance never ships — not in a demo, not in a placeholder.
- What we gain from shadcn: correct accessibility semantics for hard components (Dialog, Select, Accordion, Tabs) that would take days to build safely from scratch. What we explicitly do not take: its colors, radii, shadows, spacing, or typography.

## 2. Architecture

The complete flow from token to feature:

```
Design Tokens                src/design-system/tokens/*.css
  (--ds-* variables — the only place raw values exist;
   provenance: docs/engineering/design-tokens.md)
        ↓
Tailwind Theme               src/app/globals.css @theme inline
  (maps tokens to utilities: bg-surface-brand, text-h1,
   rounded-card, shadow-elevation-1 — off-scale values
   don't exist as utilities)
        ↓
CVA Variants                 cva() definition inside each ui component
  (variant × size × state matrix composed exclusively from
   token utilities; the only sanctioned styling API)
        ↓
shadcn Primitive             Radix behavior + our CVA classes
  (accessibility engine: focus, keyboard, ARIA;
   visual defaults stripped)
        ↓
Platform Component           src/components/ui/* (design-system owned)
  (Button, Input, Card… — clean typed props API;
   what every module consumes)
        ↓
Business Component           src/components/business/* or modules/*/components
  (FDProductCard, DepositCalculator, InterestRateDisplay —
   composes platform components + domain meaning)
```

Enforcement is mechanical, not aspirational: the ESLint boundary rules (T0.3) prevent business modules from bypassing layers, and the wiped Tailwind default scales (T0.5) mean a hardcoded shadow or off-grid radius has no utility to reach for.

## 3. Folder Structure

```
src/components/
├── ui/            # Platform components (shadcn-derived, token-skinned).
│                  # Domain-agnostic: knows nothing about FDs, banks, money.
│                  # Owned by the Design System; changes require DS review
│                  # (Document 06 §16).
├── business/      # Cross-module fintech components: InterestRateDisplay,
│                  # BankBadge, TrustIndicator, AmountDisplay. Compose ui/
│                  # components + domain formatting. Reused by ≥2 modules;
│                  # single-module business components live in that module.
├── forms/         # React Hook Form integration layer: FormField, FormLabel,
│                  # FormError, FormSection. Binds ui/ inputs to RHF + Zod
│                  # with accessible error wiring (aria-describedby).
├── navigation/    # TopNav, Footer, Breadcrumbs, (Sidebar in Phase 3+).
│                  # Consumed by layouts/, role-aware via props.
└── feedback/      # EmptyState, ErrorState, LoadingSkeleton compositions,
│                  # toast presets — the Document 05 §16–18 state patterns.
```

Rules of residence: if a component mentions a domain concept, it cannot live in `ui/`. If it is used by only one module, it belongs in that module's `components/` folder, not here. `ui/` never imports from any other component folder (enforced direction: business/forms/navigation/feedback → ui, never the reverse).

## 4. Component Generation Rules

1. **Never modify Radix primitives directly** — behavior comes from Radix as-is; customization happens in our wrapper layer only. (Radix packages update independently; local forks would orphan us.)
2. **Never ship default shadcn styling.** Generation is step one of a rework, never an endpoint.
3. **Always replace default styles with design tokens** — every class in the final component resolves to a `--ds-*` token through the Tailwind theme.
4. **Every component uses CVA** for its variant API — no ad-hoc conditional class strings, no style props.
5. **Every component supports variants** per the Component Token Mapping (inventory §2e) and Document 07 §12.
6. **Every component is accessible**: WCAG 2.2 AA, keyboard operable, `focus-ring` utility on interactive elements, ARIA correctness inherited from Radix and preserved.
7. **Every component is responsive** — behavior adapts across the approved breakpoints (768px / 1200px) without API changes (Document 06 §14).
8. **Never hardcode colors** — no hex values, no Tailwind default palette classes (`bg-purple-600` does not exist in our theme; `bg-surface-brand` does).
9. **Never hardcode spacing** — 4px-base scale utilities only; no arbitrary values (`p-[13px]` requires written justification in review).
10. **Never hardcode radius** — only `rounded-sm/md/lg/card/full` (default scale is wiped; others don't exist).
11. **Never hardcode shadows** — only `shadow-elevation-1/2/overlay`.
12. **`className` pass-through is composition-only** — consumers may adjust layout placement (margin, grid area), never repaint internals.
13. **One component, one file, one export** plus its CVA definition and types — per Document 12 §4.

## 5. Component Lifecycle

Every platform component follows this pipeline; no step is skippable:

```
Generate shadcn primitive        npx shadcn add <component> → src/components/ui/
        ↓
Replace styling                  strip default classes; delete unused variants
        ↓
Apply Design Tokens              restyle from Component Token Mapping (§2e)
        ↓
Create CVA variants              variant/size/state matrix per inventory + Document 07 §12
        ↓
Accessibility review             keyboard walk, focus-visible ring, screen-reader
                                 labels, contrast check against AA
        ↓
Responsive review                behavior verified at <768 / 768–1199 / ≥1200
        ↓
Export platform component        typed props API documented (purpose, props,
                                 variants, a11y notes — Document 07 §17);
                                 added to the Phase 1 component gallery page
```

The Phase 1 review gallery (a dev-only route rendering every component in every variant × state) is how you will visually approve components against the approved UI before any Marketplace screen is built.

## 6. Component Standards

Mandatory for every platform component:

| Standard | Requirement |
|---|---|
| **Props** | Minimal, explicit, fully typed; sensible defaults; extends the native element's attributes; `ref` forwarded |
| **Variants** | CVA-defined; only variants observed in the approved UI or Component Token Mapping — no speculative variants |
| **Sizes** | From size tokens exclusively (`button-sm/md/lg`, `input-md/lg`, `icon-sm/md/lg`) |
| **States** | Default · Hover · Focus · Active · Disabled · Loading · Error (where applicable) — all token-styled, all visually distinct |
| **Loading** | Built-in where async is plausible (Button spinner + `aria-busy`, content components pair with Skeleton); never a layout shift |
| **Disabled** | `opacity-disabled` token, `pointer-events` handled, real `disabled`/`aria-disabled` semantics — never CSS-only fake disabling |
| **Error** | Error state uses `--ds-color-error` + icon + message pattern (never color alone — Document 14 §7); wired to `aria-invalid` + `aria-describedby` |
| **Focus** | `:focus-visible` ring from focus tokens on every interactive element; focus trapped in overlays and returned on close (Document 14 §6, §14) |
| **Keyboard** | Tab/Shift+Tab, Enter/Space activation, Escape dismissal, arrow keys where composite (Select, Tabs, Accordion) — Radix supplies, we must not break |
| **Screen reader** | Accessible name required (visible label or `aria-label`); decorative icons `aria-hidden`; state changes announced (toast → `role="status"`) |
| **Testing considerations** | Structured for future automated testing: deterministic markup, no logic in components (Document 12 §16), stable accessible names as query hooks; manual keyboard + axe pass in Phase 1 review |

## 7. Initial Components (generated in Phase 1 — not now)

Selected strictly from what the approved Marketplace UI and platform shell require:

| Component | Justification (evidence in approved UI) |
|---|---|
| **Button** | Primary/secondary/outline everywhere: hero CTAs, View details, Compare, Search, Calculate, booking actions |
| **Input** | Search bar, amount fields, calculator; foundation for all future forms |
| **Select** | Tenure dropdown in search panel and calculator |
| **Card** | The core surface: product cards, key-info cards, compare columns, featured banks |
| **Badge** | Trust badges (RBI Regulated, DICGC Insured, AAA Rating), "Highest Rate"/"Short-Term" flags, benefit tags |
| **Chip** *(addition)* | Filter chips (Bank/Tenure/Interest Rate/Amount) and benefit chips are pill interactives distinct from Badge (they toggle); explicitly present in the approved UI and the design-system poster |
| **Accordion** | Product details: Interest breakdown, FAQs, Terms & Conditions |
| **Tabs** | Platform staple for future Portfolio/Reports; generated last in Phase 1 as it has no Marketplace usage — included per approved foundation list |
| **Dialog** | "Add another FD" selection in Comparison; base for all future modals; hardest a11y surface — exactly why it comes from Radix |
| **Toast** | Platform feedback capability (Document 05 §15): compare-list confirmations, future booking feedback |
| **Pagination** | Product grid pagination ("Showing 1–6 of 24", numbered pages) |
| **Skeleton** | Document 13 §16: skeleton screens over spinners for every loading experience |

Also generated as invisible infrastructure: `cn()` utility and shared CVA type helpers. Anything else (Table, Drawer, Tooltip…) waits until a screen actually needs it — rule 4.5, no speculative components.

## 8. Definition of Done — T0.7

T0.7 itself is the **initialization layer** (components are Phase 1 work). Complete when:

1. shadcn/ui initialized: `components.json` configured for our stack (RSC, TSX, `@/components/ui` + `@/lib` aliases) and pointed at **our CSS variables** — not shadcn's default palette.
2. `cn()` utility exists in `src/lib` (clsx + tailwind-merge), the single class-composition helper.
3. Required peer utilities present and version-pinned (CVA, clsx, tailwind-merge, lucide-react, tw-animate/radix peers as required by the generator).
4. **Zero component files generated** — `src/components/ui/` remains empty; nothing default-styled exists anywhere in the tree.
5. Generation rules (§4) and lifecycle (§5) recorded in this document and referenced from the roadmap.
6. A generation dry-run performed in the sandbox (generate Button → verify it lands in `src/components/ui/` with our aliases → **delete it**) proving the pipeline works without committing any default-styled artifact.
7. All gates green: `build`, `lint`, `typecheck`, `format:check`; boundary rules untouched.

## 9. Approval Gate

No code will be generated until this blueprint is approved. On approval, T0.7 executes exactly the Definition of Done above; the twelve components in §7 are then implemented in Phase 1, one lifecycle pass each, starting with Button (the reference implementation for the pattern).

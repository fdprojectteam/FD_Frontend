## 1. Approved decisions

Recorded as settled. No further discussion required; implementation follows
these exactly.

### D1 — Search commits explicitly *(approved)*

- The explicit **Search** button is kept.
- **Debounced search is not implemented in M2.5.**
- Search commits **only** on button click or `Enter` within the search panel.
- **T2.5.7 (Debounce) is removed from this milestone.**

Consequence: the roadmap wording *"debounced search bound to `?q=`"* is
inaccurate and should be corrected to *"explicit search bound to `?q=`"*.
`marketplace-url-state.md` §I6 needs no amendment — in-progress input text
remains transient local state, and only the committed query reaches the URL.

Consequence for the writer: one commit = one `router.replace()` (rule 5). With
no timer in play, there is no pending-write reconciliation problem on
back/forward — the class of bug that produced defect C1 is removed from this
milestone by construction, not by mitigation.

### D2 — URL parameter set *(approved)*

The complete and closed Marketplace Home parameter set:

```
q  amount  tenure  bank  minRate  page  sort  order
```

- No other parameter may be written by Home. `category` is **dropped** from the
  reserved set in `marketplace-url-state.md` — it has no approved control.
- Interest Rate needs no new parameter; `minRate` covers it, driven by
  `RATE_BANDS` in `constants/filters.ts`.
- `tenure` stays as the URL name (already present in shipped links). The
  translation to the API's `tenureMonths` happens in one place — see §2.
- `q` stays as the URL name. The translation away from `ProductListParams`'
  inherited `search` happens in the same place.

### D3 — Search panel and filter chips share one state *(approved)*

The Search panel and the filter chips **edit the same URL state** and must
remain synchronised **through the single URL writer**.

- The panel's Tenure/Amount controls and the Tenure/Amount chips read the same
  URL keys and write through the same `merge()`.
- Synchronisation is therefore a property of the architecture, not a feature to
  implement: both controls are props-driven, both render from the same parsed
  values, and neither holds a shadow copy.
- No UI change is required by this decision.

## 3. Contract gaps to be closed

Both are silent today — no type error, no lint error; the filter simply does
nothing. Both are resolved in `toProductListParams()` per A5/A6.

| Gap | Detail | Fix |
|---|---|---|
| **G1 — search key** | The MSW handler filters on `q`. `ProductListParams` has no `q`; it inherits `search` from `PaginationParams`. Passing `search` produces `?search=hdfc`, which the handler ignores. | **Approved scope:** add `q?: string` to `ProductFilters`. **Do not remove `search` from `PaginationParams` in this milestone** — mark it `@deprecated` and unused for Marketplace, and remove it in a later cleanup once no other module is confirmed to depend on it. `PaginationParams` is platform-shared, so its removal is not a Marketplace-local change. |
| **G2 — tenure key** | The URL carries `tenure`; the handler filters on `tenureMonths`. | Map explicitly inside `toProductListParams()`. The URL param is **not** renamed. |

Verified against `src/mocks/handlers/products.ts`: the handler already honours
`q`, `bank`, `minRate`, `amount`, and `tenureMonths` server-side, so **no mock
changes are needed** beyond regression fixtures.

## 4. Task breakdown

Each task is independently verifiable and leaves the tree green.

### T2.5.1 — Extend the URL state owner *(no UI)*

Add `bank` and `minRate` to `MarketplaceUrlValues`, and a `setFilters(patch)`
setter alongside `setSearch` / `setListing`.

- `setFilters` resets `page` in the **same single write** (rule 4).
- Validation on read: unknown `bank` ids and non-numeric or out-of-range
  `minRate` fall back to "no filter" — a hand-edited URL must never break the
  screen.
- **Canonicalisation (I7, write-only):** defaults are omitted **on write**;
  on read they are normalised internally only. No `router.replace()` fires on
  load, so a shared or hand-edited link renders correctly without rewriting
  itself.
- Semantic validation that needs data (e.g. an unknown but well-formed `bank`
  id) is **not** performed in the hook — the hook must not fetch. Such a value
  reaches the API, returns zero results, and lands in the empty state with a
  clear-filters action. Documented, not silently swallowed.

**Files.** `hooks/use-marketplace-url-state.ts`
**Verification.** URL-state suite extended to ~45 assertions: every filter
alone; every pair; filters + search + sort + page; clearing each filter;
clearing all; exactly one `replace` per interaction; and the full I7 canonical
table (§6).

### T2.5.2 — `toProductListParams()` *(no UI)*

One pure function converting validated URL values into the API parameter
shape — the single translation layer required by A5, resolving G1 and G2.

```ts
// modules/marketplace/utils/list-params.ts
export function toProductListParams(
  values: MarketplaceUrlValues,
  limit: number,
): ProductListParams
```

**Why a separate function.** Today `HomeScreen` builds the params object
inline. With eight parameters and two name mappings, that inline object becomes
the place where filters silently stop working. A pure function is directly
unit-testable without React and gives A5 a single call site to assert.

**Files.** `utils/list-params.ts`, `types/filters.ts` (add `q`)
**Verification.** Unit assertions for every mapping, including empty-string and
out-of-range inputs; assert the produced key set matches the handler's read set.

### T2.5.3 — `FilterBar` component *(presentation-only)*

The approved chip row: Bank · Tenure · Interest Rate · Amount.

- Props only: current values plus `onChange`. No hook, no router, no service.
- Options come from `constants/filters.ts` (`TENURE_OPTIONS`, `RATE_BANDS`,
  `AMOUNT_PRESETS`) and from `useBanks()` **via HomeScreen**, not directly.
- Built from the frozen `Chip` primitive. No new primitives.
- A chip is a `<button aria-pressed>` — it toggles a filter, it is not a link.

**Files.** `components/filter-bar.tsx`
**Verification.** Boundary probe (A1/A3); accessible name and pressed state per
chip; keyboard operable.

### T2.5.4 — `ActiveFilters` component *(presentation-only)*

Removable pills for each applied filter plus "Clear all".

- Renders nothing when no filter is active — no empty row, no layout shift.
- Each pill's accessible name states what removing it does
  ("Remove filter: HDFC Bank").

**Files.** `components/active-filters.tsx`
**Verification.** Boundary probe; a11y naming; empty-render case.

### T2.5.5 — Wire into `HomeScreen`

`HomeScreen` remains the sole hook owner and sole URL writer (A1, A2, I2a).

- Add `handleFilterChange` and `handleClearFilters`, each exactly one
  `setFilters` call.
- Feed the listing query from `toProductListParams(values, DEFAULT_PAGE_SIZE)`.
- Search submit continues to route through `setSearch` on click/Enter only (D1).
- Pass banks from the existing `useBanks()` query into `FilterBar` — no second
  banks fetch (I5).
- **The hero sample query must not change** (A4). It stays
  `{ sort: 'interestRate', order: 'desc', limit: HOME_PRODUCT_SAMPLE }`.
  Filtering the hero would make "highest rate available today" depend on the
  user's filters — wrong, and invisible until someone filters.

**Files.** `components/home-screen.tsx`
**Verification.** Journey suite (§5); hero and recommendations provably static.

### T2.5.6 — Empty state with clear-filters action

`ProductGridSection`'s empty branch gains an `onClearFilters` callback and
accurate copy. The current copy already references clearing a search, which
only becomes true once T2.5.5 lands.

**Files.** `components/product-grid-section.tsx`
**Verification.** Empty state reachable via a real filter combination (not a
mock scenario); the clear action returns to `/` in one `replace`.

## 5. Verification plan

The harness built during the M2.4 audit is committed as the project's first
real test setup rather than rebuilt ad hoc (risk R6).

### 5.1 Layers

| Layer | What runs |
|---|---|
| Unit | `toProductListParams` mappings (incl. G1/G2 and the handler key-set match); URL merge, validation, and canonicalisation (~45 assertions) |
| Integration (DOM + real MSW) | Full user journeys — see 5.2 |
| Invariants | The extended probe: `setFilters` callable only from `HomeScreen`; `FilterBar`/`ActiveFilters` hook-free; single `router.replace()` module; single `toProductListParams` call site |
| Boundaries | Existing import-graph probe, unchanged |
| Gates | `tsc`, `eslint --max-warnings 0`, `prettier --check`, `next build` |

### 5.2 Journey verification *(approved extension)*

Runtime verification is extended from pairwise interaction checks to **complete
user journeys**, exercising search, filters, sorting, pagination, back/forward,
refresh, and shared URL **together** rather than only in pairs.

**J1 — Discover and refine**
Search `q` → apply Bank → apply Tenure → sort → page 3 → remove one filter →
clear all → back to `/`. Asserted at every step: one `replace`, correct result
set, correct count, page reset where required, hero unchanged.

**J2 — History integrity**
Run J1, then walk the entire history backwards and forwards. Every intermediate
state must restore exactly, including scroll-independent focus behaviour, with
no write triggered by a history navigation.

**J3 — Refresh fidelity**
At three points inside J1 (filtered, filtered + sorted, filtered + sorted +
paged), remount from the current URL and assert the rendered state is identical
to the pre-refresh state.

**J4 — Shared URL**
Cold-load a URL produced mid-journey by another session, including a
hand-edited hostile variant (unknown bank, `minRate=abc`, `sort=nonsense`,
`tenure=99`). The screen must render a valid normalised state, never error, and
— per the approved write-only rule — issue **zero** `router.replace()` calls on
load. The out-of-range `page` clamp is the one named exception (§6).

**J5 — Two controls, one state (D3)**
Change Tenure in the search panel, then in the chip row, then back. Both
controls must reflect the same value at every step, and no interaction may
produce more than one `replace`.

**J6 — Canonical URLs (I7, write-only)**
The table in §6, asserted end to end: URL untouched on load, canonical after the
next user-initiated write.

**Regression set that must stay green:** the full 39-assertion M2.4 runtime
suite. Filters must not alter pagination, sorting, focus, or hero behaviour.

## 6. New invariant — I7 Canonical URLs *(write-only, approved)*

Added to `marketplace-url-state.md` alongside I1–I6.

> **I7 — Canonical URLs.** Equivalent states must always produce exactly one
> canonical URL. Canonicalisation is **write-only**: a non-canonical or invalid
> URL is normalised *internally on read* and must **not** trigger a
> `router.replace()` on load. A canonical URL is emitted only when Marketplace
> performs a **user-initiated write** — search, filter, sort, pagination, clear.

| Input | Rendered as | URL on load | URL after the next user write |
|---|---|---|---|
| `?page=1` | page 1 | unchanged | `/` |
| `?sort=interestRate&order=desc` | default sort | unchanged | `/` |
| `?bank=` | no bank filter | unchanged | `/` |
| `?bank=hdfc&page=1` | HDFC, page 1 | unchanged | `?bank=hdfc` |

Why write-only: rewriting the URL on load is a navigation the user did not
perform. It would break "exactly one `replace` per user interaction" (rule 5),
add a history entry nobody asked for, and make a shared link mutate itself in
front of the recipient. Normalising on read gets the same rendering guarantee
without touching history.

**Named carve-out — the out-of-range page clamp.** `HomeScreen` corrects
`?page=99` to the last real page after the response arrives (M2.4 approved
behaviour, verified). This is **not** I7 canonicalisation and is deliberately
retained:

- I7 governs states that are *equivalent* and known to be so at parse time.
  `?page=99` is not equivalent to page 4 — it is **invalid**, and its validity
  cannot be determined until the server reports `totalPages`.
- Without the clamp, a stale deep link renders an empty listing with pagination
  showing a page that does not exist. That was M2.4 defect territory.

It remains the one write on this screen not initiated by the user. It is called
out here rather than hidden, and re-raised in the final audit for a decision in
M2.6.

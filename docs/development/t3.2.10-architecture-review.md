**Reviewing** `t3.2.10-readiness-package.md` · **Date** 2026-08-06

A note on posture: I wrote the package under review. I have therefore looked

---

## 1. Architecture

### 1.1 ⚠ `DepositTerms` now carries three duplicated facts — **the central finding**

The type has drifted into a pattern where a machine-readable truth sits beside
human display copy, with **no enforced relationship between them**:

| Machine truth | Display copy | Can they disagree? |
|---|---|---|
| `tenureRates: TenureRate[]` | `interestRate: number` (headline) | ✅ **yes** |
| `tenureRates: TenureRate[]` | `tenureRange: { minDays, maxYears }` | ✅ **yes** |
| `supportedPayouts: PayoutOptionId[]` | `payoutOptions: string[]` | ✅ **yes** |

Each pair is a **one-owner violation**, and I introduced two of the three
(T3.2.4b and T3.2.9) while documenting them as deliberate. The documentation was
the mistake: calling a field "marketing copy" explains why it exists, not why it
is allowed to contradict the truth beside it.

The concrete failure mode is live today:

```
Overview rail   → buildInvestmentSummaryRows → terms.interestRate      → 7.25%
Details rail    → buildConfiguredSummaryRows → resolveTenureRate(24)   → 7.25%
```

These agree only because the fixture makes them agree. Change `interestRate` to
7.50% without touching the card and **two screens in one booking quote different
rates for the same deposit** — the precise defect the tenure→rate model was
created to prevent, reintroduced one field along.

`tenureRange` is worse, because it is not merely redundant but *actively
contradictory*: it advertises "7 Days – 10 Years" while the card publishes one
tenure, and §5.1 of the package is the consequence.

**Required before T3.2.10** (see §9, M1–M3):

- `interestRate` becomes **derived** — the headline is the rate of a nominated
  tenure (`headlineTenureMonths`), or the card's maximum. Not a free field
- `payoutOptions: string[]` is **deleted**; the rail derives its text from
  `supportedPayouts` through `PAYOUT_OPTION_LABELS`, which already exists
- `tenureRange` is **deleted or derived** from the card's min and max

All three are cheap now (one fixture, two row builders) and expensive after two
more screens read them.

### 1.2 The screen is becoming a god-component — real, not yet urgent

`InvestmentDetailsScreen` currently owns 1 `useState`, 1 `useEffect` and 4
`useMemo`s. T3.2.10 adds at least two more derivations plus custom-input state.
The invariant *"the route's sole owner"* is being satisfied by putting
everything in one file, which is not the same thing.

**Recommendation:** extract `useInvestmentConfiguration(deposit)` into
`modules/booking/hooks/`, returning `{ configuration, quickAmounts,
payoutOptions, tenures, errors, returns, actions }`. The screen becomes
composition; the derivations become independently testable. Marketplace already
has `hooks/` for exactly this. **Not a blocker** — but doing it *before* T3.2.10
is cheaper than after, and the hook is where §5.3's payout-reconciliation logic
will have to live.

### 1.3 The default-payout seeding effect — accepted, with a caveat

Writing the default into the draft (T3.2.9) was the right call over a
render-time fallback; the alternative had the screen pricing one thing while the
record held `null`. But it means **merely visiting the screen creates a draft
with `updatedAt` set and records a choice the user never actively made.**

Consequences to be aware of rather than fix now: Review & Confirm will say "you
chose At Maturity" for a user who never opened the control, and abandonment
analytics cannot distinguish a visit from an engagement. Acceptable because the
UI *did* show it selected. **Log as debt, revisit at Review & Confirm.**

### 1.4 Hidden coupling — one found, one cleared

- **Cleared:** `resolveTenureRate` being called twice per change (rail + engine)
  is not coupling. Same pure function, same inputs, no shared state.
- **Found:** `EstimatedReturns` imports `PAYOUT_OPTION_LABELS` to render the
  instalment sentence. Minor, but it means a presentation component reaches into
  domain constants. Better: `ReturnsResult` carries a `payoutLabel`, or the
  screen passes it. **Low priority; note at R1.**

## 2. Domain Model

### 2.1 `TenureRate` — insufficient for the stated future

```ts
interface TenureRate { tenureMonths: number; annualRate: number }
```

| Gap | Consequence |
|---|---|
| **No identity** | A rate band cannot be referenced by an audit record, a booking, or a "rate changed" notification. Doc 13 requires every transition to be auditable |
| **No effective dating** | Doc 19 §Versioning: *"Historical bookings should always reference the version that was effective at the time of investment."* Not possible. This is a **stated requirement already deferred**, not a future nicety |
| **No unit** | The §5.1 problem. `tenureMonths` cannot express 7 days |
| **No compounding frequency** | See §3.3 — the engine hardcodes quarterly |
| **Percentage as bare `number`** | `7.25` and `0.0725` are both valid. V3 in the package admits the platform cannot detect the error. A branded `Percentage` type would make it a compile error |
| **No display label** | Banks say "1 Year", not "12 months". Currently `formatTenure` decides for them |

### 2.2 `InvestmentConfiguration` — one real defect

```ts
interface InvestmentConfiguration {
  amount: number | null;
  tenureMonths: number | null;
  payoutOption: PayoutOptionId | null;
}
```

**Defect: fractional rupees are permitted.** The persisted schema is
`z.number().positive().finite()` with **no `.int()`** — while `tenureMonths`
correctly has `.int()`. So `amount: 500000.5` round-trips through storage and
into the returns engine. `validateAmount` does not reject it either.

Nothing produces such a value today: the field strips non-digits, and quick
amounts are integers. But a hand-edited storage entry or a future API would pass
straight through. **Fix now — it is one `.int()` and one validation branch, and
"the platform accepts half a rupee" is not a defect to discover in production.**

**Missing: the applied rate is never captured.** The configuration records what
the user chose but not what they were quoted. Doc 19 requires *"Confirmed
Interest Rate"* to be persisted, and BR-PROD-003 needs a before/after to detect a
change. Correct for a *draft* — derived is right while editing — but the
transition to a booking record needs it, and Review & Confirm is two screens
away. **Not a T3.2.10 blocker; must be designed before Review.**

### 2.3 Integration contract — two omissions

Ownership and flow (§2.2–2.3 of the package) are sound. Missing:

1. **No reconciliation step when tenure changes.** If §5.3 turns out to be real —
   payout availability varying by tenure — the flow needs an explicit
   *"re-narrow payouts; reset the selection if it is no longer offered"* stage.
   The contract should name that stage now, even as a no-op, so it is not
   retrofitted into an effect later.
2. **No statement of who clears a stale `ReturnsResult`.** Today the memo returns
   `null` and the strip shows its awaiting state. Correct, but unstated — and
   the behaviour matrix row 6 (invalid month keeps the previous figures) implies
   the *opposite*, which is a latent contradiction between §2.3 and §3.

### 2.4 Missing before implementation — spec requirements not modelled

Two items **spec 21b requires** are absent from `ReturnsResult` and were not
raised by the package:

- **Maturity Date** (§E: *"Maturity Amount ↓ Maturity Date"*). Not computable —
  there is no value date, and no day-count convention
- **Effective Annual Yield** (§6, "Derived")

Maturity Date is the more serious: it is the single most concrete thing a
depositor wants, it appears in the spec's own calculator list, and computing it
requires the same day-granularity decision as §5.1. **These two questions are the
same question.**

## 3. Product Modelling

### 3.1 The six listed questions — assessment

| # | Question | Assessment |
|---|---|---|
| 7 Days vs Months | ✅ Correctly identified as a blocker. Under-stated: it is also why Maturity Date cannot be computed |
| Custom Tenure | ✅ Correct. Add: `Custom` is *incoherent* under C1, not merely awkward — an exact-match resolver plus a free-text month field is a control whose success case is "you guessed a published value" |
| Index-domain slider | ✅ Sound. But see §3.6 — the dual control has an unasserted accessibility claim |
| Tenure-dependent payout | ✅ Correctly raised, correctly deferred |
| Rate composition | ✅ Correct, correctly routed to R1 |
| Duplicate rate rows | ✅ Correct, cheap to close |

### 3.2 ⚠ Additional — compounding frequency is hardcoded

`@/utils/maturity.ts` has `COMPOUNDS_PER_YEAR = 4`, derived from six Marketplace
figures in M2.1. That derivation is sound *for those six products*.

It is a **platform-wide constant standing in for a per-bank contract term.**
Indian banks compound quarterly by convention, but not universally, and
cumulative vs payout products often differ within one bank. At 100+ partners
this is not "may break" — it will produce wrong maturity values, silently, for
whichever banks compound monthly or annually.

**Not a T3.2.10 blocker.** It is the highest-priority item for R1, and
`compoundingFrequency` belongs on the product or the rate band.

### 3.3 ⚠ Additional — no day-count convention

`periods = 4 × (tenureMonths / 12)` treats every month as exactly 1/12 of a year.
Fine for whole-month tenures; **materially wrong for short ones**, which is
exactly what §5.1 proposes to introduce. A 7-day deposit computed as 0.23 months
is meaningless.

Actual/365, actual/actual and 30/360 give different answers, and banks specify
which. **This must be decided together with §5.1 — they are one decision.**

### 3.4 Additional — rounding policy is implicit

The engine `Math.round`s the maturity value; the instalment rounds separately.
T3.2.9 already surfaced the visible consequence (₹3,021 × 24 = ₹72,504 against a
stated ₹72,500). Banks specify rounding rules. Currently the platform has a habit
rather than a policy. **Low risk, but it should be a named decision.**

### 3.5 Additional — is the rate card the *booking* rate or the *display* rate?

Marketplace shows one rate per product; Booking now resolves a rate per tenure.
Nothing states whether these are the same quantity. If Marketplace's card rate is
a headline and Booking's is contractual, two screens quote different numbers by
design — and no one has said so. **Ask.**

### 3.6 Additional — the dual-control accessibility claim is asserted, not verified

Chips and slider driving one value is claimed WCAG-compliant (T3.2.3 docs, A-T2).
That is a reasonable reading of 4.1.2, but *two focusable controls reporting the
same value* is unusual enough that it should be validated with a real screen
reader before it ships, not after. The package lists it as a manual check; it
should be listed as a **pre-merge** manual check.

### 3.7 Additional — minimum investment may vary by tenure

`minInvestment` is a product-level field. Banks commonly set higher minimums for
short tenures. If true, the amount validator's bounds become tenure-dependent —
which would mean **T3.2.8's quick-amount filter is also tenure-dependent**, and
that is a change to already-approved work. **Ask now**, because the answer
retroactively affects a shipped task.

## 4. Future Scalability

> Assumption to test: 100+ banks · dynamic rates · senior products ·
> payout-specific pricing · amount slabs · effective dating · API-driven cards.

**Verdict: the current model does not survive.** Not because it is badly built —
it is correct and well-tested for what it models — but because it models *rate as
a function of tenure alone*, and every item on that list adds a dimension.

| Requirement | Survives? | Why not |
|---|---|---|
| 100+ banks | ⚠ | Inline `tenureRates` on every product is a payload and cache problem; rate cards want to be a resource |
| Dynamic rate updates | ❌ | No effective dating, no identity, no way to detect a change (BR-PROD-003) |
| Senior citizen products | ❌ | Rate is not a function of investor profile |
| Payout-specific pricing | ❌ | Rate is not a function of payout — and this would **break `resolveTenureRate`'s signature**, which three call sites depend on |
| Amount slab pricing | ⚠ | Exists in Marketplace, unreachable from Booking; composition order unspecified |
| Effective-dated rates | ❌ | Not modelled |
| API-driven rate cards | ⚠ | Shape is transport-friendly, but has no version, no id, no issued-at |

### 4.1 The recommended change — `RateQuote` instead of `number | null`

The single highest-leverage change, and it is cheap **today** because
`resolveTenureRate` has exactly three call sites:

```
resolveRate(product, criteria) → RateQuote | null

criteria : { tenureDays, amount?, payoutOption?, investorProfile?, asOf? }
RateQuote: { annualRate, compoundingFrequency, bandId,
             effectiveFrom, basis /* day-count */ }
```

Why this shape survives the list above:

- **Every future dimension is a field on `criteria`**, not a new function or a
  changed signature. Senior rates, payout pricing and amount slabs all become
  resolution inputs
- **The answer carries its provenance.** A booking can persist *which band* it
  was quoted, satisfying Doc 19 and making BR-PROD-003 implementable
- **Compounding and day-count travel with the rate**, killing §3.2 and §3.3 at
  the source rather than as global constants
- `calculateReturns` stops taking a bare rate and takes a quote, so it can never
  be handed a rate without knowing how to compound it

**Cost now:** one type, one function rename, three call sites, and the fixture.
**Cost after T3.2.10:** the above plus the tenure control, the slider mapping and
the custom input.

I would rather do this before T3.2.10 than before R1. It is not a large change
and it is on the critical path of every scalability item listed.

## 7. Decision Review — the 7-Day modelling problem

Reviewed for the long-term platform, explicitly not for the demo.

### Option A — days canonical (`tenureDays`)

- ➕ **Days are the atomic unit of a deposit contract.** Banks compute on
  value-date → maturity-date; months are a human summary of a day count
- ➕ **Makes Maturity Date computable** (§2.4) — currently impossible
- ➕ Expresses everything: 7 days, 45 days, 18 months, 10 years
- ➕ Equality is unambiguous — one tenure, one integer
- ➖ Forces the day-count decision (§3.3). *This is a benefit disguised as a
  cost:* the convention is needed regardless and is currently an unexamined
  assumption
- ➖ Migration: `TenureRate`, `InvestmentConfiguration`, draft schema version
  bump, `formatTenure`, the engine's month arithmetic

### Option B — `{ value, unit }`

- ➕ Most expressive on the surface
- ➖ **Modelling error.** It admits three representations of one quantity —
  `{12,'months'}`, `{1,'year'}`, `{365,'days'}` — so equality, sorting,
  deduplication and `Set` membership all break unless every consumer normalises
  first. If every consumer must normalise, the normalised form is the domain
  model and the pair is presentation
- ➖ Display information leaking into the domain
- **Reject.**

### Option C — months only, drop "7 Days"

- ➕ Cheapest; no migration
- ➖ Contradicts the approved artwork and the advertised range
- ➖ Contradicts Founder §5's **"short-term parking"** goal — a named planner use
  case the platform would become unable to serve
- ➖ Leaves Maturity Date uncomputable
- ➖ Defers the same decision to whenever the first sub-month product arrives,
  by which point far more code assumes months

### Option D — months only, drop `Custom`

- Solves a symptom. The unit problem is untouched. **Reject as a standalone.**

### Recommendation — **Option A**, with one addition

Adopt **`tenureDays: number`** as the canonical unit in `TenureRate` and
`InvestmentConfiguration`, and add an optional **`label?: string`** to
`TenureRate` so a bank can present "1 Year" or "7 Days" in its own words.

The label is what makes A strictly better than B: B's only real advantage was
expressing the bank's chosen unit, and a display label delivers that **without**
putting three equal-but-unequal representations into the domain.

Consequences to accept deliberately:

- One draft-schema version bump — bundle with H1 and C2
- `formatTenure` gains a days→display rule; the platform keeps one formatter
- The day-count convention must be chosen (§3.3). **Recommend actual/365 unless
  Finance says otherwise**, and record it as a named decision rather than a
  constant
- `Custom` becomes coherent for the first time: a day or month entry that
  resolves against a card indexed in days, still exact-match, still no invented
  rates

**Optimising for the demo would choose C.** The demo has one 24-month product and
would never notice. That is precisely why C is wrong: the cost of A is at its
lowest today and rises with every screen that assumes months.

## 8. Missing Questions

The package failed to ask these. In rough priority:

1. **What is the maturity date, and what is the value date?** Spec 21b §E
   requires it; nothing models it. Same root cause as C1
2. **What is the day-count convention?** Unexamined assumption in shipped code
3. **How does each bank compound?** A global constant currently answers a
   per-bank question
4. **Is the Marketplace rate the same quantity as the Booking rate?** (§3.5) Two
   screens, one deposit, no stated relationship
5. **Does `minInvestment` vary by tenure?** (§3.7) Would retroactively change
   approved T3.2.8 work
6. **Who owns the rate card's lifecycle** — admin UI, partner sync, or manual?
   Determines whether effective dating is optional or mandatory
7. **What happens to an in-flight draft when the card changes underneath it?**
   Behaviour row 4 handles display; nobody has said whether the user is *told*
8. **Is a rate card per product or per bank?** At 100 banks, sharing matters
9. **What rounding policy do partners require?** (§3.4)
10. **Has the dual chip+slider control been tested with a screen reader?** (§3.6)
    Claimed compliant; unverified

## 9. Sign-off

The readiness package is structurally sound: the integration contract is
correct, the behaviour matrix is thorough, the verification plan is adequate, and
it correctly identified the tenure-unit problem as a blocker before any code was
written. It is approved as a *plan*.

raised and two it did not.

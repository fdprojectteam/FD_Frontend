## 1. The blocking design question — R15

**Nothing in the application navigates to `/compare`.** No nav item, no button,
no link anywhere in `src/`. And under C4 a bare `/compare` renders the empty
state even when the store holds three products, because on that route the URL
*is* the selection.

So R15 is now two questions, and only the first is a design decision:

| | Question | Notes |
|---|---|---|
| **R15a** | What affordance takes a user to the comparison, and where does it live? | The approved Home and Details screens do not appear to show one. Candidates: a bar that appears once ≥ 2 products are selected; a count badge in the top nav; a button in the Details action bar |
| **R15b** | Whatever it is, it must compose `?ids=` from the store | Not a decision — a consequence of C4. A plain `<Link href={ROUTES.compare}>` would open an empty comparison |

**Recommendation for R15b only:** the link target is built by the same pure
module that parses it — `serialiseCompareIds` already exists — so no second
place learns the parameter's name.

**R15a needs your answer before T2.7.3 completes.** It does not block the
journeys: the harness can visit `/compare?ids=…` directly, which is exactly what
L4 does. It blocks only the entry affordance, which can land last in this task
or move to T2.7.4.

## 4. The four journeys

### L4 — cold load performs zero navigations

Load `/compare?ids=fd-001,fd-002,fd-003`. Assert: three columns; the URL is
untouched; `pushCalls + replaceCalls === 0`. This is I7 write-only on the second
route, and the sync's first proof of life — it must populate the store **without
navigating**.

### L6 — Back and Forward across removals

Remove a column, then Back, then Forward. Assert one `push` per removal, and
that each history step changes **both** the URL and the rendered columns. This
is the journey that would have caught B1: under hydrate-once the URL moved and
the columns did not.

### L6b — Back after a removal restores the column *and* the count

The sharper half of L6, kept separate because it is the assertion that fails
loudest if the sync regresses: after Back, the removed product is present again
and the heading reads "Comparing 3 of 4" once more.

### L6c — an over-cap URL settles (R13)

Load `?ids=` with five ids. Assert: four columns; the URL still carries five
(I7 forbids rewriting on load); **zero navigations**; and — the loop guard —
the render count stabilises. Practically: settle, then re-read state and confirm
nothing has moved, since a looping effect never reaches a fixed point.

**Also worth asserting here:** the first user write canonicalises the URL to
four ids, which is the documented over-cap behaviour completing.

Project: FD Investment Platform

Compares: `FD Marketplace_product_desktop_01.png` and `…_mobile_01.png`
against `m2.6-implementation-plan.md` rev 2 and completed tasks T2.6.0–T2.6.2
Status: **Review only. No implementation.**

## Verdict up front

**No — the plan as written would not reproduce the approved screens exactly.**
The section inventory, ordering, and content are right. Eight gaps exist, and
three of them would produce visibly wrong output if T2.6.3 started today:

- the desktop content column is **much narrower** than the page container the
  plan implies (G-UI-3);
- the trust badges differ in **content**, not just layout, between breakpoints
  (G-UI-1);
- the product header **restacks** on mobile (G-UI-2).

The plan's §0 claim — *"Desktop and mobile differ only in layout: the key-info
grid goes 4-up → 2-up, the calculator stacks with the button on its own row,
and the action bar is full-width and sticky"* — is incomplete. Details below.

## 3. Layout verification

### Desktop

Measured from the approved image, in shell-relative terms:

- shell content spans the full frame (nav logo to avatar);
- **every content section sits in a narrower, centred column — roughly 60–62%
  of the shell width.** Header card, badges, key info, calculator, benefits,
  eligibility, and accordions all share the same left and right edges;
- the **action bar does not.** Its divider and buttons span the **full shell
  width**, with the buttons right-aligned to the shell edge.

So the screen has **two widths**: a reading column for content, full bleed for
the action bar. The plan specifies neither.

### Mobile

Single column, full width inside the device frame. Restacking as inventoried
above: header stacks, key info 2 × 2, Calculate on its own row, results split,
benefits wrap.

### Sticky vs static

**Mobile** — clearly pinned: a divider sits directly above the bar at the frame
bottom, content runs behind/above it, and no footer appears. Consistent with
D7.

**Desktop — this is where D7 needs re-examination.** Looking closely, the
desktop screen shows ~145 px of empty space between the last accordion and the
divider, the bar flush with the bottom of the frame, and **no footer**. That is
at least as consistent with a viewport-pinned bar as with a static one at the
end of content. D7 chose "sticky on mobile, static on desktop" partly on my
earlier reading of these images; the closer look does not support that
confidently. See G-UI-6.

### Responsive changes required

| Change | Breakpoint |
|---|---|
| Header: two-column → stacked; "per annum" → "p.a." inline | below `md` |
| Trust badges: 3 → 2, label shortened | below `md` |
| Key info: 4-up → 2-up | below `md` |
| Calculator: button inline → own row | below `md` |
| Results: one row → two rows | below `md` |
| Benefits: single row → wrap | automatic |
| Action bar: right-aligned pair → side-by-side pair; "Add to Compare" → "Compare" | below `md` |

## 5. Pixel-faithfulness audit

### Differences from the approved design that the plan would produce

| # | Gap | Severity |
|---|---|---|
| **G-UI-1** | **Trust badges differ in content, not layout.** Desktop shows three (RBI Regulated, ₹5L DICGC Insured, AAA Rating); mobile shows two, and the DICGC label loses its "₹5L". The plan treats the row as identical at both breakpoints. This needs a decision: hide the third below `md` and shorten the label, or show all three. Hiding content responsively also has an a11y consequence — it must be `hidden`, not visually clipped, or a screen-reader user gets a badge the design withheld | **High** |
| **G-UI-2** | **Product header restacks.** Desktop is two columns with the rate right-aligned and "per annum" beneath; mobile stacks and renders "p.a." inline. The plan lists no header responsive change | **High** |
| **G-UI-3** | **Desktop content column is ~60–62% of the shell width, centred** — much narrower than `container-page`, which every other Marketplace screen uses at full width. Building this with the standard container produces a visibly different screen | **High** |
| **G-UI-4** | **The action bar is full-bleed while content is narrow.** Two widths on one screen; the plan implies one | Medium |
| **G-UI-5** | **Action bar label differs by breakpoint:** "Add to Compare" desktop, "Compare" mobile | Low |
| **G-UI-6** | **D7 may be wrong for desktop** — see §3. The approved desktop screen is ambiguous and arguably favours a pinned bar | Medium |
| **G-UI-7** | **Neither approved screen shows the footer**, yet `PublicLayout` renders one on this route. Either the prototype omits it for framing, or the details route is intended to suppress it | Medium |
| **G-UI-8** | **Section headings are smaller than Home's.** "Key information", "Benefits", "Eligibility" render as compact bold labels, not the larger `SectionHeading` treatment used on Home. Reusing `SectionHeading` unchanged would oversize them | Low |

### Assumptions made because the design is ambiguous

1. **Heading hierarchy.** The screens show no explicit `h1`. The bank name in
   the header card is the most prominent text and is the natural `h1`; K7
   asserts exactly one. Assumed, not shown.
2. **Tenure field styling.** D2 = A makes it read-only. The design draws it
   identically to the editable Amount field, so it is assumed to keep the input
   box and gain `readOnly`/`aria-readonly` rather than a disabled appearance —
   otherwise it would look different from the approved screen.
3. **Accordion default state.** All three render collapsed; assumed to be the
   default, with no "expand all".
4. **Results arrows.** Assumed decorative. If they are meant to convey the
   progression semantically, they need text alternatives.
5. **Eligibility panel** is assumed to be a muted surface panel, not a `Card` —
   it has no border or shadow in either screen.

### Requires design confirmation before T2.6.3

- **G-UI-1** — is the third badge dropped on mobile deliberately, and is the
  shortened DICGC label intentional?
- **G-UI-3 / G-UI-4** — the exact content measure, and whether the action bar is
  deliberately full-bleed.
- **G-UI-6** — is the desktop action bar sticky?
- **G-UI-7** — should the footer render on this route?
- **G-UI-5** — is the shortened mobile button label intentional?
- The 404 copy written in T2.6.2, which has no approved screen at all.

## 6. Final verdict

**The plan does not yet reproduce the approved UI exactly.** The inventory,
order, and content are correct and nothing is missing or invented — the gaps
are all *fidelity* gaps, and they are concentrated in responsive behaviour and
page measure, which rev 2 summarises in a single sentence that turns out to be
incomplete.

**Minimal changes before T2.6.3:**

1. Amend plan §0 to replace the "differ only in layout" sentence with the
   responsive table in §3 above — including the trust-badge **content**
   difference and the header restack.
2. Add the desktop content measure and the full-bleed action bar to §2.6 as
   explicit layout requirements.
3. Get answers on G-UI-1, G-UI-3/4, G-UI-6, G-UI-7, G-UI-5.
4. Note in §2.3 that `SectionHeading` is **not** reused for this screen's
   sub-headings (G-UI-8), or confirm it is with a smaller variant.

None of this changes the architecture, the task breakdown, the decisions
D1–D7, or the verification plan. T2.6.3 (screen shell) touches only sections 2
and the loading/error states, so it could proceed while G-UI-1/2/5 are
confirmed — but **G-UI-3, G-UI-4, G-UI-6, and G-UI-7 all bind the shell**, and
those are exactly what T2.6.3 builds. My recommendation is to settle them
first.

# M2.5 — Final Architecture Audit

Project: FD Investment Platform
Date: 2026-07-31
Revision: 2 — F3 decided; invariant I8 added and verified
Scope: the Marketplace module after M2.5, judged against
`marketplace-url-state.md` (I1–I8) and the M2.5 architecture requirements A1–A6
Verdict: **Architecturally sound, no open questions.** Every invariant is
enforced by construction and verified by an executable probe. One carried debt
is due in M2.6 (D1).

## 1. Invariants

| # | Invariant | Enforcement | Result |

| I2 | Hero, recommendations, and featured content independent of the listing | Hero query is a literal; asserted unchanged across a full filter journey | **PASS** |
| I2a | `HomeScreen` is the sole owner of URL mutations | Only `HomeScreen` calls the setters; the read seam exposes none | **PASS** |
| I3 | Presentation components stay presentation-only | No section component imports a hook, service, repository, or the router | **PASS** |
| I4 | M2.5 extends the architecture, it does not fork it | Filters use the same writer, the same key factory, the same fetch path | **PASS** |
| I5 | One query key per purpose | Every `queryKey` comes from `marketplaceKeys`; banks fetched once | **PASS** |
| I6 | Only domain state belongs in the URL | Typing performs zero writes; facet open/closed state is local | **PASS** |
| I7 | Canonical URLs, write-only | Canonical serialisation on write; zero writes on load across five URLs | **PASS** |
| I8 | Intent pushes, correction replaces | One `push` and one `replace` in the module, both inside `navigate()`; every setter commits, only the clamp corrects; asserted statically and in the journey | **PASS** |

### How I7 ended up stronger than specified

The approved rule was "defaults are omitted on write". The first implementation
satisfied that key-by-key and still failed two rows of the approved canonical
table, because a redundant `sort=interestRate&order=desc` elsewhere in the URL
was never the key being patched.

Writes now serialise from parsed values. One state therefore has one URL
including parameter *order*, and — the part worth keeping — **no parameter
outside the approved eight can survive a write**. Decision D2's closed set is
enforced by the code rather than by reviewer discipline.

## 3. Layering

```
app  →  modules/marketplace  →  components  →  hooks  →  services  →  api
                              ↘  utils (pure)
```

Executed as `npm run verify boundaries` (15 checks):

- `axios` is imported only by `services/api/api-client.ts` and `api-error.ts`
- `@/mocks` is imported only by `app/providers.tsx` (the approved MSW seat)
- `process.env` is read only by `config/env.ts`
- no module imports a sibling module
- no file crosses a disallowed element boundary
- the five new M2.5 files import nothing from services, repositories, or the
  router

The new `utils/` modules deserve a note: `url-values.ts`, `list-params.ts`, and
`filter-labels.ts` are pure and depend only on constants and types. That is what
made them assertable without React, and it is why the URL contract is now
covered by 40 direct assertions rather than inferred from rendering.

## 4. Component design

| Component | Owns | Receives | New primitives |
|---|---|---|---|
| `FilterBar` | which facet is open (transient UI) | values, banks, `onChange` | none — built on the frozen `Chip` |
| `ActiveFilters` | nothing | descriptors, `onRemove`, `onClearAll` | none |
| `ProductGridSection` | nothing | a `toolbar` slot + listing props | none |

**The disclosure pattern is the one design judgement made here.** The approved
screen shows four collapsed facet chips and no open state. Four facets with six
options each cannot be a plain toggle, and a popover or menu would have been a
new primitive — explicitly out of scope. Each chip is therefore a disclosure
that reveals its options as a row of `Chip`s beneath the row: the collapsed
state is pixel-faithful to the approved design, nothing new was invented, and
the whole interaction is keyboard-operable. If the design intent was a floating
menu, that is a design decision to confirm, not something to assume.

**One recorded a11y tension.** `Chip` always emits `aria-pressed`, so the
removable pills announce a pressed state as well as their "Remove filter: …"
name. Resolving it cleanly needs an `action` variant on `Chip` — a
component-library change, not a Marketplace one. Recorded rather than worked
around.

## 5. Resolved architectural question — F3, now invariant I8

The original rule 5 mandated `router.replace()` for every write. `replace`
overwrites the current history entry, so no filter interaction ever created one:
Back left the site instead of undoing a refinement, contradicting the M2.5
definition of done.

**Approved and implemented:** intent pushes, correction replaces.

```
navigate(patch, mode)                    the module's only navigation
  ├─ commit(patch)  → router.push        search · filters · sort · page · clear
  └─ correct(patch) → router.replace     canonicalisation · normalisation · clamp
```

Rule 5 was amended from "one `router.replace()` per interaction" to "one
*navigation* per interaction". That is the smallest change that resolves the
conflict: the invariant always cared about *how many* navigations an interaction
performs, and it now leaves *which kind* to I8.

Three properties make this hold up rather than becoming a per-control judgement
call:

- **The rule is a question, not a list.** *Did the user ask for this URL?* If
  yes it is a place they can return to. If the application produced it on its
  own it must not be, because Back would land on a state already known to be
  wrong and the correction would fire again.
- **There is exactly one `push` and one `replace` in the module**, both inside
  `navigate()`. The probe asserts the counts and their location, so a future
  control cannot quietly introduce a third navigation of either kind.
- **The distinction is visible at the call site.** `setPage` and `correctPage`
  build the identical patch and differ only in intent; naming them apart is what
  keeps the clamp from silently becoming a history entry during a later
  refactor.

Cost, stated plainly: filter-heavy sessions now produce more history entries
than before. That is the intended trade — on a screen whose purpose is narrowing
options, Back undoing the last refinement is the behaviour users expect, and it
is what the DoD asked for.

## 7. Readiness for M2.6

M2.5 leaves the architecture in a better state than it found it:

- the URL contract is pure, isolated, and directly testable;
- the API translation has exactly one call site, so a future filter cannot
  silently fail to reach the backend;
- the parameter set is closed by construction;
- the project has a committed verification harness — M2.4's risk R6 is closed,
  and it has already paid for itself by finding two real defects.

- navigation intent is now explicit, so M2.6's route transition inherits a rule
  rather than a habit: opening a product is intent and pushes; any correction on
  the details route replaces.

**One thing should be settled before M2.6 implementation starts:** **D1**, the
`ProductDetails` cache contract. M2.6 is where a `ProductSummary` stored under a
`ProductDetails` key stops being a type-level inaccuracy and starts being a
rendering one. It does not block planning.

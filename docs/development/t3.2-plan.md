## 0. Founder Note compliance — re-verification

### 0.1 Where the Note and the approved UI disagree ⚠ blocking

Founder Note §7, row *Booking*:

> **Must avoid** — Long form-heavy process at the beginning.
> **Must deliver** — **Four clear steps: Details, Nominee, Review, Pay & Confirm.**
> Use progressive disclosure.

The approved UI draws **eight** steps in the stepper, the Screen Inventory
(doc 20) specifies eight, and `BOOKING_STEPS` shipped with eight in T3.1.

Priority 1 outranks Priority 2 and Priority 3, so the Note governs. It cannot be
satisfied by relabelling; it changes what the user is shown they must complete.
**This blocks T3.2**, because the screen's own stepper is one of the artefacts in
dispute and because "Details" under a four-step model is not the same screen as
"Investment Details" under an eight-step one.

**DECIDED 2026-08-06 — four phases in the stepper, eight routes underneath.**
The user is told they face four steps; the eight screens remain as routes, with
sub-steps hidden from the indicator. Nothing shipped is retired.

This is the cheapest reconciliation in code and the one that keeps every
approved screen intact. It is recorded honestly that it satisfies the Note's
*labelling* more fully than its *intent* — the user still completes eight
screens. The Note's lightness requirement therefore falls on the screens
themselves (D9, D11 and the out-of-scope list) rather than on the count.

**Implementation shape — no `Stepper` change required.**

```
BOOKING_PHASES  = [details, nominee, review, pay-confirm]   // rendered
BOOKING_STEPS   = [overview … success]                      // routed, unchanged
resolvePhase(stepId) → phaseId
```

`Stepper` already takes `steps` + `currentStepId`, so it receives the four
phases and a resolved phase id. The component is untouched; only what it is fed
changes.

| Phase (rendered) | Routes (unchanged) |
|---|---|
| **1 · Details** | `overview`, `investment` |
| **2 · Nominee** | `nominee` |
| **3 · Review** | `review` |
| **4 · Pay & Confirm** | `bank-account`, `payment`, `processing` |
| *(all complete)* | `success` |

`processing` resolves to Pay & Confirm because the phase is still in flight;
`success` resolves to every phase complete. Neither is a fifth phase.

**Touches one shipped file.** `BookingOverviewScreen` (T3.1) currently passes
`BOOKING_STEPS` and `currentStepId="overview"`; it changes to phases and a
resolved id. That is a Booking file, not a Marketplace one, so Priority 4's
no-touch rule does not apply — but it is called out rather than slipped in.

## 1. Scope

### What this screen is

Spec 21b §1: *the only screen where users make investment-related decisions.* It
must answer "Am I investing the right amount, for the right tenure, with the
right payout option?" — and it is the first Booking screen that **collects**
anything, which is why the module's state contract has to be settled here rather
than deferred to Nominee.

| | |
|---|---|

| Panels | Configured Investment Summary (right rail), Important Information |

### 2.2 The right rail is *configured*, not static — the key reading

Overview's summary lists the product's **capabilities**: `Tenure Options
7 Days – 10 Years`, `Interest Payout Options  Monthly, Quarterly, Cumulative, At
Maturity` — nine rows, no bank header.

Screen 2's summary lists the user's **choices**: `Tenure  24 Months`,
`Interest Payout  At Maturity` — seven rows, with a bank header block.

So the same panel serves two different row models, and on this screen it is
**live**: changing tenure or payout must update the rail, not only the Estimated
Returns strip. This is a second derivation of the same object, not a second
component — see §4.

### 2.3 Responsive

The approved artwork is desktop-only, so the breakpoints below follow the
patterns already established in this codebase rather than being invented:

- **`< md`** — one column, source order preserved: controls first, then the
  configured summary, then Important Information, then the action row. Same
  choice as `BookingOverviewScreen`, so the reading sequence matches at both
  widths
- **Quick-select chips** sit under the amount input rather than beside it
- **Tenure chips** wrap; they do **not** scroll horizontally — a hidden tenure
  is a tenure the user cannot know is on offer
- **Payout radio cards** stack to full width
- **Estimated Returns** goes 4-across → 2×2 below `md`. The four cells are of
  equal weight in the artwork, so no cell is promoted
- **Touch targets** — 44px below `md`, 40px from `md`, per the standing UX-1-C1
  rule in `current-task.md`

### 2.4 Accessibility

- Tenure chips are a **single-select group**, so `role="radiogroup"` with
  `aria-checked` — not eight independent `aria-pressed` toggles. `Chip` exposes
  `aria-pressed` today; T3.2 adds a group wrapper rather than changing `Chip`
- The **slider and the chips are one value in two presentations**. Hiding the
  slider from assistive technology was considered and rejected — a focusable
  control that screen readers cannot see is worse than two controls that agree.
  Per D7 the *chip group* is the labelled control, and the slider stays
  focusable with the native `input[type=range]` semantics plus
  `aria-label="Tenure in months"`. Both announce the same value; neither is
  hidden (WCAG 4.1.2)
- **Payout cards** are a native `<fieldset>` + `<legend>` + `input[type=radio]`,
  visually restyled. No ARIA needed
- **Estimated Returns** is an `aria-live="polite"` region so a recalculation is
  announced once, debounced, rather than on every keystroke (§18 performance)
- Amount errors are `role="alert"`, referenced by `aria-describedby`, and the
  Continue button is `aria-disabled` rather than `disabled` so it stays
  focusable and can explain why it will not proceed
- Reduced motion honoured on the slider fill and the recalculation settle

## 3. The Booking state contract

This is the part of T3.2 that outlives T3.2, so it is decided from the
documents rather than from convenience.

### 3.1 What the documents already decide

`docs/engineering/09_State Management Strategy.md` is unusually specific here:

- §3 classifies **Booking → "Booking Step"** as **Feature State**
- §6 names Booking's feature state explicitly: **"Current Step · Entered Details
  · Confirmation Status"**
- §4 assigns feature state to **"Custom Hooks / Context (only if needed)"** and
  reserves **Zustand for global application state**
- §5 forbids module data in the global store
- §10 forbids storing derived values: *"Instead of storing Maturity Amount,
  store Deposit Amount, Interest Rate, Tenure, then calculate when needed"*

Booking's own FRS adds the persistence requirement:

- **FR-CONF-002** — preserve entered configuration across navigation, refreshes,
  and recoverable interruptions
- **FR-SYS-001** — restore interrupted sessions
- **FR-SYS-002** — auto-save without a manual save action
- **BR-SYS-001**, **BR-REC-002** — progress preserved automatically; local
  progress preserved through network interruption

### 3.2 Decision — module-scoped context, session-persisted

**`BookingDraftProvider` + `useBookingDraft()`**, in
`src/modules/booking/hooks/use-booking-draft.tsx`, seated in a new
`src/app/(public)/booking/[productId]/layout.tsx` so the draft survives
navigation *between* steps and dies when the product changes.

This is not a new pattern. `useCompareSelection` is the Marketplace precedent:
module-scoped context, ids only, no dependency added. Booking gets the same
shape for the same documented reason.

**Zustand is not used.** Not because it is unavailable — it is in the CLAUDE.md
stack and is not currently installed — but because Document 09 §4/§5 place the
booking draft in the feature tier, and §5 forbids putting module data in the
global store. Installing a global-state library to hold feature state would be
architectural drift dressed as stack compliance.

### 3.3 What the draft holds

```
BookingDraft {
  productId: string
  investment: {
    amount: number | null
    tenureMonths: number | null
    payoutOption: PayoutOptionId | null
  } | null
  // steps 3–8 add sibling keys; nothing here is step-2 specific
  furthestStep: BookingStepId    // for step guards, D3
  updatedAt: number              // for expiry, D2
}
```

**No maturity amount, no interest, no rate.** Document 09 §10 and Document 19
§5 ("avoid storing values that can be recalculated") both forbid it, and
BR-INV-004 requires recalculation on every change — a cached figure is precisely
the stale calculation that rule exists to prevent. Everything derived is
computed in a `useMemo` from `(amount, tenureMonths, payoutOption, deposit)`.

**The current step is not in the draft**, despite Document 09 §6 naming it.
The route already says which step the user is on, and a second copy is the
"multiple copies of the same state" §2 forbids. `furthestStep` is a different
fact — the high-water mark — and that one *is* state.

### 3.4 Persistence — `sessionStorage`, versioned, field-scoped

| | |
|---|---|
| Medium | `sessionStorage` |
| Key | `fd:booking-draft:v1:<productId>` |
| Write | on change, coalesced through `requestAnimationFrame` |
| Read | once, on provider mount, behind a schema parse |
| Expiry | `updatedAt` older than 24h is discarded on read |
| Clear | on reaching Success; on a product change; on an explicit Cancel |

**Why `sessionStorage` and not `localStorage`.** Document 19 classifies session
information as *Operational Data* with shorter retention. A pre-payment
investment draft is exactly that. `localStorage` would leave a stranger's
deposit amount on a shared machine indefinitely, which no requirement asks for
and BR-REC-001 (restore *after re-authentication*) implicitly argues against.

**Why a version prefix and a schema parse.** Stored shapes outlive the code that
wrote them. A `v1` key plus a Zod parse on read means a future shape change
fails closed to an empty draft instead of hydrating a half-valid object into a
financial form.

**Field-scoped persistence — the policy that matters later.** T3.2's three
fields (amount, tenure, payout) carry no PII and are safe to persist. Screens 3
and 4 collect **PAN, date of birth and bank account numbers**, which Document 19
§Security names as sensitive and requires to be protected at rest. Proposed
policy, to be confirmed when T3.3 is planned: **the draft persists identifiers
of saved entities (`nomineeId`, `bankAccountId`), never raw sensitive values.**
Recorded here as OQ-8 so it is not discovered mid-implementation.

### 3.5 Server state stays with TanStack Query

The draft is client state only. When `GET /bookings/{id}` and the product
configuration endpoint exist, they are queries — not draft fields — exactly as
`useProduct` is on the Marketplace side. The draft never caches a server
response.

## 5. Decisions

### D1 — Tenure is selectable, so the rate must be a function of tenure ⚠ blocking

The approved screen offers seven tenures against a single quoted rate of 7.25%,
and spec 21b §9 asks the platform to say *"Investing for one more year unlocks a
higher interest rate."* Neither is possible today: the domain has one rate per
product, and M2.6 decision D2 fixed tenure on the Marketplace calculator for
precisely this reason — *"a fixed deposit is a rate-for-tenure contract: this
product has one rate and one tenure, so offering other tenures would quote a
return the user cannot obtain."*

Selecting a tenure on this screen while holding the rate constant would ship the
exact defect M2.6 refused to ship, on the screen where the user commits money.

- **Option A (recommended)** — add `tenureRates: { tenureMonths, annualRate }[]`
  to `DepositTerms` and the fixture. Booking already owns its own types, so
  Marketplace is untouched. Rate becomes a pure lookup, `resolveTenureRate`,
  falling back to the headline rate when a tenure is unlisted. Makes §9's
  suggestions truthful when they are approved later
- **Option B** — one rate for all tenures. Cheap, and quotes an unobtainable
  return for six of the seven tenures
- **Option C** — tenure is display-only, as on the Marketplace calculator.
  Contradicts the approved screen, which shows tenure as the primary control

**Recommendation: A.** Requires the client to supply, or approve, a rate card.

### D2 — Draft state model *(proposed: §3)*

Module context, `sessionStorage`, versioned key, no derived values, field-scoped
sensitivity policy. Grounded in Document 09 §3–§6 and §10; Document 19
Operational Data; FR-CONF-002, FR-SYS-001, FR-SYS-002.

### D3 — Step guards

`/investment` is **deep-linkable without a draft**: Overview collects nothing,
so arriving here directly loses no information — the screen seeds from the
product and the user configures from scratch. Steps 3+ will guard on
`furthestStep` and redirect to the earliest incomplete step (BR-BOOK-002:
skipping states is not permitted). The guard helper ships in T3.2 so step 3 does
not invent its own.

### D4 — Client calculation, server authority

Spec §18 asks for client-side calculation for non-authoritative previews with
server validation before proceeding; §19 says never trust client calculations.
Both are satisfied by: compute locally for the live preview, label it an
estimate (the approved footnote does), and revalidate server-side on Continue.
The revalidation is a **seam** in T3.2 — `bookingService.validateConfiguration`,
resolving optimistically — because no endpoint exists. Same posture T3.1 took
with the fixture, and for the same reason.

**Consequence:** **BR-PROD-003** (rate changed mid-booking → notify, recalculate,
require confirmation) and **BR-PROD-004** (product withdrawn mid-booking) cannot
be implemented in T3.2. They are recorded against the endpoint, not silently
skipped.

### D5 — Payout option changes what "maturity" means ⚠ blocking

`At Maturity` / `Cumulative` compounds; `Monthly` / `Quarterly` pay interest out
as it accrues, so the maturity amount is the principal. The approved strip shows
all four cells for the selected `At Maturity` option and the spec does not
define the non-cumulative case.

- **Option A (recommended)** — non-cumulative payouts use simple interest on the
  principal at the selected frequency; `Maturity Amount = Principal`;
  `Total Interest` becomes total interest paid over the term, with the strip
  gaining a per-instalment line (e.g. *"₹3,020 / month"*) — a copy change, not a
  layout change
- **Option B** — show the same compounded figures regardless of payout. Simpler,
  and wrong: it tells a monthly-payout investor they will receive ₹5,66,478 at
  maturity when they will receive ₹5,00,000

**Recommendation: A.** Needs confirmation of the per-instalment line.

### D6 — Quick Select semantics ⚠ blocking

The approved chips read `+ ₹1L`, `+ ₹5L`, `+ ₹10L` — the `+` says *add*. Spec
21b §B lists `₹50K / ₹1L / ₹2L / ₹5L / ₹10L` as *quick amount* chips — absolute
values. The artwork also shows `+ ₹5L` in the **selected** treatment while the
amount reads ₹5,00,000, which is what an *absolute* chip would look like after
being pressed, and is not a state an additive chip should have at all.

Three readings, and no default is safe on a money field:

- **Option A** — additive. `+ ₹5L` adds ₹5,00,000 to the current amount, clamped
  to the maximum. The selected styling becomes a transient press state
- **Option B** — absolute. Chips set the amount; selection reflects a match.
  Matches the spec and explains the artwork's selected state, but contradicts
  the `+` in the labels
- **Option C** — additive with the label rendered as pressed only while active

**No recommendation.** This one needs design's answer, not engineering's guess.

### D7 — Tenure: chips + slider are one value

Two presentations, one state — the same discipline M2.8 applied to the
comparison table and cards. The chips are the labelled control
(`role="radiogroup"`); the slider is a second input on the same value with its
own `aria-label`. Moving either moves the other.

The slider's domain is the product's tenure range (`7 Days – 10 Years` in the
fixture), stepped in months, with the preset chips as landmarks. `Custom`
reveals an **inline month field** constrained to that range — not a dialog and
not a date picker: the value is a duration, and a calendar would ask the user to
compute one.

### D8 — Route and the T3.1 seam

`/booking/[productId]/investment`, a sibling of `/overview` under the same
product segment, as `ROUTES.bookingOverview`'s docstring anticipated. Adds
`ROUTES.bookingInvestment(productId)`. Overview's `handleContinue` — currently
an empty function with a comment naming T3.2 — is wired here, closing the seam.

Route group stays `(public)`, following T3.1's documented deviation. The
approved artwork shows an authenticated sidebar shell that does not exist;
building it is a navigation-architecture task, and inventing it here would be
the redesign the instruction forbids.

### D9 — Forms: Zod + controlled state, not React Hook Form (yet)

Document 09 §9 says forms use React Hook Form and names Booking. RHF is not
installed, and T2.6.5 deliberately built the Marketplace calculator with Zod and
local state instead.

This screen is three controls: one numeric input and two single-select groups.
There are no text fields, no async submit and no field array — the cases RHF
exists for. **T3.2 follows the T2.6.5 precedent; T3.3 (Nominee) introduces RHF**,
where a real form with a repeating nominee array actually needs it. Recorded so
that Document 09 §9 is honoured on schedule rather than quietly dropped.

Founder §7 *"must avoid: long form-heavy process"* reinforces this: the lightest
thing that validates three fields is the right thing.

### D10 — Canonical maturity formula lives at platform level; Marketplace untouched

Recorded in §0.3 and §4.3. Adds `@/utils/maturity.ts` and
`MaturityInput`/`MaturityResult` in `@/types/finance.ts`. Marketplace keeps its
own copy until explicitly instructed otherwise. A cross-implementation unit
assertion prevents silent drift.

### D11 — Confirm-and-adjust, not configure-from-blank ⚠ depends on the planner

Founder §3 corrects the product from *"select bank → enter amount → pay"* to
*"tell us your goal → get a safe and suitable FD structure → understand why →
book with confidence"*, and §7 requires the booking flow to stay lightweight
because **value is established before booking begins**.

Under that direction this screen's three fields should arrive **pre-filled from
the recommended plan** — amount, tenure and payout already chosen, with the
reason shown and adjustment allowed. It stops being a form and becomes a
confirmation the user may override.

The goal-led planner does not exist. So:

- **T3.2 builds the screen to accept a pre-filled configuration** — the draft is
  seeded from an injected `recommendedConfiguration`, defaulting to the
  product's own minimum when none is supplied. That is one optional prop and a
  fallback, not a speculative feature
- **The reason panel is not built** until there is a recommendation to explain.
  Building an explanation of a decision nothing made would be inventing product
  behaviour

This keeps the screen correct today and correct after the planner lands, without
guessing what the planner will produce. See OQ-11.

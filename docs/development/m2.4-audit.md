## C0 — Marketplace Home is unreachable *(Severity 1, OPEN)*

**Observed.** A production build emits three routes. `/` is 123 B and its
prerendered `index.html` contains "Phase 0 — Platform Foundation". The
Marketplace hero string never appears in any build artefact.

```
Route (app)                     Size    First Load JS
┌ ○ /                          123 B          103 kB     ← Phase 0 placeholder
├ ○ /_not-found                993 B          104 kB
└ ○ /gallery                  45.7 kB         161 kB
```

`app-paths-manifest.json` lists **both** `/page` and `/(public)/page`. Two
files resolve to `/`:

- `src/app/page.tsx` — the Phase 0 placeholder, whose own docblock reads
  *"Replaced by Marketplace Home in Phase 2"*
- `src/app/(public)/page.tsx` — Marketplace Home

Next resolves the conflict silently in favour of the root file. Removing
`src/app/page.tsx` changes `/` to 10.2 kB / 195 kB — Marketplace Home, inside
the public shell.

**Root cause.** The Phase 0 placeholder was never retired when M2.3 landed
Marketplace Home. Nothing in the toolchain flags it: the build succeeds, types
pass, lint passes.

**Architectural impact.** Everything M2.3 and M2.4 delivered is dead code in a
production build. The public shell — top navigation, footer, mobile tab bar,
skip link — is also absent from `/`, because the placeholder sits outside the
`(public)` group and renders its own `<main>`. This is why the browser-audit
items in the M2.4 brief cannot have been verified against the real route.

**Fix.** Delete `src/app/page.tsx`. I did not apply this — deleting a file
needs your approval and it was declined during the audit. Three options:

1. **Delete it** (recommended). Its docblock already declares this the
   intended lifecycle, and the Phase 0 token check is reproducible at
   `/gallery`.
2. **Relocate it** to a non-conflicting path such as
   `src/app/(public)/foundation/page.tsx` if the token proof is still wanted
   as a live page. Still requires removing the original file.
3. **Leave it** — Marketplace Home stays unreachable and M2.5 would be built
   on a page no user can load.

Until this is resolved, no browser-level verification of M2.4 is meaningful.

## C1 — Infinite render loop in `SearchBar` *(Severity 1, fixed)*

**Reproduced** under React 19.1.0 + jsdom with the exact hook and component
code. One parent re-render produced 200+ renders and three
`Maximum update depth exceeded` errors before hitting the harness cap.

```
after mount               -> renders: 1   effects: 1
after 1 parent re-render  -> renders: 202 effects: 200
Maximum-update-depth errors: 3
>>> INFINITE RENDER LOOP CONFIRMED
```

**Root cause.** `useMarketplaceSearchParams` narrowed the memoised URL state
by constructing a new object literal on every render:

```ts
return { values: { q: values.q, amount: values.amount, tenure: values.tenure }, commit: setSearch };
```

`SearchBar` then synchronised its draft with `useEffect(() => setDraft(values), [values])`.
Because `values` changed identity every render, the effect re-ran every commit
and set state with a fresh object each time, which never satisfies React's
`Object.is` bail-out.

At mount the loop is dormant — the effect passes back the very object already
held in state, so React bails out. It arms on the **first parent re-render**,
which on this page is guaranteed: `HomeScreen` re-renders on every transition
of its three queries. The page becomes unresponsive during initial data load.

**Architectural impact.** The selector pattern in `marketplace-url-state.md`
is sound, but a selector must be *identity-stable*, not merely value-correct.
Narrowing state is only safe if the narrowed value changes identity exactly
when its contents change. M2.5 adds `setFilters` and more selectors over this
same hook; the same defect would have been reproduced in each.

**Fix.** `useMarketplaceSearchParams` now memoises both the projection (on the
three primitives) and its return object. `SearchBar`'s sync effect keys on the
primitives rather than the containing object, so it stays correct even if the
hook regresses.

**Re-verified:** 12 renders across 1 mount + 10 parent updates, 1 effect run,
0 errors.

## C2 — `useSearchParams()` outside a Suspense boundary *(Severity 2, fixed)*

**Root cause.** M2.3 wrapped `SearchBar` in Suspense with this rationale:

> *Isolating it here keeps the rest of Home statically rendered.*

M2.4 made `HomeScreen` itself call `useMarketplaceUrlState()` →
`useSearchParams()` at its top level. From Next's source
(`client/components/navigation.js`), `useSearchParams()` throws
`BailoutToCSRError` during any prerender. `HomeScreen` now bails out *before*
the inner boundary is reached, so the boundary protected nothing and its
comment had become false.

**Verified counterfactually.** With Marketplace Home genuinely resolving to
`/` and no boundary above it:

```
⨯ useSearchParams() should be wrapped in a suspense boundary at page "/".
Error occurred prerendering page "/".
Export encountered an error on /(public)/page: /, exiting the build.
BUILD_EXIT=1
```

With the boundary at the route entry point: `BUILD_EXIT=0`, `/` prerenders.
This defect is currently *masked* by C0 — `(public)/page.tsx` is never
prerendered, so the build passes. Fixing C0 alone would have broken the build.

**Fix.** The boundary moved to `src/app/(public)/page.tsx`, above every
URL-reading component. The redundant inner boundary was removed.

**One consequence to note.** The fallback is `null`, so the prerendered HTML
contains the shell and an empty `<main>`; hero copy and the `<h1>` are
client-rendered. A visible full-page skeleton would be new UI and needs
design approval, so I did not invent one. Flagging it as an SEO and
first-paint decision for M2.5.

## A3 — I2a violated: `SearchBar` writes the URL *(Severity 2, documented)*

I2a states that only `HomeScreen` calls the URL setters and that section
components receive callbacks as props. `SearchBar` calls
`useMarketplaceSearchParams().commit`, which is `setSearch` — a setter.

Every other section component is clean. A per-component hook scan shows
`HomeScreen` and `SearchBar` as the only two hook owners on the page.

**Impact.** Low today: both hooks read the same `useSearchParams()` context, so
they observe the same snapshot. It matters in M2.5, when filters add a third
writer — this is precisely the clobbering class the invariant exists to
prevent, and it is currently unenforceable by inspection.

**Recommended fix (needs approval — changes a prop contract).** Make
`SearchBar` presentation-only: `HomeScreen` passes `values` and
`onSearchSubmit`. `useMarketplaceSearchParams` then either disappears or
becomes read-only.

## A4 — I1 violated: pagination state comes from the server *(Severity 2, documented)*

`ProductGridSection` receives `currentPage={meta.page}` — the echo from the
API response — while the URL is the declared single source of truth.

With `keepPreviousData`, `meta` is the *previous* page's meta while a new page
loads. So after clicking page 3, `aria-current="page"` and the active
highlight stay on page 2 until the response lands. On a slow connection the
pager appears not to respond, and screen readers announce a stale current
page.

**Recommended fix (needs approval).** Drive `currentPage` from
`values.page`. `totalPages` legitimately stays server-owned.

## M5 — Focus does not move for cached pages *(Severity 3, fixed)*

**Reproduced** against a real `QueryClient` with the project's 60 s
`staleTime`:

```
navigation      requests  focus BEFORE fix   focus AFTER fix
page 1 -> 2       1         moves              moves
page 2 -> 3       1         moves              moves
page 3 -> 2       0         DOES NOT MOVE      moves
page 2 -> 1       0         DOES NOT MOVE      moves
```

**Root cause.** The effect keyed on `[listingQuery.isFetching]`. A cached,
fresh page resolves with no fetch, so `isFetching` never changes and the
effect never re-runs. Paging *back* within 60 s is the common case.

Worse, `shouldFocusListing.current` stayed `true`, so the next genuine fetch —
a sort change, say — stole focus to the listing for an unrelated interaction.

**Fix.** The effect now also depends on `values.page`, so it runs whether or
not a fetch occurs, and the pending flag always resolves.

## M6 — Detail cache primed as fresh with a partial payload *(Severity 3, fixed)*

`useProducts` primed `products.detail(id)` with a `ProductSummary`. That entry
is missing `trustIndicators`, `eligibility`, `interestBreakdown`, `faqs`, and
`terms` while being stored under — and typed as — `ProductDetails`.

Because `setQueryData` dates the write to now, the 60 s `staleTime` made the
partial entry **fresh**: `useProduct` would have rendered an incomplete
payload for a full minute with no revalidation, contradicting the approved
"render immediately, revalidate in the background" strategy.

**Fix.** Priming now skips ids that already hold a full payload and seeds new
entries with `{ updatedAt: 0 }`, so they are stale on arrival and refetch on
mount while still rendering instantly.

**Left open deliberately.** The primed value still does not satisfy the
`ProductDetails` type it is stored under. That is a contract question for the
M2.6 details screen — either a `summary` cache key, or a `ProductDetails`
type that models partiality. Recorded so it is decided, not discovered.

## M7 / L8 — Live region defects *(Severity 3 / 4, fixed)*

- **M7.** For `?page=99` against 24 products, `ResultCount` computed
  `from = 589`, `to = 24` and announced *"Showing 589–24 of 24 products"*
  before the clamp effect corrected the URL. The range is now clamped to the
  total.
- **L8.** `ResultCount` was mounted only once `meta` existed
  (`{meta ? <ResultCount/> : null}`). A live region must be in the DOM before
  its content changes, so the **first** announcement — the one that matters on
  load — was dropped. It now always renders, empty included.

## 2. URL-state audit — 19/19 correct

The merge logic was ported verbatim and exercised exhaustively. No defects.

| Behaviour | Result |
|---|---|
| Sort change keeps `q`, resets page | PASS |
| Page change keeps `q` + sort | PASS |
| Search submit keeps sort, resets page | PASS |
| Search keeps `amount` + `tenure` | PASS |
| Unknown params preserved (M2.5 forward-compat: `bank`, `minRate`) | PASS |
| `page=1` removes `page` | PASS |
| Default sort removes `sort` + `order` | PASS |
| Empty `q` removes `q` | PASS |
| Exactly one write per interaction (sort / search / page) | PASS ×3 |
| `page=abc` / `page=0` / `page=-3` / `page=2.5` → 1 | PASS ×4 |
| Unknown sort, sort-without-order, order-without-sort → default | PASS ×3 |

**No parameter clobbering exists.** Every write reads current
`URLSearchParams`, applies the patch, and navigates once. Coupled updates —
sort-resets-page — are a single merged write.

**Back/Forward** follows structurally: `router.replace` with canonical URLs
and validation on read means every history entry is a complete, valid state.
Not exercised in a browser (see §7).

### L9 — canonicalisation asymmetry *(accepted)*

Hand-edited non-canonical URLs render correctly but are never rewritten:
`?page=1`, `?sort=interestRate&order=desc`, `?order=asc`, `?page=abc` all
persist. Out-of-range pages *are* written back, via the clamp effect. This is
compliant — the spec canonicalises *on write* — but the asymmetry is worth
stating explicitly in `marketplace-url-state.md` so it reads as a decision.

## 3. React Query audit — 1 defect (M6, fixed)

Query keys hash deterministically via `hashKey`:

```
hero   ["marketplace","products","list",{"limit":12,"order":"desc","sort":"interestRate"}]
page1  ["marketplace","products","list",{"limit":6,"order":"desc","page":1,"sort":"interestRate"}]
```

- **Determinism** — property order does not affect the hash; keys are pure
  functions of Marketplace state. PASS
- **I2 (hero ≠ listing)** — distinct keys; the hero sample does not change
  when the user paginates or sorts. PASS
- **Cache reuse / no duplicate requests** — navigating 1→2→3→2→1 issues
  exactly **3** requests. PASS
- **`keepPreviousData`** — previous page stays mounted; `isFetching` drives
  the dimmed state. Correct, but it is what exposes A4.
- **`staleTime`** — 60 s honoured; cached pages resolve with zero requests.
  Correct, and it is what exposed M5.

## 4. Accessibility audit — 3 defects (fixed)

**Correct as built:**

- Heading hierarchy is clean: one `<h1>` (hero) → `<h2>` per section via
  `SectionHeading` → `<h3>` on cards and trust items. No skipped levels.
- Landmarks: `<main id="main-content">`, skip link as first focusable element,
  `<nav aria-label="Pagination">`, `<form role="search">`, every `<section>`
  named by `aria-labelledby`.
- Combobox semantics are unmodified Radix. `SortControl` correctly uses
  `aria-labelledby` rather than `<label htmlFor>`, since the trigger is a
  `<button>` and not a labelable element.
- Pagination semantics: real `<button type="button">` elements,
  `aria-current="page"`, labelled icon-only prev/next, genuinely disabled at
  the range boundaries.
- Loading skeletons carry `sr-only` text ("Loading products…"), so their live
  regions announce something meaningful.
- The listing section is `tabIndex={-1}` and focusable for the page-change
  focus move.

**Fixed:** M5 (focus after pagination), M7 (garbled announcement), L8
(dropped first announcement).

**Not verified:** keyboard-only walkthrough and screen-reader behaviour need a
browser — see §7.

## 5. Performance audit — no defects

- **Network requests:** 3 on first load (hero sample, listing page, banks) —
  matches the approved strategy. Pagination adds one request per uncached
  page and zero for cached pages.
- **Renders after pagination / sorting:** one URL change → one
  `router.replace` → one render pass. No render storms once C1 is fixed.
- **Hydration warnings:** `MswProvider` correctly does not gate children, so
  server and client markup agree. With C2 fixed the Home subtree is
  client-rendered inside a boundary, which cannot mismatch.
- **Bundle:** Home is 10.2 kB / 195 kB First Load once C0 is resolved.

**Optimisation notes (not defects).**

1. `handlePageChange` and `handleSortChange` are recreated each render and
   `ProductGridSection` is not memoised. Harmless now; worth `useCallback` +
   `memo` when M2.5 adds filter chips.
2. `SearchBar` renders twice at mount — the sync effect's first `setDraft`
   commits an equal-valued object. One extra render, not a loop.

## 7. Browser audit — NOT PERFORMED

Pagination, sorting, URL updates, deep links, refresh persistence,

1. **C0 makes it meaningless.** Visiting `/` renders the Phase 0 placeholder,

builds — not by reading code. But the browser pass is genuinely outstanding
and should be run after C0 is resolved.

## 8. Phase readiness — M2.5 must not begin yet

**M2.5 cannot safely begin.** Three blockers:

1. **C0 must be resolved.** Building filters onto a page no user can reach is
   not defensible, and it invalidates every manual verification step.
2. **A3 must be decided.** M2.5 adds `setFilters` — a third URL writer. The
   invariant that makes that safe is currently violated by `SearchBar`.
   Adding filters before fixing it means the first genuine clobbering bug
   arrives with three writers instead of two.
3. **The browser pass must actually happen** on the real route.

**A4** should be fixed with M2.5 rather than before it — filter chips will
reset the page constantly, and a pager whose highlight lags every interaction
will be much more visible then.

Once C0 and A3 are settled, the M2.4 architecture is sound and M2.5 extends it
without further structural change. The URL-state contract already preserves
unknown parameters (verified with `bank` and `minRate`), the query-key factory
already accepts filter params, and the boundary enforcement already holds.
Those are the three things M2.5 depends on, and all three are in good order.

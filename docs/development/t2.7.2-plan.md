## 2. O1 — closed

`useCompareProducts.ids.slice(0, MAX_COMPARE)` is removed. The hook resolves
whatever ids it is given; it does not adjudicate how many are allowed.
`parseCompareIds` does not cap either — a business rule in the parser would let
the pure layer and the store disagree about what "full" means.

**`useCompareSelection` is the sole enforcer**, across `add`, `toggle`, and
`replaceAll` — three methods, one module (C2).

How O1 survived a green suite is recorded in C2 and drives §5.1: the old probe
was named "enforced in the store, and only there" but never looked at
`use-compare-products.ts`.

## 3. Design

### 3.1 The synchronisation, and the trap in it

C4 rule 2: when the parsed, deduped, **capped** id list differs **by value** from
the store, call `replaceAll`.

The obvious implementation caps by importing `MAX_COMPARE` into the hook — and
that would be a **third** file referencing the cap, failing the exact-list probe
that closes O1. The two requirements appear to collide.

They don't: the store already publishes its own limit as `selection.max`. The
hook compares against `parsed.slice(0, selection.max)`, so the cap still lives
in one module and the hook simply reads what the store declares.

This is worth stating in advance because the natural first draft gets it wrong,
and the failure mode is a probe failure rather than a behaviour failure —
easy to "fix" by loosening the probe.

**Why the comparison must be capped at all (R13):** an over-cap URL disagrees
with the store permanently, by design — `?ids=` with five renders four and I7
forbids rewriting on load. An effect firing on any difference would fire every
render, forever.

**Why by value:** a fresh array each render is never reference-equal, so an
identity comparison loops for the same reason.

**Strict Mode:** the effect is double-invoked in development. The value
comparison makes the second run a no-op, so no guard, ref, or once-flag is
needed — the sync is idempotent by construction rather than by bookkeeping.

### 3.2 Intent

Add and remove compute the next id list **from the current URL** (read-then-merge,
rule 1), serialise it, and `push` once. They do not touch the store; the store
follows. `correct` exists for the unknown-id case discovered when the batch
responds and issues a `replace` (I8).

### 3.3 Module surface

| Module | Exports |
|---|---|
| `utils/compare-url.ts` (pure) | `IDS_PARAM`, `parseCompareIds`, `serialiseCompareIds`, `mergeCompareParams` |
| `hooks/use-compare-url-state.ts` | `useCompareUrlState(selection)` → `{ ids, addId, removeId, correctIds }` |

### 5.2 Unit assertions — `compare-url.ts`

Parse: one id · several in order · duplicates deduped to first occurrence ·
empty segments dropped · malformed ids dropped · an over-long string truncated ·
missing parameter → `[]` · **more than four ids parse intact** (the assertion
that proves D8).

Serialise: `[]` → `''`, so the canonical empty compare URL is `/compare` · order
preserved · round-trip stable · no other parameter survives a merge.

### 5.3 What T2.7.2 will not prove

Push/replace counts, the synchronisation, Back/Forward, and the loop guard are
**not** exercised here — no screen mounts the hook until T2.7.3. A green suite
after T2.7.2 means the URL *contract* is correct and the writer is
*structurally* conformant. It does not mean the route navigates correctly.

Journeys stay at **127**.

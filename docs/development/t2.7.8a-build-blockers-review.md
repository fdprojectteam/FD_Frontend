| E2 | `npx eslint src` | clean, exit 0 |

**E6 is the finding that reframes this.** cva does not throw on an unknown
variant value and does not fall back to `defaultVariants` — it contributes
nothing. So the three affected controls have been rendering with **no variant
classes and no size classes at all**: no height, no padding, no background, no
hover, no border.

That is why nothing looked broken enough to notice, why no probe fired, and why
seven tasks passed over it. It also means these are not cosmetic type errors.

## 3. Group A — `variant="ghost" size="icon"`

### 3.1 Root cause, in three layers

**Proximate.** Three call sites pass prop values `Button` does not declare: the
column-header remove `X`, the carousel's Previous/Next arrows, and the carousel
dots.

**Why it survived.** Four independent safety nets were all blind to it at once:
cva swallows unknown values silently (E6); esbuild bundles the harness without
type-checking; the invariant probes read source *text*, and the text is
plausible; and `tsc` was believed unrunnable, so the one tool that would have
caught it in T2.7.4 was never invoked.

**Underlying.** The platform has **no icon-only control**, and the three
components that needed one before M2.7 each solved it locally (E8):

| Prior site | Solution |
|---|---|
| `top-nav.tsx`, `mobile-nav.tsx` | native `<button>`, `focus-ring inline-flex size-10 items-center justify-center rounded-full hover:bg-surface-muted` |
| `dialog.tsx` close | Radix `Close` with `rounded-md p-1 hover:bg-surface-muted` |
| `pagination.tsx` arrows | a component-local cva, `size-8`, bordered |

M2.7 is the **first** place that reached for `Button` for an icon-only control,
and it reached for shadcn/ui's names for that job — `ghost` and `icon` — which
this project's `Button` never adopted. The names were plausible precisely
because they are the industry default.

### 3.2 Classification — the two props classify differently

| Prop | Classification | Basis |
|---|---|---|
| `variant="ghost"` | **Pre-existing gap, exposed by M2.7.** The Phase 0 blueprint specifies a `ghost` variant (E5); Phase 1's T1.1 implemented three of the four and nothing recorded the omission | E4 + E5 |
| `size="icon"` | **Introduced by M2.7.** No document anywhere specifies an `icon` size; sizes are `sm/md/lg` in both the blueprint and `design-tokens.md` | E5, E7 |
| Both, as *shipped call sites* | **Introduced by M2.7** (T2.7.4, T2.7.5) | E3 |

**Not** caused by an incorrect invariant or contract. No rule told anyone to
write these props. DoD criterion 8 ("no new design-system primitive") is
sometimes offered as the culprit — it is not: it forbids *adding a primitive*,
and the correct response to a missing variant was to raise it, which is what the
per-task contracts existed for.

### 3.3 The consequence, which is worse than a red build

With no size classes (E6), the rendered targets are:

| Control | Rendered target | Where |
|---|---|---|
| Remove `X` | ≈ 16 × 16 px (icon box only) | desktop table + mobile cards |
| Previous / Next arrows | ≈ 20 × 20 px | **mobile carousel** |
| Dots | 8 × 8 px (`size-2` from `className`) | **mobile carousel** |

Against `--ds-touch-target-min: 44px` (E7) and Document 14 §10 ("at least
44 × 44 px where practical"), all three fail; the arrows and dots also fall
below WCAG 2.2 SC 2.5.8's 24 px floor. The dots have an arguable *equivalent
control* exception (the arrows do the same job); the arrows have no equivalent
other than swiping, which is not a control.

This is a real accessibility defect on the presentation with the least automated
coverage, and it has been in the repository since T2.7.4. It is also the reason
this group should not be fixed by making the types agree — making
`variant="ghost"` compile without giving it a size would leave every target
exactly as small as it is now.

### 3.4 Smallest correct fix — three options, honestly costed

| | Option | Cost |
|---|---|---|
| **A** | **Implement `ghost` and add an `icon` size on `Button`** | A platform-wide change to a primitive. Purely **additive**: nothing renders `ghost` or `icon` today except the three broken sites, so no existing screen can shift. Closes the blueprint gap, fixes the targets, removes the duplication pressure, adds no token (`icon` = `size-11` = the existing `--ds-touch-target-min`) |
| **B** | **Extract an `IconButton` primitive** | The most "correct" long-term shape given four call-site families, and the most expensive: a genuinely new primitive, three prior sites that should then be migrated, and a direct collision with DoD 8 if done inside M2.7 |
| **C** | **Drop `Button` at the three sites and hand-write the `top-nav` recipe** | No design-system change, but copies a class recipe into a module component for the fourth time — the duplication `CLAUDE.md` prohibits — and re-implements `focus-ring`, disabled semantics and `asChild` by hand |

**Recommended: A.** It is the smallest change that makes the code compile *and*
fixes the accessibility defect *and* reduces duplication rather than adding to
it. B is the right conversation for M2.9 or Phase 3 and should be recorded as
such, not smuggled into a build fix.

**A is not a new primitive.** `Button` already exists; `ghost` is already
specified; `icon` maps onto a token that already exists. DoD 8 is satisfied on
its own terms. It is still a change to shared platform code, so §6 asks for it
explicitly.

### 3.5 The dots need a decision of their own

Under option A the dots would become 44 px targets — and a row of four 44 px
boxes at `gap-2` is **visually different** from a row of four 8 px dots. That is
an approved-UI change, so the contract does **not** make it.

The dots keep `className="size-2 p-0"`, which tailwind-merge resolves over the
`icon` size deterministically — **but not over the variant's hover.** Executed
against the real `tailwind-merge`, `cn('… size-11 p-0 hover:bg-surface-muted
…', 'size-2 rounded-full p-0 bg-content')` collapses the size and padding
correctly and **retains `hover:bg-surface-muted`**, which would repaint the 8 px
dot on hover. That is an unreviewed visual change to an approved control, so the
dots must neutralise the inherited hover in their own `className` (the active
dot to `bg-content`, the rest to `bg-border-default`) and render exactly as they
do today.

The sub-minimum target is **recorded as an accepted exception** with its
justification (the arrows are an equivalent control, and remain equivalent only
because option A brings *them* to 44 px).
Recording it is the point: an 8 px target that is written down is a decision, an
8 px target that is silent is a defect.

### 3.6 Impact assessment

| Dimension | Effect |
|---|---|
| **Architecture** | None. No new module, hook, boundary or authority. `components/ui` → module direction is unchanged |
| **Ownership** | None. `Button` is already the design system's; the module remains a consumer |
| **Public behaviour** | **Yes, and deliberately**: three controls gain the variant and size they were always written to have. Nothing else in the application can change, because nothing else passes these values (E3) |

## 4. Group B — `products` is possibly `undefined`

```
compare-screen.tsx(223,29) / (226,29):
  Type 'NoInfer<ProductDetails[]> | undefined' is not assignable to 'ProductDetails[]'
```

### 4.1 Root cause

```ts
const hasComparison = ids.length > 0 && !isError && Boolean(products);
…
) : !hasComparison ? ( skeleton ) : (
      <CompareTable products={products} … />   // products: ProductDetails[] | undefined
```

`hasComparison` is a **boolean**. TypeScript narrows from the expression, not
from a name bound to its result, so the guard is invisible at the render site.
The code is correct at runtime and unprovable to the compiler.

### 4.2 Classification — **caused by a contract that is right in substance and
lossy in form**

This is the one error in the ten that traces to a rule rather than a mistake.
D-A3 (T2.7.7, and reinforced by the T2.7.7 implementation review) required *one
derived decision carrying every guard*, so that the action bar and the reading
container could not drift apart. That requirement is correct and should stand.

What was never specified is that the derived value must carry its **evidence**
as well as its verdict. `Boolean(products)` discards exactly the fact the render
site needs. The contract asked for a single source of truth and got a single
source of *opinion*.

Secondary contributor: the invariant probe pins the source string
`Boolean(products)` literally, so the lossy form is currently *enforced*.

### 4.3 Smallest correct fix

```ts
const comparison = ids.length > 0 && !isError && products ? products : null;
const hasComparison = comparison !== null;
…
) : !comparison ? ( skeleton ) : (
      <CompareTable products={comparison} … />
```

Three lines. `!comparison ? A : B` narrows `comparison` to `ProductDetails[]` in
`B`, so both view components type-check without a cast, a `!`, or a `?? []`.

**Runtime behaviour is bit-for-bit identical**, including the edge case:
`Boolean([])` is `true` today and `[] ? … : null` is truthy tomorrow, so a batch
that returns an empty array for entirely unknown ids renders the same thing it
renders now.

Rejected alternatives, and why: `products!` and `products ?? []` both make the
compiler agree while erasing the invariant — the second silently renders an
empty table if the guard is ever weakened. Re-testing `products &&` at each
render site duplicates the decision, which is the thing D-A3 exists to prevent.

### 4.4 Impact assessment

| Dimension | Effect |
|---|---|
| **Architecture** | None — it strengthens D-A3 from *one derived decision* to *one derived decision that carries its evidence* |
| **Ownership** | None. `CompareScreen` remains the sole decider |
| **Public behaviour** | **None.** Identical rendering in every branch, including the empty-batch edge |

### 4.5 Expected production files

`src/modules/marketplace/components/compare-screen.tsx` — only.

### 4.6 Expected verification changes

| Change | Why |
|---|---|
| **Re-point** the D-A3 probe from the literal `Boolean(products)` to the new derivation | It pins source text; leaving it would fail the suite for the wrong reason and, worse, would keep enforcing the lossy form |
| Keep asserting **all three guards** appear in the derivation | The T2.7.7 correction is the substance and must not be lost in the re-point |
| **`npm run typecheck` is the authoritative check** for this defect class — no probe replaces it | Once `comparison` is narrowed, a cast is not *available* without deleting the narrowing, and `tsc` rejects that. A probe cannot do better |
| Record the re-point in `verification/README.md`, per the existing convention | A re-pointed probe with no record is indistinguishable from a weakened one |

**A probe banning `!`, `as` and `?? []` at the render sites was proposed here and
is withdrawn.** It enumerated three wrong fixes and would have missed every
other one (`?? EMPTY`, widening the child prop to optional, a helper returning
`[]`) — a probe whose name claims a property while its assertion checks
vocabulary, which is this milestone's documented failure mode. The compiler
already forbids the whole class.

Estimated: **0 new invariants, 1 re-pointed**, 0 journeys (behaviour is
unchanged, so a new journey assertion would assert what L4/L6 already do).
This is a **change from the previous estimate of +1 invariant**, and it is the
only count this correction moves.

### 4.7 T2.7.8 or deferred?

**T2.7.8a**, with Group A. It is three lines and no behaviour change, so folding
it into the audit is tempting — but the audit's value is that it touches
nothing, and splitting the two groups across two tasks would leave the build
gate red after the first of them.

## 6. The single decision that is not mine

**May `src/components/ui/button.tsx` gain a `ghost` variant and an `icon`
size?**

It is shared platform code, so the answer belongs to you even though the change
is additive and no existing screen can shift. For completeness, the two ways to
say no:

- **No, use option C** — hand-write the icon-button recipe at the three sites.
  Compiles, fixes the targets, and accepts a fourth copy of the recipe.
- **No, defer option B** — extract an `IconButton` in M2.9 and leave the build
  red until then. Not recommended: it keeps a 16 px control shipping to close a
  milestone.

Two smaller confirmations, neither blocking:

- **R-A2** — that an audit *reports* findings and never fixes them. I inferred
  this at T2.7.8's review and it has never been confirmed; the whole shape of
  §3.9 and §4.7 rests on it. If it does not hold, both groups fold into T2.7.8
  and T2.7.8a disappears.
- **G1** — that `tsc --noEmit` joins the recorded gates and runs every task.

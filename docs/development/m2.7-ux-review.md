## 1. Mobile — "Compare +" cannot be tapped reliably *(High)*

### 1.1 Root cause — three candidates, all real, all cheap to distinguish

**C1 — the button is 40 px tall, and the platform minimum is 44 px.**
`FDProductCard`'s footer buttons take `Button`'s default `size="md"` = `h-10`
= 40 px. `sizes.css` declares `--ds-touch-target-min: 44px`, and Document 14 §10
requires ≥ 44 × 44 px. This is a **4 px shortfall on every card action** —
"View details" too — and it has been there since M2.2. It is not specific to
Compare; Compare is simply the one being aimed at repeatedly.

**C2 — the sticky entry bar occludes the bottom of the grid.**
`CompareEntryBar` is `sticky bottom-0 z-10` and is the **last** element in
`HomeScreen`. A sticky element reserves its space at its *flow* position but
paints at the viewport edge while stuck — so once two products are selected, the
bar sits over whatever is currently at the bottom of the viewport, which on a
short mobile screen is a product card's footer. `z-10` guarantees it wins the
hit test. This matches the report's "another element appears to interfere"
exactly, and it is manual check #11, which has never been run on a device.

**C3 — at the cap, unselected Compare buttons are genuinely disabled.**
`disabled={compareDisabled && !isComparing}` fires when four products are
selected. The only cue is `opacity-70` plus a muted palette, and — unlike the
picker, which announces *"maximum"* — the grid explains nothing. A user at the
cap experiences precisely "I tap and nothing happens".

C1 is certain (measurable in the source). C2 and C3 are conditional: C2 only
with ≥ 2 selected, C3 only at 4. **On device they are trivially separable** —
if the button responds when scrolled to mid-screen, it is C2; if it never
responds with four selected, it is C3.

### 1.2 Classification

C1 **layout/design-system**, C2 **layout**, C3 **UX** (the state is correct; its
communication is not).

### 1.3 Smallest safe fix

| | Fix | Files |
|---|---|---|
| **C1** | In `button.tsx`, `md: 'h-10 px-4'` → `md: 'h-11 px-4 md:h-10'` — 44 px on touch viewports, 40 px unchanged from `md` up | `src/components/ui/button.tsx` (1 line) |
| **C2** | In `HomeScreen`, add bottom padding to the container while the bar is shown: `cn('container-page flex flex-col gap-16 py-12', showCompareEntry && 'pb-28')` | `home-screen.tsx` (1 line) |
| **C3** | Not fixed here. Recorded — the correct answer is a cap message on Home, which is a copy decision, not a styling one | — |

C1 belongs in the primitive, not at the call site: T2.7.8a established that a
size is a design-system decision and **never** a call-site `className`. Fixing
it there also repairs every other 40 px control at once, which is why it is both
the smallest and the most valuable change in this review.

### 1.4 Impact

Architecture: none. Ownership: none — `HomeScreen` already owns
`showCompareEntry`. Verification: **none** — no probe asserts a button height or
the container's padding. C1 is platform-wide and should be eyeballed on the
gallery page.

## 2. The first selection gives no feedback *(High)*

### 2.1 Root cause — two layers, and the second is the one being reported

**Layer 1 — the card's selected state is nearly invisible.** The only change is
the button's variant: `secondary` (strong border, card surface, default text)
→ `outline` (brand border, transparent surface, brand text, semibold). Both are
bordered buttons of identical size in the same position. The **card itself does
not change at all**.

**Layer 2 — and this is the actual complaint.** `MIN_COMPARE = 2`, so the entry
bar appears only on the *second* selection. The first selection produces **no
page-level feedback whatsoever**; the second produces a bar sliding in at the
bottom. That is exactly *"only after selecting another product do I clearly
recognize the selection state"* — the user is describing the threshold, not the
styling.

### 2.2 Classification

UX (discoverability), with a styling contributor. Nothing is behaving
incorrectly.

### 2.3 Smallest safe fix

Two changes, independent, both prop-driven — `FDProductCard` already receives
`isComparing`, so **no new prop and no new state**:

1. **Card-level selected state** — `Card` gains
   `isComparing && 'border-border-primary ring-1 ring-border-primary'`. The
   whole card responds, not a button in its corner.
2. **The icon carries the state** — `leftIcon={isComparing ? <Check/> : <Plus/>}`.

3. **The threshold** — `MIN_COMPARE: 2 → 1`, so the bar appears on the first
   selection and the count is visible from the start. A one-product comparison
   is already valid and renders (decision D5), so nothing downstream changes.
   **This is a product decision and I am not making it.** If a one-product
   comparison is undesirable, the alternative is to show the bar at 1 with
   Compare disabled — `HomeScreen` derives the flag and passes it down, which
   keeps `CompareEntryBar` presentation-only under D-A2, at the cost of one prop.

### 2.4 Impact

Architecture: none. Ownership: none.

**Verification: two constraints that must be respected.**

- The button's **accessible name and visible text must not change**. Swapping
  "Compare" → "Added" would break `J10`: `compareButtons()` filters on an
  `aria-label` beginning "Compare ", and the journey selects cards by index
  after the first is selected — a renamed control shifts every index. Changing
  the icon and the card border has **zero** verification cost; changing the
  label has a real one, for no accessibility gain (`aria-pressed` already
  carries the state).
- Changing `MIN_COMPARE` requires re-pointing `J10`, which asserts *"one
  product is below the threshold — still no bar"*. That is a **documented
  re-point**, not a weakening, and must be recorded in `verification/README.md`.

## 3. Mobile comparison experience *(Medium)*

### 3.1 Root cause

Not styling. `CompareCards` presents **one product per card at 100 % width**
(`w-full shrink-0 snap-center` in a `snap-mandatory` scroller), so exactly one
product is visible at a time. **Comparing therefore requires memory**: to
compare two rates the user must read one, swipe, and recall it. That is the one
thing a comparison screen exists to remove.

The spacing and typography are fine. The *presentation model* is the problem,
and it was an approved decision (T2.7.5, approach A), so this is a genuine
re-open of a design question rather than a defect.

### 3.2 Classification

UX / interaction model.

### 3.3 Options, honestly costed

| | Option | Cost |
|---|---|---|
| **A** | **Peek the next card** — `w-full` → `w-[85%]`, so the neighbour is partly visible | **One class.** Two products readable at once at the boundary; swipe affordance becomes self-evident. Does not make columns properly comparable |
| **B** | **Horizontally scrolling table at all widths**, with the attribute column `sticky left-0` | The correct answer for a comparison. Also the expensive one: it removes `CompareCards`, and with it the dual-DOM `data-compare-view` architecture, `STACKED_COMPARE_ROWS`' only consumer, one of the three `isBestCell` callers, and journeys L9 and L9b entirely |
| **C** | Keep the carousel, add a sticky row-label column | Not expressible — the labels live inside each card |

**Recommended: A now, B as an M2.9 or Phase 3 design decision.** A is one class
with no verification impact and it measurably reduces the memory cost. B changes
an approved architecture and should not be smuggled in as a UX refinement.

### 3.4 Impact

Option A — architecture: none. Ownership: none. Verification: **none** (no probe
asserts card width; L9 counts `article` elements and reads `data-row-layout`).
Option B — architecture: **yes, materially**. Out of scope for this review.

## 4. Desktop table row spacing *(Medium)*

### 4.1 Root cause

Precise, and it is two things compounding:

1. Every `th` and `td` in `tbody` carries `p-4` — 16 px vertical on a
   `text-body` line gives ≈ 56 px rows separated by a 1 px `border-b`.
2. `BEST_HIGHLIGHT` paints `bg-surface-brand-subtle` **on the `<td>` itself**.
   Under `border-collapse`, the tint therefore runs the full height of the cell
   and meets the next row's cell across that 1 px line. Its `rounded-card`
   corners are invisible because there is no gap for them to round into.

So a highlighted row does not read as a highlighted *row* — it reads as a tinted
block fused to its neighbour. The report is accurate.

### 4.2 Classification

Styling.

### 4.3 Smallest safe fix

`p-4` → `px-4 py-5` on the `tbody` `th` and `td` (2 class strings, one file).
Rows gain 8 px of vertical breathing room, the tinted block gets space above and
below the text, and the 1 px separator does the rest.

Deliberately **not** proposed: changing `BEST_HIGHLIGHT` (it is shared with the
mobile row, where it renders correctly and is asserted token-for-token by L9b),
or switching to `border-separate` with `border-spacing-y` (it discards
`border-collapse` and re-draws every border — a large change for a spacing
complaint).

### 4.4 Impact

Architecture: none. Ownership: none. Verification: **none** — no probe asserts
cell padding, and `HIGHLIGHT_TOKENS` in L9b lists the four `BEST_HIGHLIGHT`
tokens, which are untouched.

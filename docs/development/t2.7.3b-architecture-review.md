## 1. Architecture assessment

### 1.1 What the task must achieve, and the one fact that shapes it

`/compare` is **URL-authoritative** (C4): the URL *is* the selection. A bare
`/compare` renders the empty state even when the store holds four products.

So the affordance is not "a link to `/compare`". It is **a link whose `?ids=`
is composed from the store at render time**. That is R15b — a consequence of C4,
not a decision — and it is the whole architectural content of this task.

Everything else (count, Clear, placement, styling) is ordinary UI.

### 1.2 Where it lives

**Home is decided** (R15a): a floating bar appearing at ≥ 2 selected, showing
the count, a Clear action, and a Compare button.

**Details is not decided, and is a gap.** A user who selects products from
`DetailActionBar`'s "Add to Compare" has **no route to the comparison from that
screen** — they must navigate back to Home first. `/compare` was unreachable
from anywhere until now, so this was invisible; once Home has an entry, Details
becomes the only screen where a selection can be built but not viewed.

That is question **Q2** below. It is a product decision, not an implementation
detail, and I am not making it.

### 1.3 The composition problem — where the href is built

`serialiseCompareIds(ids)` returns a **query string** (`ids=a,b`), not a URL.
Something must compose `${ROUTES.compare}?${query}` and satisfy `typedRoutes`,
which requires an `as Route` cast for any runtime query string.

Three candidate owners, each with a different architectural cost:

| | Owner | Cost |
|---|---|---|
| **A** | `HomeScreen` composes inline | A third composition site and a **fifth** `as Route` cast, in a screen. Casts have so far been confined to `routes.ts` and the two URL writers |
| **B** | `constants/routes.ts` gains `compareWith(ids)` | Keeps the cast where E4 says casts live — but **`routes.ts` cannot import `serialiseCompareIds`**: the boundary policy allows `constants` to import only `constants` and `types`. **This option is closed** |
| **C** | `utils/compare-url.ts` gains a href builder | `utils` may import `constants`, so it can reach `ROUTES`; it already owns `IDS_PARAM` and the canonical form, so the parameter's name stays in one file. Cost: a cast in a third module, and a second way to compose a compare URL alongside the writer's `pathname`-based one |

B is not available. A and C are both defensible and produce different ownership.
That is question **Q1**.

### 1.4 A probe finding, surfaced here because this task depends on it

```
check('exactly two Route assertions exist, in routes.ts and nowhere else (E4)',
      (routes.match(/as Route/g) ?? []).length, 2);
```

The name says **"and nowhere else"**. The assertion reads **only `routes.ts`**.
There are in fact **four** casts in `src/` — two in `routes.ts`, one in each URL
writer.

This is not vacuous (it measures something true) but it is **narrower than its
name**, which is precisely the category T2.7.8's vacuity sweep exists to find.
It matters here because Q1's answer adds a fifth cast, and whichever option is
chosen, this probe must be re-pointed to an exact file list rather than a count
in one file.

**Recorded for the sweep; not fixed here** (R-A2).

## 2. Ownership analysis

### 2.1 What already exists and is correct

| Concern | Owner | Status |
|---|---|---|
| The selection on Home | `CompareSelectionProvider` (store) | C5 — Home carries nothing in its URL |
| `HomeScreen` reads it | `compare.toggle`, `compare.ids`, `compare.isFull` | Already the hook owner |
| The `?ids=` name and canonical form | `utils/compare-url.ts` | Exact-list probe |
| Writing `?ids=` | `useCompareUrlState` | One of exactly two URL writers |

### 2.2 What T2.7.3b would add

| Interaction | Authority | Writes |
|---|---|---|
| **Compare** (navigate) | None — a route change | Native `<Link>`. **No store write, no URL write on Home** |
| **Clear** | The **store** — `selection.clear()` | Store only. Correct on Home under C5 |
| **Count** | The store — `selection.count` | Read only |

**No new authority is created.** The bar reads the store and navigates; it
decides nothing. `HomeScreen` remains the owner of every decision, and the bar is
presentation-only under the T2.7.7 formulation — **ownership, not signature**.

### 2.3 Rules checked, and the verdict on each

| Rule | Verdict |
|---|---|
| **I1 / I2a** — one URL writer per route | **Not violated.** Home writes no `?ids=`; the bar navigates, and navigation is not a URL write of Home's state |
| **I3** — presentation-only sections | **Not violated**, provided the bar takes props and `HomeScreen` derives |
| **C4** — URL authoritative on `/compare` | **Upheld, and this is what makes the task necessary** |
| **C5** — selection changes never write another route's URL | **Upheld.** Clear writes the store, as Home must |
| **C2 / O1** — one cap owner | **At risk** — see Q4 |
| **E4** — casts confined | **Already misstated by its probe** (§1.4), and Q1 adds to it |

### 2.4 Duplication check

**No behavioural duplication.** The card's Compare button *toggles selection*;
the bar *navigates*. Different verbs on different objects.

One near-duplication to note: **Clear on Home writes the store; a Clear on
`/compare` would have to write the URL.** Both are correct under per-route
authority, and it is the single thing most likely to be got wrong by whoever
next adds a compare control. It should be stated in the contract rather than
inferred from two call sites.

## 3. Questions requiring answers before a contract

### Q1 — Who composes the compare href? *(architectural, blocking)*

Options A and C in §1.3 (B is closed by the boundary policy). This determines
where a fifth `as Route` cast lives and whether `HomeScreen` learns how a
compare URL is shaped.

*My reading, offered as input not decision:* **C** keeps the parameter's name and
its canonical form in the module that already owns both, and leaves `HomeScreen`
asking for a href rather than knowing how to build one. **A** avoids a second
composition path but puts URL shaping in a screen.

### Q2 — Is Product Details also an entry point? *(design, blocking)*

R15a decided Home. Details currently strands a selection built there. Options:
Home only (accept the strand) · both · Details later. **Not mine to choose**, and
it changes the file list.

### Q3 — "Floating": sticky or fixed? *(design, small)*

R15a says *floating*. `/compare`'s action bar is `sticky bottom-0`, which keeps
its place in the flow and cannot occlude content. A `fixed` bar over a long
product grid would overlay the last row and need reserved padding. The approved
designs show neither. **Which is intended?**

### Q4 — Where does the "2 or more" threshold live? *(architectural, small)*

D5 established that a **one-product comparison is valid and renders**. So "≥ 2"
is a rule about when to *offer the shortcut*, not about what is comparable —
presentation, not domain.

But it is still a number with no home. Writing `count >= 2` inline in
`HomeScreen` repeats O1's mistake in miniature: a threshold with no owner,
discoverable only by grep. **Does it become a named constant, and if so, where?**

## 4. Risks

| # | Risk |
|---|---|
| **R-1** | The bar navigates to a stale href. The href must be composed from the store **at render**, not memoised across selection changes, or a user who adds a fourth product navigates with three |
| **R-2** | A fifth `as Route` cast lands in a screen (Q1 = A) and the E4 probe — already narrower than its name — silently accommodates it |
| **R-3** | Clear on Home is later copied to `/compare` as a store write, breaking C4 |
| **R-4** | The href assertion is written as "navigates to compare" and cannot be exercised — `next/link` is not stubbed, so jsdom refuses document navigation. The assertion must be about the **href**, and named accordingly (the T2.7.7 lesson) |
| **R-5** | Q2 answered "Home only" without recording it, leaving the Details strand as folklore |

## 7. Decisions taken and implementation outcome

Answered under the delivery-speed working mode; each is the option that best
matches the existing architecture.

| # | Decision | Reason |
|---|---|---|
| **Q1** | **C — `utils/compare-url.ts` gains `compareHref`** | B is closed by the boundary policy (`constants` may not import from modules). C keeps the parameter's name and its canonical form in the one module that already owns both, and leaves `HomeScreen` asking for a href rather than knowing how to build one |

knowingly shipping an assertion that cannot see the thing it names. E4 is now
two probes: `routes.ts` asserts exactly two, and an **exact file list** permits a
runtime cast only where a query string is composed.

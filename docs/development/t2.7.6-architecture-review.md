# T2.7.6 — Add Product: architecture review

Project: FD Investment Platform
Date: 2026-08-01
Status: **Review only. No implementation contract, no production code.**
Governing: `marketplace-compare-state.md` (C1–C6, **C4**), `marketplace-url-state.md`
(I1–I8, D2's closed parameter set), `m2.7-implementation-plan.md` (D3, D4, A1),
`verification/README.md`.

> The feature is small — a dialog listing the catalogue with an Add per row —
> and almost every risk in it is about **which authority the Add writes to**.
> On `/compare` that is the URL, not the store, and the two most likely
> mistakes both come from reusing something that assumes otherwise.

---

## Findings

### M1 — Nothing stops the fifth add, and the failure is invisible *(Major)*

`useCompareUrlState.addId` deliberately does not consult the cap — correct, and
decided in T2.7.2: the cap belongs to the store, and a second enforcer in the
URL writer is what O1 closed.

So if the picker offers Add on a fifth product, the sequence is:

1. `addId` appends → the URL carries five ids;
2. the store caps display at four;
3. **the product the user just added is not the one that disappears — it is
   simply never shown**, because it lands in the hidden tail;
4. under over-cap promotion (R13a) it surfaces only after a later removal.

The user clicks Add and nothing observable happens. Nothing in the current code
prevents this, and no probe covers it.

**Affects:** C2 / O1 (one cap owner), R13a.
**Smallest correction:** the picker receives `isFull` from the screen — read
from `selection.isFull`, the value the store publishes, exactly as the sync
reads `selection.max` — and disables Add. It must **not** import
`MAX_COMPARE`; that would fail the exact-list probe and re-open O1.

### M2 — The catalogue query and the dialog's open state have no owner yet *(Major)*

I3 and I2a: only the screen owns hooks; sections receive props. `ComparePicker`
therefore cannot call `useProducts` itself without becoming a second hook owner
on this route.

But if `CompareScreen` calls it unconditionally, every visit to `/compare`
fetches a catalogue page the user may never open. The two are linked: whoever
owns `open` must own the query, because the query has to be gated on it
(`enabled: open`).

**Affects:** I3, I2a.
**Smallest correction:** `CompareScreen` owns both — `open` as local state and
`useProducts(params, { enabled: open })` — and passes `items`, `isLoading` and
callbacks down. The picker stays presentation-only. This grows the screen, which
is the honest cost of the rule; the alternative is an exception to it.

### M3 — In-dialog paging must never reach the URL *(Major)*

`/compare`'s parameter set is closed at **`ids` alone**
(`marketplace-url-state.md`). Paging inside the dialog is transient UI state
(I6, alongside dialog visibility). Two mistakes are available and both look
reasonable while being written: reaching for `useMarketplaceUrlState` (whose
parameters belong to Home), or adding `?page=` to `/compare`.

Either would put a second writer on the route and break D2's closed set —
the property `serialiseCompareIds` currently makes structural.

**Affects:** D2, I1/I2a, I6.
**Smallest correction:** paging/scroll position is local state in the screen; a
probe asserting the compare writer emits no parameter but `ids`.

### M4 — Reusing `FDProductCard` drags a route change into a modal *(Major)*

The card is prop-compatible to a suspicious degree — it already takes
`onCompare`, `isComparing` and `compareDisabled`, which is exactly the picker's
shape. But T2.6.8 also gave it a real `<Link href={ROUTES.product(id)}>` for
"View details". **Inside a dialog that navigates away, unmounting the
comparison and losing the selection the user was assembling.**

Its action also reads "Compare", which on Home writes the **store** and here
must write the **URL**. Same label, same component, two authorities — the
precise confusion C4 exists to prevent.

**Affects:** C4, I3.
**Smallest correction:** the picker renders a slim row — bank badge, bank name,
rate, tenure, Add — rather than the full card. Reusing the card instead would
require a new prop suppressing the link, on a component two other screens
already render, which is the larger change.

### m1 — Portalled dialog content escapes the `data-compare-view` convention *(Minor)*

Radix portals `DialogContent` to `document.body`, outside both view containers.
Every journey selector for the dialog would therefore be document-wide — the
exact hazard the scoping convention was introduced to remove, reappearing in
the one place the convention does not reach.

**Affects:** the responsive/scoping decision recorded in
`marketplace-compare-state.md`.
**Smallest correction:** dialog assertions scope to `[role="dialog"]`, and the
convention records that portalled content is scoped by role rather than by
`data-compare-view`.

### m2 — The trigger must be one button with a responsive label *(Minor)*

"Add another FD" shortens to "Add" below `md`. The `h1` already set the
precedent: shorten *inside* one element. Rendering two buttons would put two
triggers in the DOM and two in the harness, and would need the scoping
convention to disambiguate a control that should be singular.

**Affects:** the responsive decision; the single-trigger expectation in L3.

### m3 — "Already selected" has two possible sources *(Minor)*

`selection.has(id)` (store) and `ids.includes(id)` (URL) agree under C4, which
is precisely why a component handed both will use whichever is nearer and the
next reader will not know which is authoritative.

**Smallest correction:** the screen derives it once and passes the answer —
`isSelected(productId)` or a `selectedIds` array — not both inputs.

### m4 — The Add control's accessible name belongs with the others *(Minor)*

`removeLabel` and `selectLabel` live in `utils/compare-labels.ts`. An Add
control naming its product ("Add HDFC Bank to comparison") belongs there for the
same reason, or a third naming convention starts in a component.

### m5 — A picker with everything disabled is a dead end *(Minor)*

At four selected, every row is disabled and nothing explains why. Disabled
controls without a reason are the accessibility failure mode of a limit.

**Smallest correction:** when full, the dialog states the limit once. No new
pattern — the M2.5 empty state and M2.6 error card set the tone.

### O1 — Booking compatibility *(Observation)*

A future Booking flow plausibly needs "choose a deposit" from the same
catalogue. The picker stays reusable **only if it never learns about `?ids=`** —
it should take `items`, `isSelected`, `disabled` and `onAdd`. I3 already forces
that shape; the point is to notice that the rule is also what preserves the
option.

### O2 — Two "add" paths with different authorities *(Observation)*

Home's card Compare writes the **store**; the picker's Add writes the **URL**.
Both are correct — that is C4's per-route authority — and it is the single thing
most likely to be got wrong by whoever builds R15a's floating bar or any later
"add to compare" affordance. Worth stating in the contract rather than leaving
it to be inferred from two call sites.

### O3 — Decision needed: paginate in the dialog, or fetch one larger page *(Observation)*

24 products, six per page. A pager inside a modal adds focus management and a
second interactive region; a single larger page (`limit=24`) is simpler but uses
a different query key from Home's listing, so nothing is shared. Neither is
wrong; the approved design does not show the dialog (assumption A1), so it is a
decision to record rather than derive.

### O4 — Does the dialog stay open after an add? *(Observation)*

Unspecified. Each add is one `push` either way (I8), so two adds produce two
history entries and Back undoes them one at a time — which is consistent, but
worth asserting deliberately rather than discovering.

## The dimensions with nothing to report

**Single source of truth.** The catalogue comes from `useProducts` under the
existing key; the selection remains the URL on this route. No new store, no
mirror.

**URL state ownership.** `useCompareUrlState` remains the route's only writer
and already exposes `addId`. The picker adds no writer — provided M3 holds.

**Routing.** No new route. The dialog is not a route, has no URL, and must not
acquire one: dialog visibility is transient (I6).

**Business rule ownership.** The only business rule in play is the cap, and it
stays in the store (M1 is about *reading* it, not moving it).

**Data flow.** `CompareScreen` → `ComparePicker` props, one direction, with Add
reported upward into the existing URL writer. No new query key, no cache write.

**Duplication.** The real risks are m3 (two sources for "selected") and m4 (a
third labelling convention). Cell rendering, the highlight and the row model are
not involved — the picker shows catalogue rows, not comparison cells.

**Verification impact.** New journey L3 (add via the picker, cap enforced),
scoped per m1; probes for picker-is-presentation-only, no `MAX_COMPARE` import,
and the compare writer's single parameter. Radix's focus trap and restore stay
**partially observable in jsdom** — unchanged limitation, worth restating so a
green L3 is not read as "the dialog is accessible".

---

## Summary

Four Major findings, five Minor, four Observations. All four Majors are
decidable before any code is written, and three of them (M1, M3, M4) are
cheaper now than at review: they are about which authority an action writes to,
and that choice becomes invisible once it is spread across a component tree.

The Observations O3 and O4 are decisions the approved design does not make and
should be recorded, not derived.

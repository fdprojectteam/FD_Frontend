# M2.6 — Strict Architecture Review

Project: FD Investment Platform
Date: 2026-07-31
Revision: 2 — supersedes rev 1; adds a review against `roadmap.md`,
`phase-2-roadmap.md`, and `docs/engineering/*`
Reviews: `m2.6-implementation-plan.md`

## Verdict

**Not approved** — *as reviewed*. The plan's shape, invariant handling, and
verification strategy are sound, but it contained one factual error, one
decision whose recommended tool contradicts an approved engineering blueprint,
two component-layer corrections, and three unlisted decisions. Nine minimal
changes are proposed in §9. None require redesign.

> **Closed 2026-07-31.** All seven decisions were settled by the client
> (D1=A′, D2=A, D3=A, D5=Zod + local state, D6=module context with a provider
> seat, D7=sticky mobile / static desktop) and C1–C9 are applied in
> `m2.6-implementation-plan.md` **rev 2**. This document is retained as the
> record of why the plan changed. The rev 2 plan is what implementation follows.

## 1. Does M2.6 introduce architecture that does not already exist?

Yes — four elements, plus dependencies. Each needs explicit approval.

| New | Risk | Assessment |
|---|---|---|
| **Dynamic route segment** `[productId]` — the first in the app | Low | Standard Next App Router. `ROUTES.product(id)` already exists and anticipates it. |
| **`not-found` boundary** — the first in the app | Low | Standard. Required by the roadmap's "404 for unknown id". |
| **A client-state provider for compare selection** | **High** | First feature-scoped provider, and it needs a mounting seat that does not exist. See §2/D6. |
| **A sticky bottom action bar** | Medium | Document 05 defines a sticky **header** only. A bottom sticky region is a new layout pattern that interacts with the existing footer and landmark structure. See §2/D7. |
| **Dependencies:** `react-hook-form`, `@hookform/resolvers` | Medium | Required by `phase-2-roadmap.md` §M2.6 ("RHF + Zod"), not installed. Document 13 §"Modules should not increase the initial bundle unless the user navigates to them" makes this a real question — see §2/D5. |

Everything else in the plan reuses what exists: the repository/service/query
chain, `marketplaceKeys`, `calculateMaturity`, `BenefitChipList`, the frozen
primitives, `ROUTES`, and the M2.5 verification harness.

**`zustand` should not be added** — see §2/D6.

## 2. Are D1–D4 the only remaining architectural decisions?

**No. Three more exist, and one of the four is mis-framed.**

### D5 — Is React Hook Form proportionate here? *(new)*

Under D2=A the calculator is a **single** numeric input plus a button. RHF and a
Zod resolver are a meaningful addition to the shared bundle for one field, and
Document 13 explicitly targets bundle discipline. Two defensible answers:
install now and establish the platform form pattern on a trivial first case
(Booking in Phase 3 needs it regardless), or validate with a Zod schema and
local state and introduce RHF at the first real form. `phase-2-roadmap.md`
specifies RHF, so choosing otherwise needs your approval.

### D6 — Compare selection: the plan's recommended tool contradicts Document 09 *(reframed)*

This is the most consequential finding in this review.

`09_State Management Strategy.md` §3 classifies **"Compare List" as Feature
State** — "shared within a single business module". §4 assigns Feature State to
**"Custom Hooks / Context (only if needed)"** and reserves **Zustand for Global
Application State** (auth, theme, language, notifications, navigation,
permissions). §5 is explicit: *"The global store should contain only
application-wide data… Do not store marketplace products or portfolio data
here."*

So D4's recommended "Zustand store" is the wrong tool by the approved blueprint.
The correct shape is a **module-scoped React context + hook** inside
`modules/marketplace`, holding **ids only**.

That correction exposes a second problem the plan does not mention: **where does
the provider mount?** Selection must survive Home → detail navigation, so it
must sit above both routes — `app/(public)/layout.tsx`. But `app/providers.tsx`
documents its seats explicitly (MSW, React Query, Theme, Auth, Toast, Analytics)
and none is a feature provider. Mounting a Marketplace provider in the public
shell is a new architectural element.

Options, in order of increasing commitment:

| | Approach | Assessment |
|---|---|---|
| **A** | Defer compare to M2.7; the button is present but inert | No new architecture, no new seat, no dependency. Deviates from the approved screen, where the button is enabled. |
| **B′** | Module context + hook, provider mounted in `(public)/layout.tsx` | Correct per Document 09, no new dependency. Adds a provider seat — needs your approval, and the seat list in `providers.tsx` should be amended. |
| **C** | Zustand global store | **Rejected** — contradicts Document 09 §4 and §5. |

Recommendation: **B′**, and in the same decision settle where selection
ultimately lives: *the in-memory context is the source of truth; `/compare?ids=`
is a shareable projection hydrated into it on load.* Without that sentence,
M2.7 inherits two candidate sources of truth for one piece of state — the exact
failure I1 exists to prevent, arriving with four products on screen instead of
one.

### D7 — Is the action bar sticky, and how does it interact with the footer? *(new)*

`phase-2-roadmap.md` says "sticky action bar". Document 05 defines only a sticky
header. The approved mobile screen shows the bar pinned at the bottom with a
divider and no footer beneath it; the desktop screen shows it as the last
element of the content card. Sticky-to-viewport requires reserved bottom padding
on the scroll container and a decision about whether it overlays the public
footer. This is a layout decision, not an implementation detail.

## 3. Is the proposed component hierarchy correct?

Mostly. **Two corrections.**

### 3a. The calculator must not compute *(blocking)*

`07_Component Architecture.md` §15: *"Business logic belongs in: Hooks,
Services, State management, API layer. Components should receive prepared data
rather than fetch or transform it directly."* `12_Coding Standards.md` §"Keep
business logic out of UI components" repeats it.

The plan's §2.4 says both "the component computes nothing" and "the calculator
calls the same util" — those contradict each other. The correct split mirrors
`SearchBar` exactly, which is already the module's precedent for a form:

```
InvestmentCalculator   presentation-only
  owns    draft amount (transient, I6)
  props   product rate + tenure, `result`, `onCalculate(amount)`

ProductDetailScreen    sole hook owner
  owns    the calculation — calls calculateMaturity (or a service method)
```

This also removes a subtle duplication: the *default* result needs no
calculation at all. `ProductSummary.estimatedReturns` is already computed by
`ProductService` at `REFERENCE_AMOUNT` (₹1,00,000) and already equals the
approved ₹1,07,978. The screen should render that on load and only compute when
the user submits a different amount.

### 3b. Record the business-component placement rule *(non-blocking)*

Document 07 §7 lists "Deposit Calculator" — and "FD Product Card" — as Business
Components, which §9 and the folder structure would place in
`components/business/`. The project already places `FDProductCard` in
`modules/marketplace/components/`, so an interpretation has been made and works:
**domain-specific business components live in the module; cross-module ones
(`AmountDisplay`, `BankBadge`, `InterestRateDisplay`, `TrustIndicator`) live in
`components/business/`.**

Keeping the calculator in the module is right, and the ESLint boundaries confirm
it: `components → module` is forbidden, so a calculator in `components/business/`
could not import `calculateMaturity` without first promoting the util and its
types to `@/utils` and `@/types`. The rule should be written into the plan so
M2.7's Comparison Table does not re-open it.

Everything else in the component table is correct: props-in/callbacks-out,
frozen primitives only, `BenefitChipList` reused rather than rebuilt.

## 4. Are invariants I1–I8 preserved?

Yes, under D1=A′ and D3=A — with one scoping amendment needed.

| # | Status on this route |
|---|---|
| I1 | ✓ No listing state here; nothing duplicates it |
| I2 | n/a (no hero) |
| I2a | ✓ `ProductDetailScreen` is the sole hook owner. Under D3=A this route has **zero** URL writers, which is stronger than the invariant requires |
| I3 | ✓ Every section component is props-driven — subject to correction 3a |
| I4 | ✓ Same query chain, same key factory, no parallel fetch path |
| I5 | ✓ D1=A′ adds **no** key; compare reuses `products.compare(ids)` |
| I6 | ✓ Calculator draft and accordion open state are local; nothing reaches the URL |
| I7 | ✓ Vacuous — no writes on this route |
| I8 | ✓ Opening a product is intent; `<Link>` pushes by default. "Back to Marketplace" is a `<Link>`, not `router.back()` — correct for users arriving from a shared link |

**Scoping amendment (N7).** I1–I8 live in a document titled *Marketplace URL
State* and are written about Home. M2.6 is the module's first second route.
Before implementation, add one line stating that I1–I8 are **module-wide**, with
ownership scoped **per route** (each route has at most one URL writer). Without
it, M2.7 re-litigates the same ground. This is an amendment, not a new
invariant.

**Add one probe:** assert that the detail route contains zero `router.push` /
`router.replace` call sites. That is the cheapest possible guard against D3
being quietly reversed during implementation.

No item here is load-bearing debt. The plan does not introduce a second data
path, a second URL writer, or a duplicated formula.

## 6. Missing risks, edge cases, and API contract issues

The plan lists six risks. These are additionally required:

| # | Issue |
|---|---|
| **E1** | **404 vs 500 must be distinguished.** `ApiError` carries both `status` and `code` (`PRODUCT_NOT_FOUND`). A 404 renders `not-found`; a 500 renders the retryable error card. Conflating them turns a transient outage into "this product does not exist". React Query's `retry` already skips 4xx via `isClientError`, so the not-found path must not retry |
| **E2** | **Amount below `minInvestment`.** The approved screen shows no error state. `Input` has an `invalid` variant, so no new primitive — but the error **copy** is new UI and needs confirmation |
| **E3** | **Do not recompute on mount.** `estimatedReturns` already carries the approved default figures (see 3a) |
| **E4** | **`typedRoutes: true` vs `ROUTES.product(id)`.** The builder's return type widens to `string`, which is not assignable to `Route`. The M2.5 URL hook already casts once, deliberately. The cast belongs in `constants/routes.ts` — one place, not every `<Link>` |
| **E5** | **`generateMetadata` cannot fetch — plan §2.1 is factually wrong.** MSW runs in the browser only (`MswProvider` starts a worker in a mount effect) and `src/app/api/` contains no route handlers. A server-side fetch of `/api/v1/products/:id` would reach nothing. Metadata must be static until a real API or route handlers exist |
| **E6** | **SEO consequence.** Like Home (M2.4 risk R2), this route is client-rendered, so the product `h1` and rate are absent from prerendered HTML. That mattered little for a filtered listing; a product page is the canonical indexable unit. Not solvable while data is browser-mocked — record it, do not discover it later |
| **E7** | **A valid id whose detail payload is incomplete.** The MSW handler builds details from the summary, so this cannot occur today; it will once a real API exists. The screen should render the sections it has rather than fail wholesale |

## 7. Is the task order correct?

Nearly. **Three corrections.**

1. **Add T2.6.0 — dependencies and document amendments** (installs per D5/D6;
   the I1–I8 scoping line; the roadmap §6 amendment). Doing this first prevents
   a tree that is green but describes code that does not exist.
2. **404 wiring moves from T2.6.2 to T2.6.3.** The route file can create the
   `not-found` boundary, but detection happens where the query result is
   observed — the client screen. As written, T2.6.2 claims work it cannot do.
3. **T2.6.7 (compare) moves to last and is gated on D6.** It is the only task
   that adds a provider seat; if D6=A it disappears entirely. Nothing else
   depends on it.

Otherwise the order is right, and right for the same reason as M2.5: the data
contract (T2.6.1) precedes anything that renders against it.

## 8. Anything else before implementation?

The verification plan needs no structural change. K1 — *open a product, press
Back, land on the listing with filters and page intact* — is the end-to-end
payoff of I8 and should stay exactly as written. Add:

- the zero-URL-writers probe (§4);
- an assertion that `ProductDetails` remains assignable to `ProductSummary` (§5);
- K8: a 404 renders `not-found` **and issues no retry**; a 500 renders the
  retryable card (E1).

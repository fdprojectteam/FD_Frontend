### C1 — **Blocking: the Eligibility row has no data path**

The approved screen has an **Eligibility** row reading `Resident, 18+`.

- `eligibility` lives on `ProductDetails`, not `ProductSummary`.
- `ProductRepository.listByIds()` returns `ProductSummaryDto[]`.
- `productService.getProductsByIds()` returns `ProductSummary[]`.
- The MSW handler's `?ids=` branch maps through `findProductSummary`.
- Therefore `useCompareProducts` **cannot** supply eligibility today.

This is not a defect in M2.1 — the batch was built before the comparison screen
was designed in detail. But the row is approved, and no amount of care inside
`buildCompareRows` can invent the field.

**Options**

| | Approach | Assessment |
|---|---|---|
| **A** | `listByIds` returns `ProductDetailsDto[]`; `getProductsByIds` returns `ProductDetails[]` | Smallest change that keeps one request. The phase-2 roadmap's own sequencing rationale already says *"comparison reuses detail-level fields"*, so this is the documented intent, not new architecture. Cost: the batch payload gains `faqs`, `terms`, `interestBreakdown` for ≤ 4 products |
| **B** | Promote `eligibility` onto `ProductSummary` | Puts a comparison-only field on all 24 listing rows and erodes the summary/details split M2.1 established deliberately |
| **C** | Four `products.detail(id)` queries instead of the batch | Plan §3.7 already considered and rejected a client-side join; also four requests where one exists |
| **D** | Add a narrow `eligibilitySummary: string` to the summary DTO | Two representations of one concept — the thing `Eligibility` exists to prevent |

**Recommended: A.** It is one line in the repository interface, one in the API
repository, one in the service, and one lookup swap in the MSW handler. It
should be an explicit, separately-approved step — **T2.7.1a** — and not folded
silently into the row builder, because it changes a transport contract.

**C1.2 — a data correction rides with it.** The approved cell reads
`Resident, 18+`; the mock's `residency` is `'Resident individual'`, which would
render `Resident individual, 18+`. `residency` is currently rendered nowhere
(`EligibilityPanel` shows only `summary`), so changing the mock value to
`'Resident'` aligns the data with the approved UI without affecting any shipped
screen. The long form survives in `eligibility.summary`.

### C2 — Dead type, and a name collision

`types/compare.ts` exports `CompareSelection { selectedIds: string[] }`. It has
**no importers**, and the live selection type of the same name lives in
`hooks/use-compare-selection.tsx`. Both are re-exported from the module, so
`import type { CompareSelection }` resolves to different shapes depending on
the path.

Recommendation: delete the dead interface and its barrel export in T2.7.1,
while `types/compare.ts` is open. `CompareRow` stays. This is the cleanup the
M2.6 sign-off flagged, arriving at the moment it costs nothing.

### C3 — Should `CompareRow.id` be a typed union? *(minor, needs a decision)*

It is `string` today. A `CompareRowId` union would let T2.7.5 identify the two
rows the approved mobile card stacks (Benefits, Eligibility) by an exhaustive
type rather than by string literal, and would make a forgotten row a compile
error.

Recommendation: **yes** — add `CompareRowId` to `types/compare.ts` and narrow
`CompareRow.id` to it. Additive, no runtime change. Flagged rather than assumed
because the plan's reuse audit says the compare types are reused *unchanged*.

### No conflict found with

The URL contract (T2.7.1 touches no URL), the compare context (touches no
selection), the cache (touches no query), or the boundary policy (`utils` may
import `constants` and `types`, which is all it needs).

## Step 3 — Implementation design

### 3.1 Inputs and outputs

- **Input:** an ordered array of products, in **column order** — the user's
  selection order, which the design relies on for the leftmost-tie rule. Typed
  `ProductDetails[]` under C1 = A.
- **Output:** `CompareRow[]` — always seven rows, in fixed order, or `[]` for
  empty input.
- **Pure.** No React, no I/O, no clock, no locale lookup beyond the shared
  formatters. Same input ⇒ same output.

### 3.2 Row specification *(from the approved screens, verified cell by cell)*

| # | id | Label | Source | Formatter | Winner |
|---|---|---|---|---|---|
| 1 | `interestRate` | Interest Rate | `interestRate` | `formatRate` | **highest** |
| 2 | `tenure` | Tenure | `tenureMonths` | `formatTenure` | **none** |
| 3 | `minInvestment` | Minimum Investment | `minInvestment` | `formatCurrency` | **lowest** |
| 4 | `interestEarned` | Interest Earned | `estimatedReturns.interestEarned` | `formatCurrency` | **highest** |
| 5 | `maturityValue` | Maturity Value | `estimatedReturns.maturityValue` | `formatCurrency` | **highest** |
| 6 | `benefits` | Benefits | `benefits[].label` | join with ` · ` | **none** |
| 7 | `eligibility` | Eligibility | `eligibility.residency`, `.minAge` | `Resident, 18+` | **none** |

Order is declared once as a data table inside the module. The desktop table
reads it row-major; the mobile card reads the same array column-major
(`rows.map(r => r.values[j])`). **One ordering, two presentations** — which is
what keeps them from drifting.

### 3.3 Algorithm

1. `products.length === 0` → return `[]`.
2. For each of the seven specs, in order:
   - `values` = `products.map(spec.format)` — the display strings.
   - `bestIndex` = `null` when the spec has no metric, otherwise
     `pickBest(products.map(spec.metric), spec.direction)`.

`pickBest(metrics, direction)`:

- If the set of distinct metric values has fewer than **two** members, return
  `null`.
- Otherwise scan left to right keeping the current best, replacing it only on a
  **strict** improvement (`>` for `highest`, `<` for `lowest`).

### 3.4 Winner calculation — three properties worth stating

**Winners are computed on numbers, never on the formatted strings.** Comparing
`"₹10,000"` against `"₹50,000"` is a lexicographic comparison that happens to
look right until it doesn't.

**Ties resolve leftmost as a consequence, not a special case.** Strict
comparison never displaces an equal incumbent, so the first occurrence survives.
The approved screen shows exactly this: HDFC and IDFC both at ₹10,000, only
HDFC marked.

**"Fewer than two distinct values ⇒ no winner" derives assumption A6 instead of
special-casing it.** With one product there is one value, so nothing is
highlighted — which is what A6 asks for — and the same rule covers the case the
design never shows: three products with identical rates. Marking one of three
identical cells "best" would be noise presented as information.

> This second half is **new — assumption A8.** The approved screen evidences
> only a *partial* tie. If design prefers "always mark the leftmost even when
> everything ties", it is a one-line change.

### 3.5 Tie behaviour summary

| Case | `bestIndex` |
|---|---|
| One strict winner | its index |
| Two or more share the best value | the **leftmost** of them |
| All values identical | `null` (A8) |
| Single product | `null` (A6, falls out of A8) |
| Tenure, Benefits, Eligibility | `null` always |

### 3.6 Formatting strategy

Rates, tenure, and money go through the shared formatters — no literal `₹`, no
`%`, no `toFixed` in this module.

Two joining rules have no shared home:

- **Benefits** — `benefits.map(b => b.label).join(' · ')`.
- **Eligibility** — `` `${residency}, ${minAge}+` ``.

Both stay **private to `compare-rows.ts`**. Promoting them to `@/utils/format`
would assert a platform-wide meaning they do not have; one screen renders them
this way. If a second consumer appears, promote them then — with evidence.

### 3.7 Reuse strategy

Reused unchanged: `CompareRow`, `ProductSummary`/`ProductDetails`, `Benefit`,
`Eligibility`, `estimatedReturns`, `formatRate`, `formatTenure`,
`formatCurrency`.
Created: `utils/compare-rows.ts` and its barrel export.
Deliberately **not** used: `calculateMaturity`, `MAX_COMPARE`,
`INTEREST_TYPE_LABELS`, `PAYOUT_LABELS`, `BenefitChipList`, `marketplaceKeys`.

### 3.8 Edge cases

| Case | Behaviour |
|---|---|
| `[]` | `[]` — the empty state is the screen's decision, not the builder's |
| One product | Seven rows, every `bestIndex` null |
| Four products | Normal path |
| All values equal on a row | `null` (A8) |
| A product with no benefits | Renders `—` — **assumption A9**; an empty cell reads as a rendering fault. Every mock product has at least one benefit, so this is defensive |
| Zero or negative figures | Formatted as given. `calculateMaturity` already guards its own inputs; re-guarding here would be a second opinion about a number this module did not compute |
| More than four products | Formatted normally. **The cap is not re-enforced here** (compare-state C2) |

### 3.9 Complexity

`O(R × N)` with `R = 7` fixed and `N ≤ 4`: at most 28 metric reads, 28 format
calls, and 7 small set constructions. Constant in practice.

**No `useMemo` at the call site.** Memoising this would cost more in dependency
comparison than it saves, and would imply an expense that does not exist.

## Step 5 — Risk review

### Duplicated logic

- **Maturity recomputation** is the standing hazard: a contributor seeing
  `principal`, `rate`, and `tenure` on the product may reach for
  `calculateMaturity`. Mitigated by reading `estimatedReturns` and by the probe
  pinning that function to the service.
- **Benefits joining** would be duplicated if T2.7.5's mobile card re-joined
  labels itself. Both presentations consume the same `CompareRow[]`, so the
  join happens once.
- **Winner logic** must not be re-derived in the table for styling. The cell is
  best iff `bestIndex === columnIndex`; nothing recomputes.

### Hidden coupling

- **Row order is UI order in two places at once** — table rows and mobile card
  rows. That is intended and now written down, but it means a reorder here
  silently reorders the mobile card. Assertion 1 pins it.
- **`values: string[]` is presentation-ready.** Any future need for raw numbers
  (sortable columns, export) would have to re-derive them. Acceptable: M2.7 has
  no sorting, and inventing a parallel numeric channel now would be speculative.
- **The Eligibility row will show an identical string in every column**, because
  the mock data is identical. It matches the approved screen exactly, but it
  means that row proves very little in a journey test.

### Dead code

- `types/compare.ts` `CompareSelection` — dead **and** colliding (C2).
- `calculateInterestEarned` — still dead (M2.6 cleanup C2), and T2.7.1 does not
  revive it.
- `INTEREST_TYPE_LABELS` / `PAYOUT_LABELS` cite M2.7 in their doc-block but the
  comparison screen has no row for them. Their comment should be corrected so it
  does not imply a consumer that will never exist.

### Future maintenance

- Adding a row means one entry in the spec table — the design's main virtue.
- If rate slabs arrive (excluded since M2.1), `estimatedReturns` becomes
  amount-dependent and both Interest Earned and Maturity Value would need a
  principal. The builder would then take the amount as an argument. Nothing to
  do now; worth knowing where the seam is.

### Performance

Negligible (§3.9). The real cost on this screen is the network batch, not the
row build.

### One honest note about the approved highlighting

Interest Earned and Maturity Value are computed on a fixed ₹1,00,000 reference
over **each product's own tenure**, so a 24-month product will nearly always
"win" both rows against a 12-month one — as the approved screen shows Kotak
doing. That is the design's choice and is implemented as designed. It is also
precisely why Tenure itself has no winner, and it is worth being aware of before
anyone reads those two stars as "best value".

## A3. Does this violate "reuse `ProductSummary`" anywhere? — No

The change **widens** what the batch returns. It narrows nothing. Because
`ProductDetails extends ProductSummary`, a details object is assignable
everywhere a summary is expected, so no consumer can break.

Verified individually:

| Consumer | Reads | Affected? |
|---|---|---|
| `FdProductCard`, `ProductGrid`, `ProductGridSection`, `HeroSpotlightCard`, `HomeHero`, `ProductHeader`, `KeyInfoGrid`, `InvestmentCalculator` (props typed `ProductSummary`) | list / detail data | **No** — and each would accept a `ProductDetails` if ever handed one |
| `HomeScreen` `selectSpotlight` / `selectRecommended` | `Paginated<ProductSummary>` from `products.list` | **No** — the list endpoint is untouched |
| `useProductPreview` / `selectProductPreview` | `products.lists()` **only** | **No** — it never reads `products.compare()`, so there is no cross-contamination between the two caches |
| `useProducts` | list cache | **No** — cache priming was removed in T2.6.1 |
| `useProduct` | `products.detail(id)` | **No** — a separate key and a separate endpoint |
| `app/(public)/gallery/business-demo.tsx` — a **hardcoded `ProductSummary[]` fixture** | its own literal | **No under A.** This is the file that **would** fail to compile under B′, along with the mock `toSummary` |
| MSW `list` branch, `matchesFilters`, `sortProducts` | `productSummaries` | **No** — the summary array remains the list path's source |
| Zustand store | nothing | **No** — an invariant probe already asserts no product type reaches the store |

**That last column is the whole argument for A over B′.** A touches the batch
path only; B′ would change the shape every list consumer and every fixture must
satisfy — including a gallery fixture that exists purely to demo components.

## A4. One new risk this creates

After A, the `products.compare(ids)` cache holds **full `ProductDetails`**,
which makes it newly tempting to seed `products.detail(id)` from a comparison
result. **Do not.** T2.6.1 removed exactly that priming by approved decision
(D1 = A′) because a written cache entry with a fabricated `updatedAt` is a lie
the devtools repeat back. The temptation is new; naming it here is cheaper than
diagnosing it later.

## A5. Ordering

T2.7.1a is a prerequisite, not a sub-step: without it `buildCompareRows` cannot
be typed, let alone tested. Suggested order — **T2.7.1a** (transport widening +
`residency` correction + the detail-level probe), then **T2.7.1** (the row
builder + 20 unit assertions), with C2 and C3 folded into T2.7.1 since
`types/compare.ts` is open there anyway.
